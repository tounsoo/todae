### Waiting on CI

Cloud sessions have no `gh` and no `watch-pr`, and GitHub stays silent about some pull request states. These changes replace the watcher with GitHub pull request events and GitHub MCP reads.

- **Replace** "Babysitting starts when the user asks for it, which is normally once a phase or a whole stack is built, not when a PR opens." with: A session drives every pull request it opened, from the moment it opens, in `drive` mode.
- **Replace** "A conflict and the watcher's `behind-base` gate are the two blockers you report rather than resolve. For a conflict, say which branch needs the rebase. For `behind-base`, the base branch requires an up-to-date head, so say which branch needs its base brought in. Then stop. Do not fall through to CI to look busy. Name the drift sweep in that report, since trunk may have grown callers of code the stack deletes or moves, and the owner's rebase has to reconcile them in the same wave." with: Resolve a conflict yourself and don't mention it. Merge `origin/main` into the branch (no rebase or force-push; this updates the branch and is not merging the pull request, which still waits for Ben), keep both sides, regenerate generated files with `pnpm schema` and `pnpm --filter docs i18n:stamp`, run the review round from `.agents/playbooks/review-before-pr.md` on `<base>..HEAD`, then push. Tell the user only about a conflict you can't settle, such as two pull requests that change the same behavior in incompatible ways. When `mergeable_state` is `behind`, merge `origin/main` the same way. If that merge had no conflict, run only the first step of the review round, not `interrogate`, before pushing.
- **Replace** "On GitHub, status comes from the watcher at `skills/poteto-mode/scripts/watch-pr/watch-pr` under the installed plugin." with: Status comes from the GitHub MCP tools. Read the pull request's `mergeable_state`, the check runs on the head commit, and the open review threads. GitHub runs no `pull_request` workflow on a pull request that conflicts with its base, and on a draft the `Checks` job finishes as `skipped`, which is not a result, whatever the other jobs report. Right before opening, pushing or marking ready, fetch `origin/main` and run `git merge-tree --write-tree HEAD origin/main`, which exits 1 on a conflict.
- **Replace** "Run `drive` and `background` under `/loop` in dynamic mode. Rearm the watcher after every push wave and every verdict you act on. Watcher output drives wakeups. Never add a second sleep loop." with: Call `subscribe_pr_activity` for each pull request as you open it. If the call fails, or its result says another agent already watches the pull request, tell the user it isn't being watched here. GitHub pull request events (check results, reviews, comments and merge-conflict notices) then wake the session, so never sleep or poll. CI skips a pull request when every path in its diff against the base is one the `pull_request` paths in `.github/workflows/ci.yml` leave out, so no check event will come for it. After subscribing and after every push or mark-ready, read the status. For a pull request CI skips, report from that read. For any other, schedule one backstop: a `send_later` check-in about 30 minutes out whose message stands alone, naming the owner, repo, pull request number and head SHA, and asking the run to read the status with the GitHub MCP tools and push or merge nothing. If a run is still queued or in progress, it schedules one more backstop the same way. If the stop below is met, it tells the user the pull request is ready for Ben. Otherwise it tells the user what is missing or failed. Keep the backstop's `trigger_id` and fire time. When you schedule a new one, or once every check run on the head commit has finished, cancel the pending one with `delete_trigger`, but only while its fire time is still ahead, since deleting a routine that has fired also deletes the run it started. Then end the turn when nothing is left but waiting. Ignore check events for any commit but the current head, such as runs a later push cancelled. On a check event for the head that did not succeed, act. On one that did, read only the head commit's check runs, and act only when none is still queued or in progress. Also act on a review, a comment from someone else, or a conflict notice. Skip events that only echo your own posts. To act, test-merge `origin/main` as above and read the status. A draft is never a stop: finish the review round and mark it ready, as `.agents/playbooks/review-before-pr.md` says.
- **Replace** "On GitHub, stop at `READY` for one PR (single or stack mode)." with: Stop and report when the head commit's `Checks` run concluded `success` and no other run on it failed, timed out or was cancelled (or CI skips the pull request as above), `mergeable_state` is `clean`, and no blocking review thread is open. Runs that a condition skipped, such as the draft-only `Check`, don't count, and `Token consumers` is informational, so mention its failure rather than wait on it. Read all three live right before reporting, not from the last event. If `mergeable_state` is still `unknown` on a second read right after the first, or is `blocked` or `unstable` while CI is done, report what the read shows instead of waiting. After the first report, tell the user again only when the verdict changes.
- **Replace** "`drive` ends at merge-ready." with: `drive` reports at merge-ready and keeps the subscription, so a failing check, a new review or a conflict still wakes the session. Call `unsubscribe_pr_activity` when the pull request merges or closes, or when the user says to stop.
