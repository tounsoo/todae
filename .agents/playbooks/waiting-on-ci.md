### Waiting on CI

Cloud sessions have no `gh` and no `watch-pr`, and GitHub stays silent about some pull request states. These changes replace the watcher with GitHub pull request events and GitHub MCP reads.

- **Replace** "Babysitting starts when the user asks for it, which is normally once a phase or a whole stack is built, not when a PR opens." with: A session drives every pull request it opened, from the moment it opens, in `drive` mode.
- **Replace** "A conflict and the watcher's `behind-base` gate are the two blockers you report rather than resolve." with: Resolve a conflict yourself and don't mention it. Merge `origin/main` into the branch (no rebase or force-push), keep both sides, regenerate generated files with `pnpm schema` and `pnpm --filter docs i18n:stamp`, run the review round from `.agents/playbooks/review-before-pr.md` on `<base>..HEAD`, then push. Tell the user only about a conflict you can't settle, such as two pull requests that change the same behavior in incompatible ways.
- **Replace** "On GitHub, status comes from the watcher at `skills/poteto-mode/scripts/watch-pr/watch-pr` under the installed plugin." with: Status comes from the GitHub MCP tools. Read the pull request's `mergeable_state`, the check runs on the head commit, and the open review threads. GitHub runs no `pull_request` workflow on a pull request that conflicts with its base, and on a draft the `Checks` job finishes as `skipped`, which is not a result, whatever the other jobs report. Right before opening, pushing or marking ready, fetch `origin/main` and run `git merge-tree --write-tree HEAD origin/main`, which exits 1 on a conflict.
- **Replace** "Run `drive` and `background` under `/loop` in dynamic mode. Rearm the watcher after every push wave and every verdict you act on. Watcher output drives wakeups. Never add a second sleep loop." with: Call `subscribe_pr_activity` for each pull request as you open it, and confirm it took. If it didn't, tell the user the pull request isn't being watched. GitHub pull request events (check results, reviews, comments and merge-conflict notices) then wake the session, so never sleep or poll. Read the status once right after subscribing, since a result can land before the subscription, and once more if `mergeable_state` is `unknown`. Then end the turn when nothing is left but waiting. On an event that can change the verdict (a finished check run for the head commit, a review or a comment from someone else, a conflict notice), test-merge `origin/main` as above and read the status. Skip events that only echo your own posts. Treat a `mergeable_state` of `behind` like a conflict. If the head commit has no check run when you read it, and every changed path is one the `pull_request` paths in `.github/workflows/ci.yml` leave out, CI skips the pull request and no check event will come. For any other pull request with no check run queued, running or finished, schedule one `send_later` check-in about 30 minutes out as a backstop, and cancel it with `delete_trigger` once the head commit has a result. If the backstop, a later event or a message from the user still finds no result, tell the user what is missing.
- **Replace** "On GitHub, stop at `READY` for one PR (single or stack mode)." with: Stop and report when the head commit's CI is green (or CI skips the pull request as above), `mergeable_state` is clean, and no blocking review thread is open. Read all three live right before reporting, not from the last event. For a pull request CI skips, report what that read shows rather than wait for a result that won't come.
- **Replace** "`drive` ends at merge-ready." with: `drive` reports at merge-ready and keeps the subscription, so a failing check, a new review or a conflict still wakes the session. Call `unsubscribe_pr_activity` when the pull request merges or closes, or when the user says to stop.
