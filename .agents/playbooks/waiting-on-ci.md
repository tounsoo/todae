### Waiting on CI

Cloud sessions have no `gh` and no `watch-pr`, and GitHub stays silent about some pull request states. These changes replace the watcher with GitHub pull request events and GitHub MCP reads.

- **Replace** "Babysitting starts when the user asks for it, which is normally once a phase or a whole stack is built, not when a PR opens." with: A session drives every pull request it opened, from the moment it opens, in `drive` mode.
- **Replace** "A conflict and the watcher's `behind-base` gate are the two blockers you report rather than resolve. For a conflict, say which branch needs the rebase. For `behind-base`, the base branch requires an up-to-date head, so say which branch needs its base brought in. Then stop. Do not fall through to CI to look busy. Name the drift sweep in that report, since trunk may have grown callers of code the stack deletes or moves, and the owner's rebase has to reconcile them in the same wave." with: Resolve a conflict yourself and don't mention it. Merge `origin/main` into the branch (no rebase or force-push; this updates the branch and is not merging the pull request, which still waits for Ben), keep both sides, regenerate generated files with `pnpm schema` and `pnpm --filter docs i18n:stamp`, commit the merge and the regenerated files, run the review round from `.agents/playbooks/review-before-pr.md` on `<base>..HEAD`, then push. Tell the user only about a conflict you can't settle, such as two pull requests that change the same behavior in incompatible ways. When `mergeable_state` is `behind`, merge `origin/main` the same way. If that merge had no conflict, run only the first step of the review round, not `interrogate`, and push, marking the pull request ready if it is a draft.
- **Replace** "On GitHub, status comes from the watcher at `skills/poteto-mode/scripts/watch-pr/watch-pr` under the installed plugin." with: Status comes from the GitHub MCP tools. Read the pull request's `mergeable_state`, the check runs and commit statuses on the head commit, and the open review threads. GitHub runs no `pull_request` workflow on a pull request that conflicts with its base, and on a draft the `Checks` job finishes as `skipped`, which is not a result, whatever the other jobs report. Right before opening, pushing or marking ready, fetch `origin/main` and run `git merge-tree --write-tree HEAD origin/main`, which exits 1 on a conflict.
- **Replace** "Run `drive` and `background` under `/loop` in dynamic mode. Rearm the watcher after every push wave and every verdict you act on. Watcher output drives wakeups. Never add a second sleep loop." with: Call `subscribe_pr_activity` for each pull request as you open it. If the call fails, or its result says another agent already watches the pull request, tell the user it isn't being watched here and that the one backstop below is then the only check, so they can ask for a status read later. GitHub pull request events (check results, reviews, comments, and best-effort merge-conflict notices) then wake the session, so never sleep or poll. Merge conflicts, other people's pushes and commit statuses such as Vercel's preview deploy may not wake it, so check them on every status read; the backstop below covers a lost event. CI skips a pull request when every file the GitHub MCP tools list for it, across every page, is one the `pull_request` paths in `.github/workflows/ci.yml` leave out, applied in their order, so no check event will come for it. Decide this from the file list, never from an empty check list, which every pull request shows for a moment after a push. A pull request with more than 300 files, or whose list can't be read in full, is not skipped. CI is done when the head's latest `Checks` run comes from a run that started after the last push or mark-ready and has concluded, and no other latest run of a name is queued or in progress. An empty or draft-only check list means CI hasn't started. The head is the pull request's head SHA as the event or a fresh read of the pull request gives it. After subscribing, after every push or mark-ready, and whenever the head changes because someone else pushed, read the status. For a pull request CI skips, report from that read. For any other, schedule one backstop: a `send_later` check-in about 30 minutes out whose message stands alone, naming the owner, repo, pull request number and head SHA. It tells the run to do nothing if the pull request has merged or closed. Otherwise it reads the pull request and its check runs with the GitHub MCP tools and tells the user, in a line, the `mergeable_state` (naming a conflict) and which check runs are still running, failed, were cancelled or never started, or that all finished. If the head is no longer that SHA, someone else pushed, and the line names the new head instead. The run schedules nothing, pushes nothing and merges nothing. Keep the backstop's `trigger_id` and fire time. When you schedule a new one, or when you report the stop below, cancel the pending one with `delete_trigger`, but only while its fire time is still ahead, since deleting a routine that has fired also deletes the run it started. Then end the turn when nothing is left but waiting. On a check event for a commit other than the head you hold, read the pull request: if that commit is now its head, adopt it and treat it as a push; otherwise ignore the event, as for runs a later push cancelled. On a check event for the head that ended any way but `success` or `skipped`, act, unless it is `Token consumers`, which is informational, or a `cancelled` run with a newer run of the same name or one that started before the last push or mark-ready. On any other, read only the head commit's check runs, using the latest run of each name, and act only when CI is done. Also act on a review, a comment from someone else, or a conflict notice. Skip events that only echo your own posts. To act, test-merge `origin/main` as above and read the status. Hold a fix push until CI is done, so one push carries every fix. A draft is never a stop: finish the review round and mark it ready, as `.agents/playbooks/review-before-pr.md` says.
- **Replace** "On GitHub, stop at `READY` for one PR (single or stack mode)." with: Stop and report when either CI skips the pull request as above, or CI is done and, taking the latest run of each name, `Checks` concluded `success` and no run other than `Token consumers` failed, timed out or was cancelled; and in both cases `mergeable_state` is `clean` and no blocking review thread is open. A blocking thread is an unresolved one whose latest comment is not your own reply with a fix or a disproof. Runs that a condition skipped, such as the draft-only `Check`, don't count. A commit status such as Vercel's preview deploy is not CI here: mention a pending or failed one in the report rather than wait on it, and treat an `unstable` state it alone causes as `clean`. `Token consumers` is informational: when its failure is the only one, `unstable` counts as `clean`, and the report mentions it. Read all three live right before reporting, not from the last event. If `mergeable_state` is still `unknown` on a second read right after the first, or is `blocked` or `unstable` while CI is done, report what the read shows instead of waiting. After the first report, tell the user again only when the verdict changes.
- **Replace** "`drive` ends at merge-ready." with: `drive` reports at merge-ready and keeps the subscription, so a failing check or a new review still wakes the session. A conflict or someone else's push might not, so the report is as of that read, and the status is read live again before Ben is asked to merge or when he asks about it. Call `unsubscribe_pr_activity` when the pull request merges or closes, or when the user says to stop.
