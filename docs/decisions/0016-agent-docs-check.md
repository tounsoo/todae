# 0016. CI fails a new page, section or check that leaves CLAUDE.md and the verify skill behind

- **Date:** 2026-11-13
- **Status:** Active
- **Source:** Ben's rule from his agent review on 2026-11-12, that a pull request that adds a page, section or check also updates `CLAUDE.md` and the verify skill in the same pull request, and his "All three" on 2026-11-13 to enforce it in CI.

## Decision

CI's Agent docs job runs `.github/scripts/agent-docs.mjs` on every pull request that changes more than Markdown no tool reads, drafts included. It compares the pull request's head with its merge base on the base branch and lists what the head adds:

- docs pages: routes of `page` files under `apps/docs/app/(en)/` that the base had no page for. They count only when the pull request adds more routes than it removes, and then every added route counts. So a page that moves, however much it changes on the way, isn't new. A Korean page doesn't count, since each one has an English twin.
- docs sections: group `id`s in the `SITE_GROUPS` array in `apps/docs/components/siteGroups.ts`. When the base has sections and the head shows none, because the file moved or its layout changed, the job fails, even with the body line below, until the pull request teaches the script to read it, so a move can't hide new sections. The sections the script then finds count as new in that pull request.
- checks: jobs, and steps that run a command, in workflows that pull requests start (`pull_request` or `pull_request_target`), and commands that the root `pnpm check` chains. A job is known by its workflow and id. A step is known by its name, or by its command when it has none, across all those workflows, so a step copied into another job or workflow isn't new. A step that only uses an action, such as checkout or a cache, isn't a check.

When it adds any of them, the pull request must also change `CLAUDE.md`, and `SKILL.md` or `verify.mjs` in `.claude/skills/verify/`. Where one or both need no change, its body says why on a line `Agent docs unchanged: <reason>`. The script parses the body as Markdown, so the line counts only where it shows as text, not in an HTML comment or a code block, and only with a reason in place of the placeholder. It may be a paragraph, a list item, a quote or a heading, and the first line with a reason counts. A step with no name and a command of more than one line is listed by its first line. Deleting a file doesn't count as changing it, and neither does changing only the verify skill's tests. Otherwise the job fails, names what it found and what is missing, and writes the same lines to the run's summary. The job reads the body from the GitHub API when it runs, so a line added after the push counts once the job is re-run. `Checks` needs the job, and it is skipped only on a push and on a change that is only Markdown no tool reads. The job installs the workspace, as the Static job does, for its YAML and Markdown parsers. The verify skill runs the same script for docs and tooling changes, against `origin/main`, so a thread sees the failure before it pushes.

It checks that the files changed, not what the change says, and review covers the rest. It misses a section heading inside a page, a new test file, a lint rule, a step in a composite action under `.github/actions/`, a job in a reusable workflow that only `workflow_call` starts, a command added to a step that keeps its name, a check added inside a script an existing step runs, and a new page in a pull request that removes at least as many routes as it adds. Renaming a step, a job or a workflow file, or changing the command of a step with no name, counts as adding a check, and renaming a section's id counts as adding a section. Like the other CI checks, it runs the pull request's own copy of the script and workflow, so a pull request that weakens it shows that in its diff.

## Why

Agents learn the repository from `CLAUDE.md` and the verify skill, and the rule to update them with each new page, section or check was a written rule that threads missed: PRs 453, 463 and 465 added docs pages without either. A written rule is the last resort in `AGENTS.md`, so the rule became a check. The body line keeps a pull request that has nothing to add from changing the agent docs for its own sake, and puts the reason in front of Ben before he merges.
