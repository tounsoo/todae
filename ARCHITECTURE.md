# Todae architecture and decisions

Read this before adding a component, hook, recipe, token or docs page. It records what Todae has decided and why, so new work lands the same way.

These are rules for new and changed code. Some older code predates a rule and does not follow it yet. Don't copy an exception into new code; bring old code in line when you are already changing it.

The docs site explains the same ideas to people who use Todae: [Composition](apps/docs/app/(en)/composition/page.mdx), [Build on Todae](apps/docs/app/(en)/guides/build-on-todae/page.mdx), [CSS layers](apps/docs/app/(en)/guides/css-layers/page.mdx), [Tokens](apps/docs/app/(en)/tokens/page.mdx) and [Native platform](apps/docs/app/(en)/platform/page.mdx). This file is for the people and agents who change Todae. Paths such as `src/…`, `tokens/…` and `vite.config.ts` are relative to `packages/design-system`. When a decision here changes, update this file in the same pull request.

## What Todae is

Todae is a low-level base that companies build their own design systems on. A company adds a token package, a few TypeScript declarations and thin wrappers around Todae's parts, without forking Todae.

So choices favor what a company can extend or restyle without copying Todae's code: tokens over hard-coded values, parts over monoliths, native elements over JavaScript reimplementations, and no product knowledge in the package.

## Kinds of exports

What Todae ships is a component, a hook or a recipe. Providers, their hooks, and helpers such as `composeRefs` and `categoryTone` sit outside the split.

- **Component.** Todae can fix its markup, props and behavior without knowing the product's data, fetching, routing, business rules or screen layout. It may own behavior (Menu, Tabs) or only styles from tokens (Stack, Text).
- **Hook.** Behavior with no markup, exported when a recipe or a product's own markup needs it, such as `useRovingFocus` and `useCombobox`.
- **Recipe.** Copyable code in the docs that puts exports together around product data or flow, such as Combobox and File upload. It is not a package export.

Rules:

- **Anything that carries Todae tokens or styles is an exported component**, even when the browser does all the behavior. Link, Table, Separator and VisuallyHidden, for example, are `*.Root` components for this reason. Don't style bare elements in `todae.base`. *Why:* every Todae look should come from an export a company can find, wrap and restyle.
- **A recipe is thin glue.** Keyboard handling, focus management, ARIA wiring, measurement and positioning go in a component or hook, so a company can copy a recipe and restyle it without breaking accessibility. If copied recipe code would still carry hard behavior, move that behavior into Todae.
- **A container that gives context or keyboard handling to whatever children it holds is a component** (Fieldset shares `disabled` and `invalid`; Toolbar gives roving focus). **A composition that wires specific exports to each other is a recipe** (Combobox connects a Field to an OptionList).
- **Don't ship a wrapper with no behavior, styles or tokens of its own.** If the arrangement is worth showing, write a recipe.
- **Don't add a headless hook that only mirrors a component.** `useTabs` and `useMenu` were dropped because the thin native parts plus `useRovingFocus` cover custom markup. Tree's keys are likewise a `tree` mode of `useRovingFocus`, not a `useTree` hook.
- **A look that only redraws an existing component is a variant of it, not a new component.** The typing indicator is `Loader.Root variant="dots"`, not a `TypingIndicator.Root`: it is the same native `<progress>`, with the same role, name and reduced-motion rule. *Why:* Ben chose it when planning the chat components, so a chat UI adds no component that would duplicate Loader's semantics. Ben later renamed Spinner to Loader (2026-10-14), so the spinner is the default `variant="spinner"` beside `dots`, and a component's name says what it is for, not how it is drawn.
- **No icon component and no icon set.** Components take icons as children or slots (`Button.Icon`, `Alert.Icon`). Todae draws the few glyphs a part needs to look whole, such as a close cross or a check, and `GlyphsProvider` swaps them for any library's icons. There is no global icon size scale; give a new icon slot its own `icon.size` token.

## Component API

- **Compound namespaces.** A component with parts is a namespace object with a `Root`: `Menu.Root`, `Menu.Item`, `Table.HeaderCell`. A component without parts is a namespace with only a `Root` (`Separator.Root`, `Stack.Root`). *Why:* one shape across the package.
- **Don't nest namespaces** (no `Field.Button.Root`), and give each root one interactive role. Components sit side by side: a Field and a Popover are siblings, neither wraps the other. The exception is a part whose own picker is part of the control, such as `Field.ColorPicker`, `Field.DatePicker`, `Field.TimePicker`, `Field.DateTimePicker` and ChipList's +N panel: it renders its `Popover.Root` itself, the way `Field.Select` has the browser's picker. Any element other than these pickers wired with `useField`'s `getControlProps` in the same field, a Field part or a custom control, registers when it mounts and becomes the field's control, and the picker leaves the field's name to one that `getControlProps` gave that name, so the swatch and a hex input, or the calendar button and a text input, share one field. With `showValue={false}`, `Field.DatePicker`, `Field.TimePicker` and `Field.DateTimePicker` show only their glyph. *Why:* Ben chose `Field.ColorPicker` as one part, so a color field needs no recipe, and wants it paired with a typed value; `Field.DatePicker`, `Field.TimePicker` and `Field.DateTimePicker` follow it, because the browser's own date and time popups can't take Todae's tokens.
- **Dates and times are one set of Todae pickers, not native inputs.** A date is `Field.DatePicker`, a time `Field.TimePicker` and both `Field.DateTimePicker`, with the same props where they mean the same thing (`value`, `onValueChange`, `min`, `max`, `locale`, `placeholder`, `showValue`, `open`), and a typed value is a `Field.TextInput` beside the picker, written and read with `formatDate` / `parseDate`, `formatTime` / `parseTime` or `formatDateTime` / `parseDateTime`, which take the locale's own formats. A new temporal part follows the same shape. *Why:* native date and time inputs look and behave differently in each browser and on phones, open the browser's own popups, which can't take Todae's tokens, and a date input opened the browser's calendar as well as Todae's, so Ben dropped `Field.DateInput`, `Field.TimeInput` and `Field.DateTimeInput` and chose matching pickers (2026-10-14). A date and time is one part, not a date picker and a time picker in one field, so one value, label and error go together.
- **A part that renders an element forwards native attributes and its ref.** Type its props with `ComponentPropsWithRef<'element'>`, spread the rest onto the element, and merge `className` with `cx`. *Why:* a company wrapper only has to spread props to keep everything working.
- **Don't make behavior depend on a child's component type.** Parts register through context, or a parent looks for a data attribute the child renders. A type check may only guess the first server render, as long as registration or a data-attribute read corrects it after hydration. *Why:* a company's wrapped `OptionList.Option` or `Button.Icon` must still work.
- **Routers plug in through a `render` prop** (`Link.Root`), not an `as` prop or a router dependency.
- **Text Todae writes by itself**, such as a close button's default name, comes from `StringsProvider` (`useStrings()`), not a hard-coded English string. A server entry, which can't read context, uses `DEFAULT_STRINGS`.
- **Glyphs** are read from `GlyphsProvider`. Put glyph state (hidden, rotated, mirrored) on the `[data-todae-glyph]` wrapper span, not on the `svg`, so a swapped-in icon follows it.
- **Server entries.** A component that a Server Component should render directly gets a server-safe entry, `src/server/<slug>.ts`, imported as `@omsoo.design/todae/<slug>`. Add the slug next to the existing ones in four lists: the entries in `vite.config.ts`, `exports` in `package.json`, the server-entry list in `src/entries.test.ts`, and `paths` in `apps/docs/tsconfig.json`. Where the component reads a client provider, the client version is a `*.client.tsx` wrapper exported from the root entry.
- **Keep `'use client'` out of component and hook files.** It sits in `src/index.ts` and the provider files. `src/entries.test.ts` checks that a server entry's import closure has no `'use client'`, hooks, `createContext` or CSS import, so helpers a server entry needs stay hook-free in their own files (`cx.ts`, `tone.ts`).

The rules below were read from the code rather than decided in a thread. Follow them unless there is a reason not to.

- **Controlled state comes in triples:** `value`/`defaultValue`/`onValueChange`, and the same for `open`, `checked` and `pressed`, built on `useControlledState` or `useControlledValue`. The callback gets the new value, not an event, and `undefined` means uncontrolled.
- **`onOpenChange(open, reason)`** passes a typed reason, such as `'escape'`, `'backdrop'` or `'close-button'`, so a product can tell why an overlay closed.
- **Names.** Props types are `<Component><Part>Props` (`BadgeRootProps`). Union prop types are exported as `<Component><Prop>` (`AlertTone`, `ButtonVariant`). Form state is `disabled` and `invalid`, not `isDisabled` or `error`. Modal overlays take `dismissOnEscape`, `dismissOnBackdrop`, `initialFocusRef` and `restoreFocusRef`.
- **Read Fieldset state** through `useFieldsetState`: `disabled` is OR-ed with the nearest Fieldset, and a control's own `invalid` wins over the Fieldset's.
- **Run the consumer's handler first** with `composeHandlers(theirs, ours)`, which skips Todae's behavior when the consumer calls `preventDefault()`.
- **A part rendered outside its Root should throw.** Misuse that can still render (an icon-only button with no name, both `checked` and `defaultChecked`) logs a development-only `console.error` or `console.warn` behind `process.env.NODE_ENV !== 'production'`.
- **State reaches CSS through `data-*` attributes.** Boolean state is an empty attribute, left off when false (`data-selected`, `data-disabled`); enum state is its value (`data-tone`, `data-size`, `data-orientation`). Name an attribute that other Todae code looks up `data-todae-*` (`data-todae-glyph`, `data-todae-roving`).
- **Disabled items.** Menu items and listbox options take `aria-disabled`; menu items also stay in the arrow-key order, so a screen reader announces them as unavailable. Items that are buttons, such as tabs and toggle-group items, take native `disabled`. Standalone native controls take `disabled`.

## Hooks

- **Prefer one options object in and one result object out,** typed `Use<Name>Options` and `Use<Name>Result`, for hooks that drive markup.
- **Prop getters** are named `get<Element>Props` (`getTriggerProps`, `getListboxProps`). A getter that takes the caller's props merges them and keeps the caller's ref.
- **A hook that creates ids** accepts an optional `id` and returns them as `ids`, so a recipe can wire labels by hand. Ids that end up in a CSS selector or ident go through `useDomId()`.

## Tokens

- **Follow DTCG 2025.10.** Aliases are JSON Pointer `$ref`s (`{ "$ref": "#/color/gray/900/$value" }`); the build rejects curly-brace aliases. *Why:* companies should be able to use standard DTCG tools on Todae's tokens.
- **Four layers, lowest first:** `core` (raw scales), `appearance` (light and dark semantics), `density` (spacing per density) and `contract` (what components read; button variants are a contract modifier). A token references a lower layer, a token in its own set or modifier context, or a token in an earlier set or modifier of its own layer in `resolutionOrder` (`tokens/resolver.json`); the build checks this.
- **Give a new component contract tokens and have its CSS read them.** Put them in a file in `tokens/components/` and add that file to the contract set's `sources` in `tokens/resolver.json`; the build ignores a file that isn't listed. Point color tokens at semantic `appearance` tokens; a `ring.focus` color is the exception (see focus rings below). *Why:* a rebrand changes the appearance layer and every component follows.
- **Component token names** are `<component>`, then an optional part, the property, and an optional state (`chip.bg.hover`, `separator.color`). Reuse the state names that exist, such as `default`, `hover`, `active`, `focus`, `disabled`, `invalid`, `selected` and `checked`. Required state sets can be declared as `slots` in `tokens/resolver.json`, and the build checks them.
- **Focus rings read `focus.ring.color`, `focus.ring.width` and `focus.ring.offset`.** A new component's `ring.focus` color token points at `focus.ring.color`, not at the accent; `tokenConsistency.test.ts` checks this. The `focus` set comes before `button` in `resolutionOrder` so button variants can read it. *Why:* one token recolors the focus rings (invalid rings keep their own `ring.invalid` color), and a company's own focusable UI has a ring to reach for.
- **Translucent colors take `alpha` from the `opacity` scale** with a `$ref`, not a literal. `color.bg.transparent` keeps a literal 0 on purpose.
- **Contrast is APCA (Lc), not WCAG 2 ratios.** Text pairs and their minimums live in `$extensions["dev.todae"].contrast` in `tokens/resolver.json`, and the build fails a pair that falls short. A company's tokens are checked against the same pairs.
- **The accent is neutral ink, not a hue.** Don't introduce a blue accent; a build test lets only `color.category` read the blue scale.
- **Tones.** Status tones are `info`, `success`, `warning`, `critical`. Category tones are numbered `category-1` to `category-8`, not named after hues, so a company can re-hue without renaming. Avatar takes neutral and category tones, not status tones. `categoryTone(key)` hashes a string to a tone; keep its pinned test values, since changing the hash changes every user's color.
- **Generated files are committed.** Run `pnpm tokens` after editing token files; `pnpm tokens:check` fails on drift.
- **Extensibility comes first.** Companies add sets, contexts, variants and densities in their own resolver and build them with `todae-tokens build`. New token features should work through that path, not by editing Todae's files.

## CSS

- **Todae's CSS sits in one cascade layer, `todae`.** `src/styles/layers.css` declares `todae.reset` (empty), `todae.base` (tokens and the modal scroll lock) and `todae.components`, and is imported first by every build entry. A company's token build adds `todae.theme` after them. *Why:* a company places Todae with one name, and its own CSS wins by layer order, not specificity.
- **Component styles are CSS Modules** in `@layer todae.components`. Components that style a single native element (Link, Table, Code and similar) use the `todae.components.native` sublayer, so container components such as Pagination beat them.
- **Take colors, spacing, radii and sizes from tokens** through their `--todae-*` custom properties rather than literals. Restyling goes through tokens first; a class works for layout.
- **Classes are camelCase**, and a part's main class is usually `.root`. Name a custom property a sheet sets for its own arithmetic `--_<name>` (`--_ring-room`), so it doesn't look like a token.
- **Space a label or caption from its control with `Field.Group`,** a column that puts the label or caption `field.label.gap` above the control. Label carries no margin. Description and ErrorMessage keep their own top margin for use outside a group; inside one the group gives them the same distances. *Why:* Ben chose one wrapper that also covers captions, such as a `Text.Root` over a RadioGroup, which a Label margin can't reach.
- **Space layout with named gap steps, not values.** `Stack.Root` takes `gap="none" | "condensed" | "normal" | "spacious"`; each step but `none` is a contract token that reads a density token, so it follows the density. A gap that is not a step is the product's own CSS. `Grid.Root` still has one `grid.gap` and no steps. *Why:* Ben chose named steps over a free value so spacing stays on the density scale.
- **Style markdown's bare elements through `Prose.Root`.** Its sheet reaches `h1`–`h6`, `p`, `ul`, `ol`, `li` and `blockquote` through `@scope`, with any other element as the lower bound, so a demo, card or code block inside the prose keeps its own type. It zeroes each child's end margin and the first child's start margin and spaces the rest with `:nth-child(n + 2)`, which outweighs a child component's own margins. A list with a `role`, such as the lists of Stack, Breadcrumbs and Tree, keeps its own indent and item spacing, since markdown renderers leave lists without one. The docs build compiles CSS with Lightning CSS, because Next's default CSS Modules compiler leaves the class inside `@scope` unrenamed. Inline code, code blocks, links and tables are mapped onto their components in the product's markdown renderer, a recipe on the Prose page. *Why:* one export a company can restyle sets rendered text for docs and chat alike, and Todae still styles no bare element in `todae.base`.
- **Streaming belongs to `Message.Root`, not `Prose.Root`.** `streaming` sets `aria-busy` and `data-streaming` and draws nothing; a product shows a reply still coming with Loader's `dots`. Todae does no token smoothing in JS, and a message knows nothing about any agent SDK's message shape. *Why:* Ben chose this for the chat components, so Prose stays a plain text style that docs and chat share. He dropped the caret drawn from CSS after four review rounds, because selectors can't see text nodes, so no rule placed it right in all rendered markdown.
- **Use logical properties** (`inline`, `block`) for layout, and `:dir(rtl)` for anything that must flip.
- **Some CSS rules are tested.** Read `src/styles/tokenConsistency.test.ts` before writing a new sheet: it covers focus rings, disabled styles, tones and which tokens a sheet may read. `src/components/noScrollbarStyling.test.ts` bans scrollbar styling, and `src/styles/no-container-transforms.test.ts` bans a `transform` on an element that may contain a tooltip trigger.
- **Forced colors.** Where a state shows only through fill (pressed, selected, checked, current), add an `@media (forced-colors: active)` rule that maps it to system colors.
- **Use `!important` only for rules that must hold**, such as `VisuallyHidden.Root` and hidden tab panels.
- **Wrap hand-written selectors in `todae.base` in `:where()`,** so any class a company adds wins.

## Platform

- **Use the best native HTML and CSS features, with no JavaScript fallbacks and no support matrix.** The feature list is on the [Native platform](apps/docs/app/(en)/platform/page.mdx) page; add a feature there when a component starts to depend on it. *Why:* Todae stays small and gets better as browsers do.
- **Overlays.** `Dialog` and `BottomSheet` render in place on a modal `<dialog>` (no portal), so they inherit the theme. `Popover`, `Menu` and `Tooltip` use `popover="manual"` with CSS anchor positioning. Page scroll stops through `:root:has(dialog:modal)` in CSS, not a scroll-lock hook.
- **Toast** holds text and buttons, no nested menus or dialogs. Its region follows Todae's modal stack into the front modal; a product's own modal `<dialog>` joins that stack through `useModalLayer`.
- **Motion** takes its durations and easings from contract tokens, respects `prefers-reduced-motion`, and only has to work in Chrome. Don't add workarounds for Safari motion gaps.

## Accessibility

- **Follow the ARIA Authoring Practices pattern** for each interactive component, and keep that behavior in the component or a hook, not in a recipe.
- **Scroll containers that hold controls keep focus rings whole.** `ScrollArea`, `BottomSheet.Body`, `Popover` and the `Dialog` and `Drawer` panel run `revealRing` from `src/components/revealRing.ts` when focus lands (Dialog and Drawer from the `<dialog>`'s composed `onFocus`, with the panel as the area), and set `scroll-padding` to a ring's width plus offset. A new part that scrolls controls with outset rings does the same. A part that draws a control's ring on a child or sibling of the focused element, such as a Checkbox indicator, the ColorPicker thumb or a Tree row, marks that element `data-todae-focus-ring=""`; `tokenConsistency.test.ts` lists those rules. Code that moves focus where it must not scroll calls `focusWithoutScroll(el)`, not `el.focus({ preventScroll: true })`, so `revealRing` leaves it alone too. *Why:* the browser scrolls a focused control into view by its own box, so a ring drawn on another element, such as a Field shell, can stay cut at the edge.
- **A conversation is a labelled region, not a log.** `Conversation.Viewport` is a `<section>` named by the `conversation` string, and puts no live region around the messages. Conversation announces through `useAnnouncer` when an `article` in its content takes `aria-busy="true"` and when that clears, and says nothing at the end when the message holds a `role="alert"`. Following the end of a growing conversation stays inside Conversation, with no exported `useStickToBottom`. Messages don't take `content-visibility: auto`: its paint containment would clip the focus rings of action buttons at a message's edge. *Why:* Ben chose the more accessible option when planning it. `role="log"` is a live region, so it would read every streamed word, and with `aria-live="off"` its role means nothing.
- **An attachment hands focus on when it is removed.** When an `Attachment.Root` that holds focus unmounts, its layout cleanup (which runs while the element is still in the page) notes its place among its parent's children, or among the `li`s of its list when it is an `li`'s only child, and a microtask queued then, which runs once the commit is done, checks the page: if the root is gone, its list is still there and nothing else has focus (looking into shadow roots), focus goes to the reachable remove button of the attachment now in that place, else the one before. Focus then moves outside React's commit, so `onFocus` handlers such as `revealRing`'s run. A StrictMode check or a hidden Suspense tree leaves the root in the page, so nothing moves. `Attachment.Remove` focuses itself before calling the product's `onClick`, as ChipList's remove does, since Safari does not focus a clicked button; this is an exception to running the consumer's handler first. It looks no further than that list, so focus stays among the same files; after the last one, the product places focus. `Attachment.Remove` is named from `Attachment.Name`'s text through the `removeAttachment` string, so the name stays a string. *Why:* removing a focused element drops focus to the page, and only Todae's parts know where the next file is.
- **A composer sends on Enter the way a form does.** `Composer.Root` is a `form`, and Enter in one of its textareas calls `requestSubmit` with the form's first submit button, and does nothing while that button is disabled, as implicit submission does from a text input. It finds the textarea from the key event's target, not from a component type. Shift+Enter, Enter with another modifier, and Enter that ends an IME composition (`isComposing`, or `keyCode` 229, which Safari sends after `compositionend`) are left to the textarea. A held Enter in a textarea sends at most once. The root's `onSubmit` and its busy gate act only on the form's own submits, since React bubbles a portaled form's submit through it. While `busy`, the root cancels every submit event of its form, so a text input's own implicit submission or a product's button sends nothing either. `Composer.Submit` is one button that is Send or, while `busy`, Stop, so a focused button keeps focus as it swaps, while it stays enabled. On Submit, a second click of a double click (`detail` above 1) and a repeated Enter do nothing, since they land after the swap; a deliberate second press within the double-click interval counts as part of the double click. Stop cancels its click's default action: `onStop` clears `busy` before the browser acts on the click, and by then the button is a submit button again. Its name comes from `useDismissLabel`, like the close parts. Chromium takes focus off a button the moment it turns disabled, during React's commit, so Submit listens for its own `focusout` and, when the button was enabled at the last commit and is disabled now, in a microtask focuses the form's first enabled textarea if nothing else has focus. The composer's box, its rows and its counter are Field's: buttons go in a `Field.Row`, and there are no `Composer.Actions` or `Composer.Attachments` parts. *Why:* `Field.Row` already draws a composer's rows, so those parts would be wrappers with nothing of their own; and Korean and Japanese typing commits words with Enter.
- **Mentions and slash commands keep the native textarea.** `useMentions` finds the trigger word at the caret (the nearest trigger character before it that may start a word there: at the start of the text or after whitespace, or with `position: 'start'` only with nothing but whitespace before it; the word runs to the next whitespace), keeps the textarea a textbox with `aria-autocomplete`, `aria-haspopup`, `aria-controls` and `aria-activedescendant` (no `aria-expanded`, which a `textarea` may not take, so the count is announced through `useAnnouncer` instead), and leaves keys alone during an IME composition. A pick replaces the word with `document.execCommand('insertText')`, so it lands on the textarea's own undo stack; where `execCommand` is missing, throws or returns false, the hook sets the text itself. A read-only or disabled textarea opens no list. Committed tokens are ranges carried through each edit by the changed span, placed at the caret where the edit came from typing, and checked against their text, not found again by pattern. The text and its tokens are one draft: `value` holds both and `onValueChange` hands back both in one call, worked out in the edit's event from the rendered draft, so a product cannot store one without the other, and an edit it rejects or commits later moves nothing on its own. While a pick waits for the product to commit its text, no list opens, since the caret belongs to neither text; the wait ends when the text arrives, when the product puts in another text, or when the user edits, moves the caret with an arrow, Home, End or Page key, or presses the primary button on the textarea. Ben chose one draft over separate `tokens` and `onTokensChange` props, which let a product's text and tokens drift apart when it stored one later than the other. A token in `value` that does not hold its text is left out. The hook remembers the tokens each recent text last had, so undo and redo restore them. `Field.Textarea`'s `highlights` draws them on an `aria-hidden` sibling after the textarea, placed over the textarea's box with anchor positioning (and not drawn without it), behind its visible text (above it in forced colors, where tokens draw only an outline); the layer copies the textarea's computed type, padding and own `lang`, and its scroll, and token spans draw only a background, so they move no text. The caret word's span carries the popover's anchor. *Why:* Ben kept the native textarea, not contenteditable, so IME, undo, spellcheck and screen readers keep the browser's behavior.
- **A step list says each step's status in words.** `Steps.Root` is an `ol`, and each `Steps.Item` hides its marker and starts with a visually hidden status word from the `stepDone`, `stepCurrent`, `stepPending` and `stepError` strings, which a non-empty `statusLabel` replaces. The running step takes `aria-current="step"`, and its marker is a `Loader.Root`, not an indicator of its own. *Why:* Ben chose a step list component for an agent's plan (2026-10-14), and a status drawn only as a glyph or a color is lost to a screen reader.
- **Toolbar keeps its no-tabindex design:** Tab is steered to the edge of a run instead of managed `tabindex`. This was chosen knowing its limits (an ancestor that cancels Tab after the hop, an item that stops Tab propagating, Safari skipping buttons by default); don't switch back.
- **axe runs over the docs demos in a real browser**, with color contrast off, since contrast is APCA in the token build.

## Tests

- Design-system unit tests sit next to the code as `*.test.ts(x)` and run in jsdom unless a file sets another environment.
- Behavior that needs real layout, focus or the top layer goes in `src/browser/*.browser.test.tsx`, which runs in Chromium through Playwright (`pnpm test:browser`).
- Add each new part to `src/components/parts.test.tsx`, which checks that parts forward native attributes and their ref.
- `src/components/overlay.parity.test.tsx` holds Dialog, Drawer and BottomSheet to one contract (labelled, initial focus, Escape, backdrop reason, focus restore, named close button). A new modal overlay should join it.
- Keep one copy of a check: when jsdom and a browser test cover the same behavior, keep the browser one only if jsdom can't model it.
- Docs tests import the built package, so run `pnpm build:ds` before `pnpm test` in a fresh checkout.

## Docs

Each component, hook and recipe gets a page in `apps/docs/app/(en)` and a Korean twin in `apps/docs/app/ko`, changed in the same pull request (see [`CLAUDE.md`](CLAUDE.md) and [`apps/docs/TRANSLATING.md`](apps/docs/TRANSLATING.md)).

- **Page shape for a component or hook:** a short intro with a live `<Example>` and code, any topic sections, then `## Accessible composition` (**Todae handles:** / **You supply:** / **Watch for:**), `## When to use` (**When:** / **When not:**), and `## Props`. The docs MCP server reads "When to use".
- **A part with enough to say gets its own page** under its component, such as `/field/select`. List it as a child of the component's link in `siteGroups.ts`; the sidebar shows children as real links in a collapsible list, not a `role="tree"`. *Why:* Ben chose collapsible links, so every entry stays a link.
- **Prop descriptions** live in each part's `*.meta.ts` and reach the props table through `pnpm schema`. When one changes, update its Korean entry in `apps/docs/lib/i18n/props/ko.json`.
- **Tables are JSX** with `Table` parts. The docs MDX has no GFM, so pipe tables render as plain text.
- **Write narrow claims.** Absolute words such as "only", "never" and "always" are the claims reviews most often find wrong. State what the code does and stop.

### Code blocks and live examples

Code on a docs page is copied into products, so write it in the package's own style and wiring. `apps/docs/lib/codeBlocks.test.ts` checks three of these rules mechanically: that each fence names one of the languages below, that no line starts with a tab, and that `...` is not used as a placeholder. It skips the pages in its `PENDING` set, which don't follow this section yet.

- **Every fence names its language:** `tsx` for code with JSX or a hook call, `ts` for other TypeScript, `css`, `json` or `sh`.
- **Indent with two spaces**, not tabs. In TypeScript, use single quotes for strings, double quotes for JSX attributes, semicolons, and trailing commas in lists that span lines, as `packages/design-system` does.
- **Mark left-out content with `…`**, such as `<Dialog.Body>…</Dialog.Body>`. Don't use `...`, which reads as a spread.
- **Declare each id that a snippet names in `htmlFor` or an `aria-*` attribute,** such as `const id = useId();` or `const cb = useCombobox({ … });`, above the JSX. App state such as `value` and `setValue` can be assumed.
- **Show real wiring.** A `Label.Root` sits with its control in a `Field.Group` and points at it with an id from `useId()` or a hook's `ids`, not a literal. Every control has an accessible name. Links are `Link.Root`, and a router's link goes in through its `render` prop.
- **Icons are real icons with their import,** from `lucide-react`, not placeholder names such as `YourIcon`. Inside a slot such as `Button.Icon`, put the icon element on its own line.
- **Imports.** A block with an `export function` imports everything it uses: Todae from `'@omsoo.design/todae'`, or from a server entry such as `'@omsoo.design/todae/code'` when a Server Component should render it.
- **The site renders code with Todae's own parts.** MDX maps fenced blocks to `Code.Block` (inside a `ScrollArea.Root`, through `DocsPre`) and inline code to `Code.Root`. The docs set the fenced blocks' `code.block.bg` and `code.block.radius` tokens on that wrapper rather than overriding `Code.Block`'s padding, type or colors.

When the project settles a question about concepts, API shape, tokens, CSS or platform use, add it to the section it belongs to here: the rule, then why. Remove a rule that a later decision replaces instead of keeping both.
