# Todae architecture and decisions

Read this before adding a component, hook, recipe, token or docs page. It records what Todae has decided and why, so new work lands the same way.

These are rules for new and changed code. Some older code predates a rule and does not follow it yet. Don't copy an exception into new code; bring old code in line when you are already changing it.

The docs site explains the same ideas to people who use Todae: [Composition](apps/docs/app/(en)/composition/page.mdx), [Build on Todae](apps/docs/app/(en)/guides/build-on-todae/page.mdx), [CSS layers](apps/docs/app/(en)/guides/css-layers/page.mdx), [Tokens](apps/docs/app/(en)/tokens/page.mdx) and [Native platform](apps/docs/app/(en)/platform/page.mdx). This file is for the people and agents who change Todae. Paths such as `src/…`, `tokens/…` and `vite.config.ts` are relative to `packages/design-system`. When a decision here changes, update this file in the same pull request.

## What Todae is

Todae is a low-level base that companies build their own design systems on. A company adds a token package, a few TypeScript declarations and thin wrappers around Todae's parts, without forking Todae.

So choices favor what a company can extend or restyle without copying Todae's code: tokens over hard-coded values, parts over monoliths, native elements over JavaScript reimplementations, and no product knowledge in the package.

## Kinds of exports

What Todae ships is a component, a hook or a recipe. Providers, their hooks, and helpers such as `composeRefs` and `categoryTone` sit outside the split.

- **Component.** Todae can fix its markup, props and behavior without knowing the product's data, fetching, routing, business rules or screen layout. It may own behavior (Menu, Tabs) or only styles from tokens (Stack, Text).
- **Hook.** Behavior with no markup, exported when a recipe or a product's own markup needs it, such as `useRovingFocus` and `useCombobox`.
- **Recipe.** Copyable code in the docs that puts exports together around product data or flow, such as Combobox and File upload. It is not a package export.

Rules:

- **Anything that carries Todae tokens or styles is an exported component**, even when the browser does all the behavior. Link, Table, Separator and VisuallyHidden, for example, are `*.Root` components for this reason. Don't style bare elements in `todae.base`. *Why:* every Todae look should come from an export a company can find, wrap and restyle.
- **A recipe is thin glue.** Keyboard handling, focus management, ARIA wiring, measurement and positioning go in a component or hook, so a company can copy a recipe and restyle it without breaking accessibility. If copied recipe code would still carry hard behavior, move that behavior into Todae.
- **A container that gives context or keyboard handling to whatever children it holds is a component** (Fieldset shares `disabled` and `invalid`; Toolbar gives roving focus). **A composition that wires specific exports to each other is a recipe** (Combobox connects a Field to an OptionList).
- **Don't ship a wrapper with no behavior, styles or tokens of its own.** If the arrangement is worth showing, write a recipe.
- **Don't add a headless hook that only mirrors a component.** `useTabs` and `useMenu` were dropped because the thin native parts plus `useRovingFocus` cover custom markup. Tree's keys are likewise a `tree` mode of `useRovingFocus`, not a `useTree` hook.
- **A look that only redraws an existing component is a variant of it, not a new component.** The typing indicator is `Loader.Root variant="dots"`, not a `TypingIndicator.Root`: it is the same native `<progress>`, with the same role, name and reduced-motion rule. *Why:* Ben chose it when planning the chat components, so a chat UI adds no component that would duplicate Loader's semantics. Ben later renamed Spinner to Loader (2026-10-14), so the spinner is the default `variant="spinner"` beside `dots`, and a component's name says what it is for, not how it is drawn.
- **A type role is a `Text.Root` size, not a component.** `size="label"` is the role for eyebrows, kickers and metadata. It reads `text.label.*` for its family, size, weight, leading, letter spacing, case and color, and sets `font-family`, from `text.font.family` by default, while body text and headings leave it to the product, so a company can make labels mono without CSS. A given `tone` or `weight` wins: the default color and weight sit on `.root` and `.heading`, before the role and the tone and weight classes, and a test checks that order. *Why:* a portfolio built on Todae (2026-10-22) needed mono, capital, tracked eyebrows, which a company should get from tokens, and Text already owns type on the token scale.
- **No icon component and no icon set.** Components take icons as children or slots (`Button.Icon`, `Alert.Icon`). Todae draws the few glyphs a part needs to look whole, such as a close cross or a check, and `GlyphsProvider` swaps them for any library's icons. There is no global icon size scale; give a new icon slot its own `icon.size` token.

## Component API

- **Compound namespaces.** A component with parts is a namespace object with a `Root`: `Menu.Root`, `Menu.Item`, `Table.HeaderCell`. A component without parts is a namespace with only a `Root` (`Separator.Root`, `Stack.Root`). *Why:* one shape across the package.
- **A part lives inside its Root or arranges its Roots.** `Menu.Item` goes inside `Menu.Root`; `Button.Group` joins several `Button.Root`s. An element that stands on its own in the Root's place is not a part: another look of the same element is a variant prop, and anything else is its own component, such as `CodeBlock.Root` beside `Code.Root`. *Why:* Ben chose (2026-10-21) to make the code block its own component, since it has its own tokens, scrolling and accessibility needs, and block-only parts such as a copy button need a Root to live in; to drop `Chip.Overflow`, since a +N count is a plain `Chip.Root` with a visually hidden name beside it; and to keep `Button.Group` as a part of the Button family.
- **Don't nest namespaces** (no `Field.Button.Root`), and give each root one interactive role. Components sit side by side: a Field and a Popover are siblings, neither wraps the other. The exception is a part whose own picker is part of the control, such as `Field.ColorPicker`, `Field.DatePicker`, `Field.DateRangePicker`, `Field.TimePicker`, `Field.DateTimePicker` and ChipList's +N panel: it renders its `Popover.Root` itself, the way `Field.Select` has the browser's picker. Any element other than these pickers wired with `useField`'s `getControlProps` in the same field, a Field part or a custom control, registers when it mounts and becomes the field's control, and the picker leaves the field's name to one that `getControlProps` gave that name, so the swatch and a hex input, or the calendar button and a text input, share one field. With `showValue={false}`, `Field.DatePicker`, `Field.DateRangePicker`, `Field.TimePicker` and `Field.DateTimePicker` show only their glyph. *Why:* Ben chose `Field.ColorPicker` as one part, so a color field needs no recipe, and wants it paired with a typed value; `Field.DatePicker`, `Field.DateRangePicker`, `Field.TimePicker` and `Field.DateTimePicker` follow it, because the browser's own date and time popups can't take Todae's tokens.
- **Dates and times are one set of Todae pickers, not native inputs.** A date is `Field.DatePicker`, a range of dates `Field.DateRangePicker`, a time `Field.TimePicker` and both `Field.DateTimePicker`, with the same props where they mean the same thing (`value`, `onValueChange`, `min`, `max`, `locale`, `placeholder`, `showValue`, `open`), and a typed value is a `Field.TextInput` beside the picker, written and read with `formatDate` / `parseDate`, `formatDateRange` / `parseDateRange`, `formatTime` / `parseTime` or `formatDateTime` / `parseDateTime`, which take the locale's own formats. A new temporal part follows the same shape. *Why:* native date and time inputs look and behave differently in each browser and on phones, open the browser's own popups, which can't take Todae's tokens, and a date input opened the browser's calendar as well as Todae's, so Ben dropped `Field.DateInput`, `Field.TimeInput` and `Field.DateTimeInput` and chose matching pickers (2026-10-14). A date and time is one part, not a date picker and a time picker in one field, so one value, label and error go together.
- **A range of dates is one `DateRange` value, picked in `Calendar.Root mode="range"`.** `DateRange` is `{ start, end }`, both days included, and the props types follow `mode`. The first pick anchors a range and the second completes it, in either order; `onValueChange` fires only then, and Escape, or a modal's close request, drops the anchor without closing a popover around the calendar, through the Escape stack (see the Escape bullet). A new `value` equal to one of the last eight ranges picks reported and no value has answered yet is the parent's answer to that pick, however late, and moves neither the grid nor an anchor set since (it and the older reports then count as answered, so quick picks can be answered in turn); any other new `value` drops the anchor and moves the grid to its start unless the Tab stop is on one of its ends. The accepted cost: a parent that turns a pick down and later sets that same value, with no other value between, doesn't move the grid to it. A range holds only days that can be picked: after the first pick, a day past one that `min`, `max` or `isDateDisabled` rules out can't end it. `Field.DateRangePicker` closes on the completed range and sends it through a value input as an ISO 8601 interval, such as `2026-10-03/2026-10-10` (see the value-input bullet). Presets such as "Last 7 days" are a recipe, not part of the picker. *Why:* one value keeps a range's ends from being stored or validated apart, a gap in a range would hide a day that can't be booked, and presets are the product's data.
- **A number is `Field.NumberInput`, not a native number input.** `Field.TextInput` has no `type="number"` (a development warning covers JavaScript callers), so there is one way to enter a number, as there is for dates. It renders a native `<input type="text" role="spinbutton">`, so the browser keeps IME, undo and selection, and the value reaches the form through a value input of type `number` (see the value-input bullet), so the form sends `1234.5` whatever the locale. The pure `formatNumber` and `parseNumber` of `numberText.ts` write and read the locale's text beside `formatDate` and `parseDate`. The decisions:
  - **`onValueChange` fires only on a commit** (blur, Enter, a step key, a step button or a submit of the input's form), never per keystroke. A text that parses to nothing is kept, flagged and blocks its form through the value input's custom validity, and is never committed. *Why:* the callback per parsed keystroke leaks out-of-range values into product state.
  - **The grid wins over the digits the text shows.** A commit is within `min` and `max` and, with a `step`, on the grid counted from `min` (or 0); without a `step` it is rounded to the digits the text shows, by Intl, so the text, `aria-valuenow`, the value input and the callback agree. `boundsOf` is the one source of the lowest and highest number a commit can give, which `aria-valuemin` and `aria-valuemax` and the step buttons' disabled state read too. *Why:* one number everywhere, so the product is never told one the form does not send.
  - **One submit rule: a submit waits for the commit instead of forcing it.** Every commit waits for its own render, a step with no draft too. A submit of the input's form that finds a draft that reads, or a commit that waits for its render (a product's auto-submit in `onValueChange`), is held, the draft commits as blur does, and the form is submitted again once after the render that shows the commit, so the form sends what the product rendered and the product is told the number that is sent. A draft commits once, and a commit that takes the input out of the page still sends the form. One watcher holds it from the moment it is held, on the input's root node and not in the input's effects, which a Suspense boundary or an Activity turns off: it folds every later submit of the form into the held one (cancelled, the newest submitter kept), and its `MutationObserver` sends the form once, from the observer's callback after React's commit and never inside a layout effect, when the input is gone from the page or the page shows the commit (the input counts its commits in a data attribute, which render never reads). So a product's `onSubmit` sees the DOM, refs and layout effects of the whole layout commit (not passive effects, which a commit outside a discrete event runs later) and may call `flushSync`, and visible, Activity-hidden, Suspense-hidden and removed inputs all settle by that one rule. *Why:* forcing a render (`flushSync`) split the product's state from the payload when the submit started in a commit phase. Liveness is a decision: while a commit's render is pending (a Suspense boundary that has not resolved), every submit of the form waits for it, because sending the old number is worse than waiting; there is no timeout. Text that is no number never sends the old number either: the value input's custom validity lets a check that runs block it, and where none will run (a `noValidate` form that is not `Form.Root`, which registers its `<form>` in the `FORM_ROOTS` set of `Form.model.ts` in a layout effect, or a submitter with `formNoValidate`, a `Form.Root`'s too) the hook cancels the submit with `stopPropagation`, so every unreadable input of the form flags, and flags the text and moves focus to the first of them. Two limits: a native validating form checks before `submit` fires, so a programmatic submit with a stale invalid number is blocked (commit first, by blur or Enter); and the product sets its value synchronously in `onValueChange`, since the held submit goes out after the render that answers the commit, not after a transition or a store that updates later. The mechanics live in `useFormSubmitHold`'s comments.
  - **Step buttons keep focus and are not tab stops** (`Field.Increment` and `Field.Decrement` are parts, not a `stepper` prop). They reach the input through an entry it publishes to the field's store, are disabled where a key would do nothing (`canStep`), and are named from the input's label, which one shared `MutationObserver` per document follows (`watchLabel`), reading again only when a label, or an element an `aria-labelledby` names, changes. *Why:* a press must not commit early or take the phone keyboard down, and a label can mount from any component.
  - **Typed characters are filtered only where that is safe**: an `insertText` that could not become a number is refused in `beforeinput`, while deletions, pastes and compositions land and are read or flagged on commit; Home and End are left to the caret, and there is no wheel stepping.
  - `formatOptions` leaves out `UNSUPPORTED_FORMAT_OPTIONS` (compact and scientific notation, significant-digit and rounding options), which `parseNumber` cannot read back or which round differently from a commit. Mechanics (the 15-digit guard, the step arithmetic, the token names) live in the code comments of `numberText.ts` and `Field.NumberInput.tsx`.
  *Why a text input, not a native number input:* it gives a string, no locale grouping, accepts `e`, steps on the wheel and draws a spinner that tokens can't reach.
- **A one-time code is `Field.OneTimeCode`: one native input drawn as boxes, not an input per digit.** The input has `autocomplete="one-time-code"`, is always `dir="ltr"`, and lies transparent over the boxes, which are `aria-hidden` and drawn from the value and the input's selection, never stored; `className` and `style` go on the wrapper that draws them. `onChange` gets the native event with the raw text and `onValueChange` the code. The decisions:
  - **One rule for where text lands: `editOf` in `oneTimeCode.ts`.** Todae puts every insert in itself (typing, paste, a drop), so `maxLength` decides nothing. A cleaned text of `length` or more is a whole code and replaces the value; anything shorter replaces the selection and writes over what follows as far as it needs room, and what still doesn't fit is cut. So nothing typed moves out of its box, and with the caret after a full code nothing lands, so a product that sends at the last character never gets a second, different code from an extra key. Each edit goes in with `execCommand`, so it is a step of the input's own undo. *Why:* four review rounds found bugs while the rules were spread over `beforeinput` branches, composition handlers and a drop side channel.
  - **One `reconcile` for a change Todae didn't make**: autofill that skips `beforeinput`, an insert the browser won't let be cancelled, a composition, the browser's undo. What changed between the input's previous text and its new one is read as an insert by `editOf`, or kept as a deletion. A change that leaves the code as it is reaches `onChange` but not `onValueChange`. *Why:* one reading of the input's text, rather than one per path, so every path keeps the rule.
  - **A composition is the browser's while it runs.** A React write would end it, so the input renders its own text and the boxes show it reconciled. A composed text that is already a code is reported as it is typed, since a phone keyboard may compose a whole alphanumeric code as one word; anything else is applied when the composition ends, with one edit from the input's text. A `value` the product sets during a composition wins. Undo through a composition is best effort: the browser's steps are not the code's, and the input, the boxes and the code only stay one code the rule allows. *Why:* round 5's machinery to keep that undo exact broke in more cases than it fixed.
  - **Full-width digits and Latin letters** (U+FF10–FF19, U+FF21–FF3A, U+FF41–FF5A) count as their ASCII ones in `cleanCode`; not NFKC, which would also turn `½` into `12` and `①` into `1`.
  - **A press or a drop is placed by the boxes**, not by the transparent input's own text: a press on a box selects its character, so typing replaces it, and a press or a drop on an empty box or past the last one is after the code. The wrapper fills the field's row and is left to right in any page, so the room past the last box is after the code. The press is read on `click`, not by cancelling it, so a phone focuses natively and keeps its keyboard. A drop the product cancels in its `onDrop` lands nothing.
  - **The ring goes on the active boxes, not the shell**; with the caret after a full code no box is active and the row draws it. The row (`data-todae-focus-ring`) draws a transparent ring-sized outline while the input is focus-visible, so `revealRing` has the room the moment focus lands, before the render that marks the active box.
  - **The length check is a custom validity** (`useCustomValidity`) while `0 < value.length < length`, so it reports `kind: 'customError'` with the `tooShort` string and wins over a `Field.Root` `customValidity` while the code is short. It is not `minLength`, because the browser's `tooShort` skips a value a script sets or a cleaned paste writes: an exception to "nothing in Todae computes `required` or `min`".
  - **There is no `onComplete`**: the product sends when `value.length === length`.
  *Why one input:* a row of one-character inputs breaks paste, SMS autofill, undo and screen readers, and a native input keeps them all.
- **A part that renders an element forwards native attributes and its ref.** Type its props with `ComponentPropsWithRef<'element'>`, spread the rest onto the element, and merge `className` with `cx`. *Why:* a company wrapper only has to spread props to keep everything working.
- **Don't make behavior depend on a child's component type.** Parts register through context, or a parent looks for a data attribute the child renders. A type check may only guess the first server render, as long as registration or a data-attribute read corrects it after hydration. *Why:* a company's wrapped `OptionList.Option` or `Button.Icon` must still work.
- **A part picks its element in one of two ways.** A part that must know its tag, from a short list of HTML elements, takes `as` (`Stack.Root`, and `Text.Root`, which sizes a heading by its level). A part whose single interactive element can be another element, such as a router's link, takes `render`, which gets the props the part would have put on its element and returns that element: `Link.Root`, `Nav.Link`, `Button.Root`, `Menu.Item` and `Toast.Action`. Type the props `render` gets as `<Part>RenderProps`, or reuse the type of the part it is a kind of, as `Nav.Link` takes `LinkRenderProps`; leave out the props only the default element takes (`Button.Root` drops `type`, `disabled` and the toggle), add no role, and log a development-only error when the element can't carry the part's role, as `Button.Root` does for anything but an `a` or a `button`. Parts whose element must stay a button, such as close buttons and `Menu.Trigger`, take `ButtonActionProps`, which has no `render`. Routers plug in the same way, with no router dependency. *Why:* Ben chose (2026-10-20) one mechanism over a component per role and look, such as a ButtonLink, which doesn't scale; `render` over `as` keeps the props types simple and lets the product choose which props reach a router's link.
- **Text Todae writes by itself**, such as a close button's default name, comes from `StringsProvider` (`useStrings()`), not a hard-coded English string. A server entry, which can't read context, uses `DEFAULT_STRINGS`.
- **Glyphs** are read from `GlyphsProvider`. Put glyph state (hidden, rotated, mirrored) on the `[data-todae-glyph]` wrapper span, not on the `svg`, so a swapped-in icon follows it.
- **Server entries.** A component that a Server Component should render directly gets a server-safe entry, `src/server/<slug>.ts`, imported as `@tounsoo/todae/<slug>`. Add the slug next to the existing ones in four lists: the entries in `vite.config.ts`, `exports` in `package.json`, the server-entry list in `src/entries.test.ts`, and `paths` in `apps/docs/tsconfig.json`. Where the component reads a client provider, the client version is a `*.client.tsx` wrapper exported from the root entry.
- **Keep `'use client'` out of component and hook files.** It sits in `src/index.ts` and the provider files. `src/entries.test.ts` checks that a server entry's import closure has no `'use client'`, hooks, `createContext` or CSS import, so helpers a server entry needs stay hook-free in their own files (`cx.ts`, `tone.ts`).

The rules below were read from the code rather than decided in a thread. Follow them unless there is a reason not to.

- **Controlled state comes in triples:** `value`/`defaultValue`/`onValueChange`, and the same for `open`, `checked` and `pressed`, built on `useControlledState` or `useControlledValue`. The callback gets the new value, not an event, and `undefined` means uncontrolled.
- **`onOpenChange(open, reason)`** passes a typed reason, such as `'escape'`, `'backdrop'` or `'close-button'`, so a product can tell why an overlay closed.
- **Names.** Props types are `<Component><Part>Props` (`BadgeRootProps`). Union prop types are exported as `<Component><Prop>` (`AlertTone`, `ButtonVariant`). Form state is `disabled` and `invalid`, not `isDisabled` or `error`. Modal overlays take `dismissOnEscape`, `dismissOnBackdrop`, `initialFocusRef` and `restoreFocusRef`.
- **Read Fieldset state** through `useFieldsetState`: `disabled` is OR-ed with the nearest Fieldset, and a control's own `invalid` wins over the Fieldset's.
- **Run the consumer's handler first** with `composeHandlers(theirs, ours)`, which skips Todae's behavior when the consumer calls `preventDefault()`. A handler that opens or acquires, such as a trigger's click, pointer enter or focus, follows this rule. A handler that releases or keeps focus bookkeeping runs Todae's part after the consumer's handler, whatever it did. Examples are `useTooltip`'s pointer leave and blur, the focus-leave close or tab-stop return on blur in `Menu.Content`, `Tabs.List`, `ToggleGroup` and `Tree`, `useRovingFocus`'s focus tracking, and `Menu.Trigger` clearing its pending open end on blur. A prevented event then can't leave a tip or menu open, or a key's request pending.
- **Form validation is the browser's, and Todae decides when, in what words and where focus goes.** `Form.Root` is a component: a container that gives context to whatever children it holds, with focus moves and ARIA wiring a recipe may not carry. It sets `noValidate` and holds no values, schema or async logic. Nothing in Todae computes `required` or `min`; `describeValidity` reads the control's `ValidityState` and words the first failed flag from `StringsProvider`, and `validationMessage` is used only for a `customError`, whose text is the product's. `customValidity` on `Field.Root`, `Fieldset.Root`, `Checkbox.Root` and `RadioGroup.Root` goes through `setCustomValidity`, so a live rule blocks a submit like any other and needs no second engine. One control has one custom validity, so each owner registers its message for that element and the control gets the first non-empty one, innermost owner first (the control's own part, then the enclosing fieldsets outward), an empty message or none being no rule; an owner unregisters on unmount or when its target changes, so a `Fieldset.Root customValidity=""` never clears a nested `Field.Root`'s message. Todae reads the element before it writes: it writes the winning message whenever the element's current custom message differs (so a product's `setCustomValidity('')` doesn't make Todae give up its rule), and clears only when the element still holds exactly what Todae wrote (`validity.customError && validationMessage === written`), so a product's own message survives. A control barred from validation (disabled, or readOnly) reports an empty `validationMessage`, so there Todae trusts its record of what it wrote, and a product's own message set while the control is barred may be cleared. On a `Fieldset.Root` it goes to the fieldset's own first validating control, else the first at any depth (the message then shows where that control's error shows), with a development warning when there is none. *Why:* a second validity engine drifts from the browser, and the browser's own message is in the browser's language, not the page's.
- **A validation scope is a `Field.Group` or `Fieldset.Root` inside a `Form.Root`, not a new wrapper.** Its controls are the `input`, `select` and `textarea` elements that take part in validation and whose nearest `[data-todae-validation-scope]` is it, so a nested scope answers for its own. `Field.Group` and `Fieldset.Root` carry that attribute in or out of a form, so "own" is the same structural fact everywhere and `customValidity` lands on the same control either way. An `ErrorMessage.Root` with no `id` registers with the scope, renders only while the scope shows a problem, and is the only thing that puts the error id in `aria-describedby`, so the id never dangles: on the controls for a `Field.Group`, on the `<fieldset>` alone for a `Fieldset.Root`, and never on a control with `invalid={false}`. The scope joins controls through the `FieldsetContext` merge (`invalid` added, `errorId` set), so each control's own `invalid` still wins and a `Fieldset.Root invalid` still applies; nothing is plumbed per control. Outside a `Form.Root` a scope is inert. *Why:* `Field.Group` and `Fieldset.Root` already hold a label and its messages, and Ben chose one wrapper for that.
- **What a scope shows is a pure function of the controls' validity, the server errors, their dismissals and one reveal flag.** Per form: the attempt counter, the dismissals and the summary's entries (the scopes that failed at the last attempt) live in `Form.Root`; per scope: touched and revealed. A change marks only the scope that owns its target as touched, and a change or reset from a portaled element outside the form's DOM acts on nothing. A scope is revealed after a change inside it followed by focus leaving it (`useFocusLeave`, so a window switch is not leaving), or after any submit attempt; a reset un-reveals every scope. There is one timing and no `mode` prop, as `:user-invalid` has one. *Why:* it rewards early fixes and punishes late, and it keeps the prop surface small.
- **Server errors are the product's `errors`, keyed by control `name`, and do not block a submit.** They show at once and win over a native problem in what is shown, across all the scope's named controls, disabled and read-only ones too (native problems come only from controls that validate). Todae never writes `errors`: a product clears it when it sends (in `onSubmit`) and sets it when the reply comes. An edit to a control hides its entry until the next submit, or until `errors` drops that name or changes its text (a map of name to hidden text, forgotten as soon as the entry leaves `errors`, so an availability check that clears and re-sets "Taken." shows it again, while inline `errors` rebuilt every render with the same content changes nothing); a reset hides every current entry. A reply is a change of content, not of object: after a send, a commit whose `errors` content differs from the commit before and has entries is the reply (clear-then-set counts; a rebuild of the same content does not), unless an edit, reset or failed submit came first. A reply lists and focuses only server errors, never a native problem the person hasn't reached, and the row of a disabled control (`:disabled`, so a disabled fieldset counts) in the summary is plain text. The summary stores each row's `Reading` (`name`, `id`, `label`, `disabled`, carrier) as the scope read it, compared by one `sameReading`. In development `Form.Root` warns, when a reply to a send names a control no scope shows, once per form and name; a name no control has yet is rechecked one task later, and the key is spent only when it warns. The check stays at reply detection, not at render. After a successful send the form keeps waiting, so an `errors` change the person didn't cause is taken as the reply. *Why:* the server knows what the browser can't, and a stale error that blocked a resubmit would trap the person.
- **Form's submit check runs before the product's `onSubmit`.** This is a deliberate exception to running the consumer's handler first: a submit with an invalid control is cancelled and never reaches it, unless the submitter has `formNoValidate`, which is a send to the server without the check, not an attempt: it still reaches `onSubmit`, clears the dismissals and waits for a reply (except that a `Field.NumberInput` holding text that is no number blocks even this submit: it is cancelled and focus moves to the text), but leaves the attempt count and the summary's failed list alone, so it reveals nothing new. A failed submit focuses `Form.Summary` if it renders, else the first problem in document order, with the normal scrolling `focus()`. All focus (failed submit and reply) derives from `failingEntries`: a control a scope reads takes focus only as the carrier of its scope's entry, and only when that entry is enabled, so a scope whose shown control is disabled gives no focus to its other controls; on a failed submit these merge in document order with native problems of controls no scope reads. The summary lists the scopes that were failing at the last attempt, so a field fixed and broken again, or edited into a new problem, doesn't join it until the next submit. Its entries are state computed outside render by one `refresh` action: `Form.Root` reads the DOM (with the scopes' own pure helpers) when a submit or reply happens, and again from an effect or event when a scope sets new readings, when a scope unmounts, when `errors` or the dismissals change and when a reset has applied, keeping only the entries still failing. `Form.Summary` renders the stored entries and reads nothing during render. Neither the rows nor the focus wait on the scopes' state. A row links to its control when it has an `id` and is a button when it has none. *Why:* the product's handler should run for a valid form without repeating the check, and a person who submits a form with a problem needs to be told where.
- **Every value a control holds reaches the form through one native, validated element.** `Field.TextInput`, `Field.Textarea`, `Field.Select`, Checkbox, Switch and RadioGroup are that element. A control that is not native (the pickers, `Field.NumberInput`, `Field.ColorPicker`, `Field.ChipInput`, a product's `role="slider"`) renders a **value input**, with the props from `useField().getValueInputProps(options, control)`: an `<input>` of the native type that matches the value (`date`, `time`, `datetime-local`, `number`, `text`), visually hidden with `VisuallyHidden`'s class, `aria-hidden`, `tabIndex={-1}`, `autoComplete="off"`, `data-todae-value-input`. It is not `readOnly`, `inert` or `type="hidden"`, since each of those bars the element from constraint validation. Never write `type="hidden"` for a value a form should validate. It is **controlled** (`value` and a no-op `onChange`), so a value the product sets fires no event, and **a person's edit is announced explicitly**: `useField().notifyValueChange()`, which a control calls from its user path (a pick, a chip added or removed), tells `Form.Root` (`edited`: ends the wait for a reply and hides the server error under the field's name and the names the control and the value input send) and the nearest validation scope (`touch`) through context, with no DOM event. No product-driven set, form reset or mount may read as an edit. The feature lives in `components/valueInput.ts` (`useValueInput`, which `useField` joins), not in the hook. **The getter takes the control's resolved props as data, so the order of calls cannot make it stale:** `control` is what `getControlProps` returned (a picker's own button props, for the picker), and the getter reads `disabled` (including an `aria-disabled` control), `form` and whether the control has a `name` from it; the type makes the argument required and brands it, so only `getControlProps` produces one (a picker's beside branch keeps the brand). The input goes without a name when the control has one, else takes `options.name` (a picker's own `name` prop), else the field's name unless a control already took it, which it reads with `useBesideNamed`; presence is read with `useSyncExternalStore` returning only the boolean a decision needs (`useBesideNamed`, `useBesideControl`), so a control re-renders only when that flips, not as another control mounts; the name its own control took is not counted, so a named control mounts in one commit. The getter's `ref` is the same function across renders while the bounds are, so React does not detach and attach it each time. Nothing overrides the decision at a call site. **Ownership is structural:** the control's ref (`track`) is what a value input speaks for, so a picker's button always gets it, alone or beside another control; beside one it drops only the id and the description, and the button never takes the field's focus target from a counted control (`useControlSetter`). An input focused with no owner blurs. The ref registers the input in `validity.ts` (`registerValueInput`, one private `WeakMap` of `{ field, owner, bound }`): `owner` is used by `focusTargetFor` and `reachTarget` for `Form.Root`'s first-problem focus, `Form.Summary`'s links and the row's `id`, `disabled` and label, and `bound` is `{ min, max }` already worded by the picker with the helper it shares with its button (`dateLabel`, `formatTime`), so `describeValidity` names it without parsing. `Field.Root`'s `customValidity` goes on the field's control when that is a carrier, else on **the first value input of the field in document order** (`valueInputOf`). The messages for `date`, `time` and `datetime-local` read "or later" and "or earlier" (`dateRangeUnderflow`, `dateRangeOverflow`). Focus on the input moves to its owner, so the browser's own check outside `Form.Root` lands on the control too. `FOCUSABLE_FIELD_CONTROL_SELECTOR`, `tabbables.ts` and the shell's focus ring exclude `[data-todae-value-input]`, so it is no tab stop and no press on a shell focuses it. `useFieldPicker` takes `required` once, for the description and the value input, and its `valueInput` gives the props that the `FieldValueInput` component renders with the description; `valueBounds` builds the bounds options. Choices per control: `Field.DatePicker`, `Field.TimePicker` and `Field.DateTimePicker` use `date`, `time` and `datetime-local` with `min`/`max` from their props and `step="any"` on the last two, since the list picks any time; a `Field.TimePicker` whose `min` is later than its `max` is an overnight range, as a native time input reads it, and its list offers the same times (`timeSlots`' `allowOvernight` (`TimeList`'s `overnight`), which only `Field.TimePicker` passes: the one-day list of a `Field.DateTimePicker` with such bounds offers nothing); a native date input holds only the years 1 to 275760, so a value or bound outside them reads as none, and `htmlDate` and `htmlDateTime` warn once in development. A button cannot take `aria-required`, so a required picker is described by the `required` string (`aria-describedby`), and so is a required `Field.ChipInput`'s text box, which is not what must be filled; a custom control sets `aria-required` itself where its role allows. `Field.DateRangePicker` uses `text`, since no native type holds a range, and sends the range as an ISO 8601 interval written by `htmlDateText`, which holds any year and so does not warn; it takes `required` but no `min` or `max`, which its calendar keeps the range within; `Field.ColorPicker` uses `text`, not `color`, because `color` lowercases the value and turns any value that is not `#rrggbb` into black, which would change what a form sends, and it takes no `required` since it always has a color; `Field.NumberInput` uses `number` with `step` from its props (`any` without one) and `min` and `max` from `boundsOf` (the grid points within the range, so an off-grid `max` gives the highest point on the grid), and `bound` in its own format; its text input is cut loose from the field's name (`getControlProps(props, { sendsName: false })`, so the control passed to the getter has none and its name marker is off), so the value input sends `1234.5` whatever the locale and a text input beside it can still take the name; `Field.ChipInput` has always sent only the text being typed, so its value input sends nothing (its text input took the name), carries `1` or nothing and is empty exactly when there are no chips, which `required` checks. A value input is a carrier like any native control: `carriersIn` finds it inside a `Field.Group`. *Why:* a value that submits is then a value the browser validates, and the browser does the math, including date ranges.
- **A part rendered outside its Root should throw.** Misuse that can still render (an icon-only button with no name, both `checked` and `defaultChecked`) logs a development-only `console.error` or `console.warn` behind `process.env.NODE_ENV !== 'production'`. The exception is a server-safe component, such as Card, Table and DataList: its parts read no context, so they render anywhere and can't throw.
- **State reaches CSS through `data-*` attributes.** Boolean state is an empty attribute, left off when false (`data-selected`, `data-disabled`); enum state is its value (`data-tone`, `data-size`, `data-orientation`). Name an attribute that other Todae code looks up `data-todae-*` (`data-todae-glyph`, `data-todae-roving`).
- **Disabled items.** Menu items and listbox options take `aria-disabled`; menu items also stay in the arrow-key order, so a screen reader announces them as unavailable. Items that are buttons, such as tabs and toggle-group items, take native `disabled`. Standalone native controls take `disabled`.

## Hooks

- **Prefer one options object in and one result object out,** typed `Use<Name>Options` and `Use<Name>Result`, for hooks that drive markup.
- **Prop getters** are named `get<Element>Props` (`getTriggerProps`, `getListboxProps`). A getter that takes the caller's props merges them and keeps the caller's ref.
- **A hook that creates ids** accepts an optional `id` and returns them as `ids`, so a recipe can wire labels by hand. Ids that end up in a CSS selector or ident go through `useDomId()`.

## Tokens

- **Follow DTCG 2025.10.** Aliases are JSON Pointer `$ref`s (`{ "$ref": "#/color/gray/900/$value" }`); the build rejects curly-brace aliases. *Why:* companies should be able to use standard DTCG tools on Todae's tokens.
- **One Todae `$type`: `textTransform`** (`none`, `uppercase`, `lowercase` or `capitalize`), for letter case, which DTCG 2025.10 has no type for. Add no other non-standard type. *Revisit when DTCG adds a standard type for letter case:* move to it and retire `textTransform`.
- **The base theme is Graphite:** cool ink grays, a neutral ink accent, small radii and a 600 bold. Tokens that a theme may want to change but Graphite leaves flat still exist, set to a neutral value, such as `card.shadow`, the overlay shadows (`dialog.shadow`, which `sheet.shadow` and `drawer.shadow` follow, `popover.shadow`, which Menu, the field pickers and the Select list follow, `tooltip.shadow` and `toast.shadow`) and each button variant's `shadow` (`shadow.none`, a transparent layer rather than `none`, so Button can add its pressed ring to it), the `font.letter-spacing` tokens (0) and the `font.text-transform` tokens (`none`). *Why:* a company retheme overrides a token instead of writing CSS against a component.
- **Four layers, lowest first:** `core` (raw scales), `appearance` (light and dark semantics), `density` (spacing per density) and `contract` (what components read; button variants are a contract modifier). A token references a lower layer, a token in its own set or modifier context, or a token in an earlier set or modifier of its own layer in `resolutionOrder` (`tokens/resolver.json`); the build checks this. A token in a set before the first scoped modifier, such as core, is declared only on `:root`, so it holds a literal and references nothing.
- **Give a new component contract tokens and have its CSS read them.** Put them in a file in `tokens/components/` and add that file to the contract set's `sources` in `tokens/resolver.json`; the build ignores a file that isn't listed. Give the component's top group a `$description` saying which component reads it, and give a new semantic token its own; a test fails on an undescribed appearance, density or contract token. Point color tokens at semantic `appearance` tokens; a `ring.focus` color is the exception (see focus rings below). Every contract token is read by Todae's code, or listed in `src/styles/tokenUsage.test.ts` as one products apply themselves; a token nothing reads would only mislead a theme author. *Why:* a rebrand changes the appearance layer and every component follows.
- **Component token names** are `<component>`, then an optional part, the property, and an optional state (`chip.bg.hover`, `separator.color`). Reuse the state names that exist, such as `default`, `hover`, `active`, `focus`, `disabled`, `invalid`, `selected` and `checked`. Required state sets can be declared as `slots` in `tokens/resolver.json`, and the build checks them.
- **Focus rings read `focus.ring.color`, `focus.ring.width` and `focus.ring.offset`.** A new component's `ring.focus` color token points at `focus.ring.color`, not at the accent; `tokenConsistency.test.ts` checks this. The `focus` set comes before `button` in `resolutionOrder` so button variants can read it. *Why:* one token recolors the focus rings (invalid rings keep their own `ring.invalid` color), and a company's own focusable UI has a ring to reach for.
- **Translucent colors take `alpha` from the `opacity` scale** with a `$ref`, not a literal. `color.bg.transparent` keeps a literal 0 on purpose. A shadow's color is literal too, since the build rejects a `$ref` inside a shadow layer.
- **Contrast is APCA (Lc), not WCAG 2 ratios.** Text pairs and their minimums live in `$extensions["dev.todae"].contrast` in `tokens/resolver.json`, and the build fails a pair that falls short. Semantic pairs sit on the appearance modifier; pairs of Field, Nav, OptionList and Tree text on their own backgrounds, and of `text.label.fg` on the four `color.bg` surfaces and `popover.bg`, sit on the contract set, so a company that restyles those is checked. A pair whose background may be translucent lists the opaque surfaces it can sit on in `over`. A company pair with the same `fg` and `bg`, in any of its sets or modifiers, replaces Todae's and keeps its `over` unless it lists its own. A company's token build inherits these pairs, and its resolver may change a pair's minimum or add pairs. `ThemeProvider` overrides are measured only in development, against Todae's pairs and minimums (generated into `CONTRAST_PAIRS`), from the browser's computed colors; a `console.warn` names the pairs that fail with the provider's overrides but pass on the same element without them; the runtime APCA math in `overrideContrast.ts` is tested to match the build's. A pair that fails names the nearest lightness of its `fg` or its `bg` that passes, on the token that holds the literal value, in steps of 0.001, leaving out a lightness that would fail a pair that passes now; a literal in Todae's own files is named as one to override in the company resolver's entry of the same name, and a failure with the same advice as the one before it says "same as above".
- **The accent is neutral ink, not a hue.** Don't introduce a blue accent; a build test lets only `color.category` read the blue scale.
- **Tones.** Status tones are `info`, `success`, `warning`, `critical`. Category tones are numbered `category-1` to `category-8`, not named after hues, so a company can re-hue without renaming. Avatar takes neutral and category tones, not status tones. `categoryTone(key)` hashes a string to a tone; keep its pinned test values, since changing the hash changes every user's color.
- **Generated files are committed.** Run `pnpm tokens` after editing token files; `pnpm tokens:check` fails on drift.
- **The token build is `scripts/build-tokens.ts` plus `scripts/tokens/`.** `shared.ts` holds the token types, pointer helpers and CSS block helpers; `scope.ts` the `--scope` rules; `contrast.ts` the OKLCH and APCA math and the contrast checks. The modules import only `shared.ts`, never each other or `build-tokens.ts`, which re-exports every name it exported before, so its importers don't change. Imports between scripts end in `.ts`, since Node runs them with `--experimental-strip-types`; `tsconfig.scripts.json` rewrites them to `.js` for `dist/scripts`. *Why:* the file had grown past 2,000 lines of unrelated concerns.
- **Extensibility comes first.** Companies add sets, contexts, variants and densities in their own resolver and build them with `todae-tokens build`. New token features should work through that path, not by editing Todae's files. A company changes one of Todae's tokens by declaring it in a set or modifier named like the Todae entry that declares it; for a button variant, in the context named after the variant. The catalog's `entry` names that entry, with a `context` field for a button variant, and the build names it when a token is in the wrong one. A build error names the fix where it can: the token that reads a missing or out-of-order reference, the keys one context has and another lacks, the entry to list earlier. *Why:* a company author meets these rules first in an error message.
- **A scoped theme holds the whole graph.** `todae-tokens build --scope <selector>` writes Todae's tokens and the company's inside `@scope (<selector>)`, with each attribute rule also written on `:scope`, so a nested scope wins by scope proximity whatever order the files load in. A scoped element without `data-appearance` or `data-density` takes the context of the nearest element around it that has one (`@scope ([data-appearance="dark"]) to ([data-appearance])`), or the default. The scope element also sets the `--_todae-*` override inputs of the tokens it re-declares to `initial`, so an outer `ThemeProvider`'s overrides stop at it, while a provider on or inside it still applies. A sub-brand lists its main brand's token files in its own resolver; a build never layers on another company build. *Why:* a scope holding only the company's tokens would show an outer scope's value for every token it leaves alone, and Todae's tokens that read a scoped core change would not follow it, since Todae computes them only on `:root` and on elements that carry a modifier attribute.
- **`examples/fernway` is the second brand.** It themes Todae with tokens only, through the package's published entry points, and CI's Second-brand example job builds its tokens, typechecks it and bundles it. When a theming feature lands, show it there if a company would reach for it. *Why:* the token build tests run `buildCompanyTokens` on fixtures, but only a real app sees the published entry points, the generated files and the `ButtonVariants` augmentation together.
- **A nested provider keeps the enclosing one's value when it sets none.** A `ThemeProvider` with no `appearance` and a `DensityProvider` with no `density` take the enclosing provider's; only the outermost defaults, to `system` and `comfortable`. *Why:* a provider that only sets overrides shouldn't flip part of a page to the operating system's scheme or the default density.

## CSS

- **Todae's CSS sits in one cascade layer, `todae`.** `src/styles/layers.css` declares `todae.reset` (empty), `todae.base` (tokens and the modal scroll lock) and `todae.components`, and is imported first by every build entry. A company's token build adds `todae.theme` after them. *Why:* a company places Todae with one name, and its own CSS wins by layer order, not specificity.
- **Component styles are CSS Modules** in `@layer todae.components`. Components that style a single native element (Link, Table, Code and similar) use the `todae.components.native` sublayer, so container components such as Pagination beat them.
- **Take colors, spacing, radii and sizes from tokens** through their `--todae-*` custom properties rather than literals. Restyling goes through tokens first; a class works for layout.
- **Classes are camelCase**, and a part's main class is usually `.root`. Name a custom property a sheet sets for its own arithmetic `--_<name>` (`--_ring-room`), so it doesn't look like a token.
- **A component that passes a prop to its sheet through an inline custom property names it `--_<name>` too,** as `Grid.Root` sets `--_column-count` and `--_min-item-size`, and `DataList.Root` `--_min-item-size`. Only a token's custom property starts with `--todae-`.
- **Space a label or caption from its control with `Field.Group`,** a column that puts the label or caption `field.label.gap` above the control. Label carries no margin. Description and ErrorMessage keep their own top margin for use outside a group; inside one the group gives them the same distances. *Why:* Ben chose one wrapper that also covers captions, such as a `Text.Root` over a RadioGroup, which a Label margin can't reach.
- **Space layout with named gap steps, not values.** `Stack.Root` takes `gap="none" | "condensed" | "normal" | "spacious"`; each step but `none` is a contract token that reads a density token, so it follows the density. A gap that is not a step is the product's own CSS. `Grid.Root` still has one `grid.gap` and no steps. *Why:* Ben chose named steps over a free value so spacing stays on the density scale.
- **Style markdown's bare elements through `Prose.Root`.** Its sheet reaches `h1`–`h6`, `p`, `ul`, `ol`, `li` and `blockquote` through `@scope`, with any other element as the lower bound, so a demo, card or code block inside the prose keeps its own type. It zeroes each child's end margin and the first child's start margin and spaces the rest with `:nth-child(n + 2)`, which outweighs a child component's own margins. A list with a `role`, such as the lists of Stack, Breadcrumbs and Tree, keeps its own indent and item spacing, since markdown renderers leave lists without one. The docs build compiles CSS with Lightning CSS, because Next's default CSS Modules compiler leaves the class inside `@scope` unrenamed. Inline code, code blocks, links and tables are mapped onto their components in the product's markdown renderer, a recipe on the Prose page. *Why:* one export a company can restyle sets rendered text for docs and chat alike, and Todae still styles no bare element in `todae.base`.
- **Streaming belongs to `Message.Root`, not `Prose.Root`.** `streaming` sets `aria-busy` and `data-streaming` and draws nothing; a product shows a reply still coming with Loader's `dots`. Todae does no token smoothing in JS, and a message knows nothing about any agent SDK's message shape. *Why:* Ben chose this for the chat components, so Prose stays a plain text style that docs and chat share. He dropped the caret drawn from CSS after four review rounds, because selectors can't see text nodes, so no rule placed it right in all rendered markdown.
- **Use logical properties** (`inline`, `block`) for layout, and `:dir(rtl)` for anything that must flip.
- **Some CSS rules are tested.** Read `src/styles/tokenConsistency.test.ts` before writing a new sheet: it covers focus rings, disabled styles, tones, which tokens a sheet may read, and length literals: a `px`, `rem` or `em` length comes from a token, except `0`, `1em`, lengths in visually hidden text and lengths in a `forced-colors` block. `src/components/noScrollbarStyling.test.ts` bans scrollbar styling, and `src/styles/no-container-transforms.test.ts` bans a `transform` on an element that may contain a tooltip trigger.
- **Forced colors.** Where a state shows only through fill (pressed, selected, checked, current), add an `@media (forced-colors: active)` rule that maps it to system colors.
- **Use `!important` only for rules that must hold**, such as `VisuallyHidden.Root` and hidden tab panels.
- **Wrap hand-written selectors in `todae.base` in `:where()`,** so any class a company adds wins.

## Platform

- **Use the best native HTML and CSS features, with no JavaScript fallbacks and no support matrix.** The feature list is on the [Native platform](apps/docs/app/(en)/platform/page.mdx) page; add a feature there when a component starts to depend on it. The root README carries a dated table of the first browser versions that have those features, worked out from the page; recheck it when a component starts to depend on a newer feature. *Why:* Todae stays small and gets better as browsers do.
- **Overlays.** `Dialog` and `BottomSheet` render in place on a modal `<dialog>` (no portal), so they inherit the theme. `Popover`, `Menu` and `Tooltip` use `popover="manual"` with CSS anchor positioning. `Tooltip.Root` renders a `<span>`, so a trigger and its tip can sit inside a paragraph, such as a citation marker in a reply; a tip holds phrasing content only, and `Tooltip.Root` logs a development error for an element that would close a paragraph, such as a `<p>` or `<div>`. *Why:* an interactive tip stays mounted while closed, so a `<div>` in a server-rendered `<p>` made the HTML parser close the paragraph. Page scroll stops through `:root:has(dialog:modal)` in CSS, not a scroll-lock hook.
- **Escape and close requests go to the innermost layer first, through one selection.** `useEscapeKey` holds the page's one stack of layers. A key and a modal `<dialog>`'s `cancel` (Escape, the Android back gesture, `requestClose()`) ask each layer the same question with the element that has focus, and the innermost layer that takes it acts; a layer that isn't a popup, such as a Drilldown, yields to a popup beside it. Menu, Popover, Drilldown and a range Calendar with an anchor take close requests; Tooltip takes only the Escape key, so the back gesture passes a tip by. A component claims Escape by registering a layer, never by stopping the key's propagation, which can't reach the stack's document listener when React's root is the document itself (Next.js, Remix). Toast still stops propagation for its own Escape, a known gap to move onto the stack. The surface closes only when no layer takes the request, also when Chromium won't let the page cancel it. `closedby` follows the layers that take close requests registered inside the element, not whether one takes a request now, so an uncancelable request with only a hidden layer inside closes the element natively and the shell shows it again. *Why:* the back gesture reaches a modal with no key and Chromium cancels only some close requests, so the key and the gesture must answer alike, and a `closedby` read while rendering can't follow a tab switch.
- **Toast** holds text and buttons, no nested menus or dialogs. Its region follows Todae's modal stack into the front modal; a product's own modal `<dialog>` joins that stack through `useModalLayer`.
- **A timing only a hook reads**, such as a tooltip's show and hide delays or a step button's hold delay and repeat interval (`field.stepper.repeat-delay`, `field.stepper.repeat-interval`), is a contract token too. The hook or part reads it from the element's computed style and falls back to the token's default when it can't. *Why:* a theme tunes every timing in one place, CSS or not.
- **Motion** takes its durations and easings from contract tokens, respects `prefers-reduced-motion`, and only has to work in Chrome. A transition that opens a component reads its contract `motion.easing.enter` (the overlays share `overlay.motion.easing.*`), and one that closes it reads `motion.easing.exit` (set on the closed or exiting state's rule). Both alias the core `motion.easing.enter` and `motion.easing.exit`, which are raw curves. Don't add workarounds for Safari motion gaps.

## Accessibility

- **Follow the ARIA Authoring Practices pattern** for each interactive component, and keep that behavior in the component or a hook, not in a recipe.
- **What counts as a tab stop is answered in one place.** `src/overlay/tabbables.ts` owns it: `firstTabbable` and `getTabbables` for what Todae treats as tab stops in a subtree now (the candidates Todae recognizes, in document order, minus disabled, hidden, inert and `aria-hidden` content, and minus every radio of a named group but its one stop), `getTabOrder` for what content holds whatever styles hide now (Toolbar's arrow-key items, and a ScrollArea an ancestor hides), `getCandidates` for every kind of control content holds (Tooltip's content rule), `isReachable` for whether focus can move to an element at all (roving items carry `tabindex="-1"`), and `canFocusNow` for whether a script can focus it now, outside the tab order. Code that asks whether Tab stops on an element, or where Tab goes next, asks it; finding a component's own part by its marker, such as a chip's remove button, is a different question. Don't write a new focusable selector or visibility check; extend this module. `hidden` and `aria-hidden="true"` subtrees strictly inside the queried root count as removed content on purpose; one on the root itself does not, so a Toolbar that carries `aria-hidden` keeps its arrow keys. Content behind an open modal is not ruled out, since its inertness is a passing page state and `focus()` on it is a no-op. Three checks stay apart because they answer other questions: Field's `FOCUSABLE_FIELD_CONTROL_SELECTOR` (which control a press on the field's shell focuses; like `tabbables.ts`, it leaves out `[data-todae-value-input]`), and the `checkVisibility` calls in OptionList, useModalDialog and Drilldown (whether the container is rendered at all). *Why:* three hand-written selectors had drifted, so a control one counted another skipped.
- **A named radio group is one tab stop, chosen as Chromium's forward Tab chooses it.** `tabbables.ts` lists only the group's checked radio, or with none checked, the root's first that can take focus. Whether a radio claims its group follows the browser: a negative tabindex, `disabled`, `hidden`, inert or a hidden style rule it out, and `aria-hidden` does not. So a checked radio of the group outside the root takes the group out of the root, unless the root is in an open modal dialog that radio is not in, and a radio under `aria-hidden` in the root that claims its group takes the group with it, since the root lists no `aria-hidden` content. Shift+Tab into a group with none checked lands on its last radio instead, which the list does not show. Firefox and Safari may decide the claim differently; only Chromium is checked. *Why:* default initial focus must land where Tab would, and a radio group is one stop.
- **Scroll containers that hold controls keep focus rings whole.** `ScrollArea`, `BottomSheet.Body`, `Drawer.Body`, `Popover` and the `Dialog` and `Drawer` panel run `revealRing` from `src/components/revealRing.ts` when focus lands (Dialog and Drawer from the `<dialog>`'s composed `onFocus`, with the panel as the area), and set `scroll-padding` to a ring's width plus offset. A new part that scrolls controls with outset rings does the same. A part that draws a control's ring on a child or sibling of the focused element, such as a Checkbox indicator, the ColorPicker thumb or a Tree row, marks that element `data-todae-focus-ring=""` (a transparent outline that only gives the room counts, as on Field.OneTimeCode's row of boxes); `tokenConsistency.test.ts` lists those rules. Code that moves focus where it must not scroll calls `focusWithoutScroll(el)`, not `el.focus({ preventScroll: true })`, so `revealRing` leaves it alone too. *Why:* the browser scrolls a focused control into view by its own box, so a ring drawn on another element, such as a Field shell, can stay cut at the edge.
- **A conversation is a labelled region, not a log.** `Conversation.Viewport` is a `<section>` named by the `conversation` string, and puts no live region around the messages. Conversation announces through `useAnnouncer` when an `article` in its content takes `aria-busy="true"` and when that clears, and says nothing at the end when the message holds a `role="alert"`. Following the end of a growing conversation stays inside Conversation, with no exported `useStickToBottom`. Messages don't take `content-visibility: auto`: its paint containment would clip the focus rings of action buttons at a message's edge. *Why:* Ben chose the more accessible option when planning it. `role="log"` is a live region, so it would read every streamed word, and with `aria-live="off"` its role means nothing.
- **A message's time is a part; its actions are a recipe.** `Message.Time` renders a `<time>` from a `Temporal.ZonedDateTime`, so the product picks the time zone and the text doesn't depend on the runtime's own zone; it writes Gregorian dates, as `formatDate` does, and `dateTime` as the UTC instant; it writes no relative time, since that needs a clock, and children replace its text. `Message.Actions reveal="hover"` hides the row with `opacity` only while the message is neither hovered nor holds focus, and only under `(hover: hover)`, so the buttons stay in the tab order and show on focus. Copy, regenerate, rating and edit are the [Message actions](apps/docs/app/(en)/recipes/message-actions/page.mdx) recipe over `Button`, `Toolbar`, `ToggleGroup` and `useClipboard`, with no `Message.Copy` or feedback part. *Why:* what each action does is the product's data and flow, and the parts it needs already exist.
- **Suggested prompts and a reply's versions are a recipe.** Starter and follow-up prompts are `Button.Root`s in a labelled list above the Composer that fill the field and move focus to it; the "2 of 3" switcher is two icon-only Buttons described by a count at the start of the reply's Toolbar, with `aria-disabled` at the ends as Pagination's steps have, so the focused one keeps focus (`Button.Root` draws `aria-disabled="true"` as disabled, and ignores its clicks, so `onClick` doesn't run and a toggle doesn't flip), and the product keeps versions as siblings under the message they answer. Both are the [Suggestions](apps/docs/app/(en)/recipes/suggestions/page.mdx) recipe, built over Button rather than Chip, with no `Suggestions.*` or `Message.Branch` part. *Why:* which prompts to offer and how a conversation branches are the product's data, and a suggestion is an action, which is a button, not a value a Chip holds.
- **A model's reasoning is a recipe over `Disclosure`.** The [Reasoning](apps/docs/app/(en)/recipes/reasoning/page.mdx) recipe sets `open` on `Disclosure.Root` from whether the reasoning is still arriving, so the block opens while it streams and closes when the answer starts, and React leaves the person's own toggles alone between those changes. Its summary says the state in words and hides Loader's dots. There is no `Reasoning` or `Message.Reasoning` part. *Why:* `<details>` already gives the keyboard and the expanded state, and when reasoning starts and ends is the product's stream state.
- **A disclosure closed by code hands focus to its summary.** When `open` goes away while the disclosure's content holds focus (looking into the shadow root that holds it), the main entry's `Disclosure.Summary` takes focus without scrolling, from a `MutationObserver` on `open`. The observer's microtask runs before the browser drops focus to the page, so focus goes straight from the content to the summary; that was checked by hand on a plain `details` in the Chromium, Firefox and WebKit builds of Playwright 1.56, other engines are unchecked, and the browser tests run the component in Chromium only. The server entry's summary has no observer. *Why:* a block that closes itself, such as the Reasoning recipe's, would otherwise drop a focused link's focus to the page, and moving focus is behavior a recipe may not carry.
- **Citations are a recipe.** A citation is a bracketed number in a `Link.Root` to the reply's sources list, at the text's own size, with an interactive `Tooltip.Root` preview, one `useTooltip` per marker. The [Citations](apps/docs/app/(en)/recipes/citations/page.mdx) recipe shows it, with no `Citation` part. The marker sits in a sentence, so WCAG 2.2 SC 2.5.8's inline exception covers its target size; a marker outside a sentence isn't covered by that exception and needs a 24 by 24 CSS pixel target or the spacing the criterion allows. *Why:* the sources are the product's data, and the link and preview parts already exist; a number at text size keeps a cited sentence's flow.
- **A tool call is a recipe.** The [Tool call](apps/docs/app/(en)/recipes/tool-call/page.mdx) recipe draws a call as a `Disclosure.Root` whose summary holds the tool's name and a status `Badge`, with its input and output in a `DataList` of `CodeBlock`s and Approve and Deny `Button`s after it while it waits. The message's `streaming` follows the agent's turn: on while it writes or a call runs, off while any call waits, so the buttons never sit in a busy message. Todae has no `ToolCall` part and no status-to-tone map, since the statuses, their words and when a call runs are the agent's, and the parts already carry the keyboard, expanded state and tones. `useFocusHandoff` on the Approve and Deny group moves focus to the summary when the group unmounts holding focus, so a decision made by a click or from another device keeps focus in the reply. *Why:* each agent SDK shapes calls differently, and Todae knows nothing about any SDK's message shape.
- **Focus held by an element that unmounts goes on through `useFocusHandoff`.** It returns a ref callback whose cleanup, which React runs before it takes the element out, checks whether focus is inside; a microtask after the commit then focuses `to` if the element is gone, focus is lost (nothing, the body, or a disconnected element) and `to` is in the page. A capture-phase click listener on the element first focuses the innermost clicked control (from `getCandidates`), since Safari and Firefox on macOS don't focus a clicked button; it skips an untrusted click with `detail` 0, so a script's `click()` never moves focus, while an assistive tech's click, trusted but with `detail` 0 and unfocused in WebKit, still does. Attachment keeps its own hand-off, since it picks a neighbour's remove button rather than one fixed target, and tries several targets in turn, but shares `activeIn` and `focusLost` from `src/components/activeElement.ts`, where Disclosure's `activeIn` comes from too. It returns the ref callback itself, not a result object, since a ref is all it gives. *Why:* buttons that a stream or another device removes would drop focus to the page, and a recipe can't catch that without hard focus code of its own.
- **An attachment hands focus on when it is removed.** When an `Attachment.Root` that holds focus unmounts, its layout cleanup (which runs while the element is still in the page) notes its place among its parent's children, or among the `li`s of its list when it is an `li`'s only child, and a microtask queued then, which runs once the commit is done, checks the page: if the root is gone, its list is still there and nothing else has focus (looking into shadow roots), focus goes to the reachable remove button of the attachment now in that place, else the one before. Focus then moves outside React's commit, so `onFocus` handlers such as `revealRing`'s run. A StrictMode check or a hidden Suspense tree leaves the root in the page, so nothing moves. `Attachment.Remove` focuses itself before calling the product's `onClick`, as ChipList's remove does, since Safari does not focus a clicked button; this is an exception to running the consumer's handler first. It looks no further than that list, so focus stays among the same files; after the last one, the product places focus. `Attachment.Remove` is named from `Attachment.Name`'s text through the `removeAttachment` string, so the name stays a string. *Why:* removing a focused element drops focus to the page, and only Todae's parts know where the next file is.
- **A composer sends on Enter the way a form does.** `Composer.Root` is a `form`, and Enter in one of its textareas calls `requestSubmit` with the form's first submit button, and does nothing while that button is disabled, as implicit submission does from a text input. It finds the textarea from the key event's target, not from a component type. Shift+Enter, Enter with another modifier, and Enter that ends an IME composition (`isComposing`, or `keyCode` 229, which Safari sends after `compositionend`) are left to the textarea. A held Enter in a textarea sends at most once. The root's `onSubmit` and its busy gate act only on the form's own submits, since React bubbles a portaled form's submit through it. While `busy`, the root cancels every submit event of its form, so a text input's own implicit submission or a product's button sends nothing either. `Composer.Submit` is one button that is Send or, while `busy`, Stop, so a focused button keeps focus as it swaps, while it stays enabled. On Submit, a second click of a double click (`detail` above 1) and a repeated Enter do nothing, since they land after the swap; a deliberate second press within the double-click interval counts as part of the double click. Stop cancels its click's default action: `onStop` clears `busy` before the browser acts on the click, and by then the button is a submit button again. Its name comes from `useButtonName`, like the close parts. Chromium takes focus off a button the moment it turns disabled, during React's commit, so Submit listens for its own `focusout` and, when the button was enabled at the last commit and is disabled now, in a microtask focuses the form's first enabled textarea if nothing else has focus. The composer's box, its rows and its counter are Field's: buttons go in a `Field.Row`, and there are no `Composer.Actions` or `Composer.Attachments` parts. *Why:* `Field.Row` already draws a composer's rows, so those parts would be wrappers with nothing of their own; and Korean and Japanese typing commits words with Enter.
- **Mentions and slash commands keep the native textarea.** `useMentions` finds the trigger word at the caret (the nearest trigger character before it that may start a word there: at the start of the text or after whitespace, or with `position: 'start'` only with nothing but whitespace before it; the word runs to the next whitespace), keeps the textarea a textbox with `aria-autocomplete`, `aria-haspopup`, `aria-controls` and `aria-activedescendant` (no `aria-expanded`, which a `textarea` may not take, so the count is announced through `useAnnouncer` instead), and leaves keys alone during an IME composition. A pick replaces the word with `document.execCommand('insertText')`, so it lands on the textarea's own undo stack; where `execCommand` is missing, throws or returns false, the hook sets the text itself. A read-only or disabled textarea opens no list. Committed tokens are ranges carried through each edit by the changed span, placed at the caret where the edit came from typing, and checked against their text, not found again by pattern. The text and its tokens are one draft: `value` holds both and `onValueChange` hands back both in one call, worked out in the edit's event from the rendered draft, so a product cannot store one without the other, and an edit it rejects or commits later moves nothing on its own. While a pick waits for the product to commit its text, no list opens, since the caret belongs to neither text; the wait ends when the text arrives, when the product puts in another text, or when the user edits, moves the caret with an arrow, Home, End or Page key, or presses the primary button on the textarea. Ben chose one draft over separate `tokens` and `onTokensChange` props, which let a product's text and tokens drift apart when it stored one later than the other. A token in `value` that does not hold its text is left out. The hook remembers the tokens each recent text last had, so undo and redo restore them. `Field.Textarea`'s `highlights` draws them on an `aria-hidden` sibling after the textarea, placed over the textarea's box with anchor positioning (and not drawn without it), behind its visible text (above it in forced colors, where tokens draw only an outline); the layer copies the textarea's computed type, padding and own `lang`, and its scroll, and token spans draw only a background, so they move no text. The caret word's span carries the popover's anchor. *Why:* Ben kept the native textarea, not contenteditable, so IME, undo, spellcheck and screen readers keep the browser's behavior.
- **A drilldown goes back before it closes.** In `Drilldown`, Escape and a close request go back one view while the stack is deeper than one (`escape="back"`), and close the overlay only at the first view; a Drilldown that isn't rendered passes them on. Focus returns to the trigger that pushed the view, and only to the view the trigger sits in; only the next change of the stack can be a trigger's push, so a push the product turns down leaves no trigger behind, and a change that shows another view first ends it. With no trigger that can take focus, whatever the change's direction, the view takes its `initialFocusRef` if that can take focus, else its first tab stop. Focus moves only when it was in the views, on Back, on the surface or nowhere. A view gets back its scroll offset and trigger only if it showed when a change covered it. An uncontrolled stack starts over with reason `reset` once its surface finishes closing, on every surface, through `useSurfaceClosed`: the surface signals as its exit ends (`useOverlayPresence`'s `onExited`, or a Popover closing) while its content is still mounted, never from an unmount, which can cut an exit short, so a Drilldown or surface the product unmounts or hides first hears nothing. Views slide by transitions on `inset-inline-start`, so the slide flips with the text and a view a later change overtakes goes on from where it is, and each view settles when its own transitions finish. The viewport's height animation starts from the height on screen, read without changing the DOM, holds the new view's height until every view settles, and stops for a pop that brings back an offset the height on screen can't reach, which needs the full height at once. *Why:* Ben approved the design (2026-10-21) so a stack of views behaves like the platform's navigation stacks and the APG rule that Escape closes the innermost layer first.
- **An alert dialog is `Dialog.Root role="alertdialog"`, not a component of its own.** The role turns off backdrop dismiss by default (Escape stays on, as Cancel) and sends initial focus to the first tabbable close part, found by its `data-todae-close` marker in `initialFocusTarget`, before the first tabbable; `initialFocusRef` still wins. Without `Dialog.Description` or `aria-describedby` it logs a development-only error. Drawer and BottomSheet take no `role`. A promise-based `confirm()` and what counts as destructive are the product's. *Why:* it is the same native `<dialog>` with another role, and the APG alert dialog pattern asks for a description and focus on the least destructive action.
- **A step list says each step's status in words.** `Steps.Root` is an `ol`, and each `Steps.Item` hides its marker and starts with a visually hidden status word from the `stepDone`, `stepCurrent`, `stepPending` and `stepError` strings, which a non-empty `statusLabel` replaces. The running step takes `aria-current="step"`, and its marker is a `Loader.Root`, not an indicator of its own. *Why:* Ben chose a step list component for an agent's plan (2026-10-14), and a status drawn only as a glyph or a color is lost to a screen reader.
- **Site and app navigation is `Nav`, links in lists, not a `Tree`.** Each link and branch toggle is its own Tab stop, with no arrow keys, and a `Nav.Branch` is a native `<details>`. The docs sidebar is built from it. *Why:* Ben chose (2026-10-14) to ship the docs sidebar as a component, since products built on Todae need one too; a `role="tree"` is a widget whose arrow keys and selection don't fit a list of pages.
- **A page's "On this page" list is `Contents`, with links given by hand.** `Contents.Link`s register the fragment they point at, and `Contents.Root` marks the last section whose heading has passed its line with `aria-current="location"`. The line is where a fragment link scrolls the heading to (the scroller's `scroll-padding-block-start` plus the heading's `scroll-margin-block-start`), so the marker and a click agree. It follows the headings with one `IntersectionObserver` per line, whose box reaches far above the scroller, so a jump of any length crosses it. The scroller is the nearest ancestor that actually overflows, since `overflow-x: hidden` alone computes `overflow-y` to `auto`. A click, or a hash that names a section the page shows (on mount or on a hash change, so a restored scroll position isn't overridden), picks a section of the page (a hash change that names the pick keeps it, so a click holds through a smooth scroll; a pick of a section the page lacks lapses at once), which holds until a wheel, touch or scroll key that no field takes and no widget stops or cancels, until it has been in view and leaves, or until the hash names something else, so a short last section can be current. A `MutationObserver` starts following again when a heading mounts after its link, is replaced or is renamed, and a `ResizeObserver` on the scroller and the first heading's parent measures the lines again. Folding the list on a phone is the product's, with a `Disclosure`. *Why:* Ben chose (2026-10-22) hand-given links like Nav, so the list can render on the server and say what the product chooses, and `aria-current="location"`, so the current section is not shown by color alone.
- **Keys that belong to an IME composition are left to the control.** In the package, key handlers on an editable element (an input, a textarea or a contenteditable) return early on `isImeKeyEvent(event, commitKeys)` from `src/components/ime.ts`, which takes a React or a DOM key event. It checks `isComposing` and `key === 'Process'` for every key, and `keyCode` 229 only for the keys that commit in that control: Enter by default, a chip input's commit keys, and Enter and Tab in `useMentions`. That covers the one case `isComposing` misses: Safari sends the Enter that ends a composition after `compositionend`, with `isComposing` false and `keyCode` 229. Arrows, Escape and Backspace never check 229. The helper is not exported. Document-level hotkeys (`useHotkey`, the Toast region's key) check only `isComposing`: they already skip keys that would type into an editable target, where a composition happens. Roving widgets such as OptionList, Menu and Tree own focus on an element that takes no text, so they do not need it. *Why:* Korean and Japanese typing commits words with Enter, and Safari marks the Enter that ends a composition only with `keyCode` 229.
- **A sortable column is `Table.HeaderCell sort` plus `Table.SortButton`; selected rows are `useSelection` plus `Checkbox.Root`.** `sort` puts `aria-sort` on the sorted column alone, as the ARIA Authoring Practices sortable table does, and `'none'` marks a sortable column through `data-sort` only. `Table.SortButton` is a real `<button>` that draws the `sort` glyph from the header cell's `data-sort` (so it doesn't depend on a component type), and announces through `useAnnouncer` when that cell's sort next changes after the button's own click, unless the user presses or types something else first (a lone modifier key doesn't count), and not after a click the product prevented. The wait ends there so a click that sorted nothing can't claim a change made later by other means once the user has moved on; until then it can. It lives in `Table.client.tsx`, since it needs hooks, and not in the server `Table`. `Table.Row selected` only styles the row (`data-selected`); it sets no `aria-selected`, which doesn't apply to a row of a table that is not a grid, so the row's checkbox carries the state, and a header checkbox shows a partial selection with `Checkbox.Root indeterminate` and the `indeterminate` glyph. A data grid stays out of scope. *Why:* a table that can sort and select is still a table, and the native button and checkbox already carry the semantics that a grid role would have to rebuild.
- **Toolbar keeps its no-tabindex design:** Tab is steered to the edge of a run instead of managed `tabindex`. This was chosen knowing its limits (an ancestor that cancels Tab after the hop, an item that stops Tab propagating, Safari skipping buttons by default); don't switch back.
- **axe runs over the docs demos in a real browser**, with color contrast off, since contrast is APCA in the token build. `site.browser.test.tsx` runs it over the English site chrome, and the screenshot tests over the Korean pages in light and dark at desktop and phone width.

CI's test of the real changelog catches a changelog it refuses; on the live site, such a changelog fails `get_changes` alone. *Why:* an agent upgrading a project needs the changes after the version it has, which the installed package can't hold and the npm tarball doesn't ship.

It also needs When copy there. *Why:* the docs MCP lists only what has a meta, so an export without one is invisible to agents.

Change them together, and check a change in a new Next.js and Vite app. *Why:* a fresh-install check on 2026-10-21 found npm refusing the install next to TypeScript 5, the quick start failing in a Server Component, and the reset in a Next.js app made without Tailwind CSS stripping Todae's styles, none of which the docs said.

It does not describe wrong-typed input, round trips ("X reads it back"), "does what Y does" or a parser's grammar; the docs page carries those details.

### Code blocks and live examples

Code on a docs page is copied into products, so write it in the package's own style and wiring. `apps/docs/lib/codeBlocks.test.ts` checks three of these rules mechanically: that each fence names one of the languages below, that no line starts with a tab, and that `...` is not used as a placeholder. It skips the pages in its `PENDING` set, which don't follow this section yet.

- **Every fence names its language:** `tsx` for code with JSX or a hook call, `ts` for other TypeScript, `css`, `json` or `sh`.
- **Indent with two spaces**, not tabs. In TypeScript, use single quotes for strings, double quotes for JSX attributes, semicolons, and trailing commas in lists that span lines, as `packages/design-system` does.
- **Mark left-out content with `…`**, such as `<Dialog.Body>…</Dialog.Body>`. Don't use `...`, which reads as a spread.
- **Declare each id that a snippet names in `htmlFor` or an `aria-*` attribute,** such as `const id = useId();` or `const cb = useCombobox({ … });`, above the JSX. App state such as `value` and `setValue` can be assumed.
- **Show real wiring.** A `Label.Root` sits with its control in a `Field.Group` and points at it with an id from `useId()` or a hook's `ids`, not a literal. Every control has an accessible name. Links are `Link.Root`, and a router's link goes in through its `render` prop.
- **Icons are real icons with their import,** from `lucide-react`, not placeholder names such as `YourIcon`. Inside a slot such as `Button.Icon`, put the icon element on its own line.
- **Imports.** A block with an `export function` imports everything it uses: Todae from `'@tounsoo/todae'`, or from a server entry such as `'@tounsoo/todae/code'` when a Server Component should render it.
- **The site renders code with Todae's own parts.** MDX maps fenced blocks to `CodeBlock.Root` (inside a `ScrollArea.Root`, through `DocsPre`) and inline code to `Code.Root`. The site doesn't override the code block's tokens, padding, type or colors.
- **The site shows Todae as it ships.** `apps/docs` sets no Todae token, and its pages load no font of their own (the link-preview images draw with their own fonts); the site's own chrome reads Todae's tokens as they are. Themes appear only inside the Playground, through `ThemeProvider` overrides. *Why:* people judge Todae's base theme by the site itself.

## Releases

- **Changesets versions and publishes `@tounsoo/todae`.** A pull request that changes what the package ships (its code, types, CSS, tokens, schema or CLI) adds a changeset with `pnpm changeset`. CI fails a pull request that changes the package without adding a changeset; tests, fixtures, snapshots, `CHANGELOG.md` (which the package doesn't ship) and dotfiles don't count, and a change that ships nothing gets `pnpm changeset --empty`. *Why:* the changelog is built from these files, so a change without one is missing from the release notes.
- **A changeset is short.** Its first line says what changed for people who use Todae, in one sentence that names the component, hook or token. It leaves out why, how and edge cases, which belong in the pull request and the docs. A breaking change adds one bullet per break, each saying what to change in your code, such as "`getTriggerProps().ref` is a callback ref; read `cb.triggerRef` for the element." `.changeset/config.json` prints each entry as that line and a link to its pull request, or to its commit when there is none, with no author or thanks. *Why:* people read the changelog to find what to change when they upgrade, and `get_changes` on the MCP hands the same text to their agent.
- **Relative imports in shipped `src` files name the emitted file,** such as `./cx.js` for `cx.ts`. `tsconfig.build.json`, which covers the files that ship (not tests or `*.meta.ts`), resolves modules as `nodenext`, so `pnpm typecheck` fails on a missing extension there. *Why:* the published `.d.ts` files keep the source's import paths, and TypeScript projects that resolve modules as `node16` or `nodenext` can't follow a path without an extension.
- **Top-level code in shipped `src` files has no side effects.** A top-level value built by a call or `new` is marked `/* @__PURE__ */`, and one that reads a property, such as `styles.panel`, or spreads is built inside a function called that way. `package.json` marks only CSS files as having side effects, and `src/entries.test.ts` fails when bundling the main entry with nothing imported leaves any code. *Why:* bundlers drop an unused component only when nothing at its top level could have a side effect, and esbuild treats calls, property reads and spreads as possible ones.
- **Bumps before 1.0:** a breaking change is `minor` and everything else is `patch`. *Why:* in semver, a `0.x` minor is the breaking release, and a `major` would publish 1.0.
- **Merging to `main` doesn't publish.** `.github/workflows/release.yml` turns changesets on `main` into a "Version Packages" pull request with the next version and changelog. Merging that pull request publishes to npm through trusted publishing, so the workflow holds no npm token. npm only takes a trusted publisher for a package that exists, so the first version is published by hand. `apps/docs` is private and never published or versioned.

## Recording a decision

When the project settles a question about concepts, API shape, tokens, CSS or platform use, add it to the section it belongs to here: the rule, then why. Remove a rule that a later decision replaces instead of keeping both.
