# Todae architecture and decisions

Read this before adding a component, hook, recipe, token or docs page. It records what Todae has decided and why, so new work lands the same way.

These are rules for new and changed code. Some older code predates a rule and does not follow it yet. Don't copy an exception into new code; bring old code in line when you are already changing it.

The docs site explains the same ideas to people who use Todae: [Composition](apps/docs/app/(en)/composition/page.mdx), [Build on Todae](apps/docs/app/(en)/guides/build-on-todae/page.mdx), [CSS layers](apps/docs/app/(en)/guides/css-layers/page.mdx), [Tokens](apps/docs/app/(en)/tokens/page.mdx) and [Native platform](apps/docs/app/(en)/platform/page.mdx). This file is for the people and agents who change Todae. Paths such as `src/…`, `tokens/…` and `vite.config.ts` are relative to `packages/design-system`. When a decision here changes, update this file in the same pull request.

## What Todae is

Todae is a low-level base that companies build their own design systems on. A company adds a token package, a few TypeScript declarations and thin wrappers around Todae's parts, without forking Todae.

So choices favor what a company can extend or restyle without copying Todae's code: tokens over hard-coded values, parts over monoliths, native elements over JavaScript reimplementations, and no product knowledge in the package.

## Kinds of exports

What Todae ships is a component, a hook or a recipe. Providers, their hooks, and helpers such as `composeRefs` and `categoryTone` sit outside the split.

- **Component.** Todae can fix its markup, props and behavior without knowing the product's data, fetching, routing, business rules or screen layout. It may own behavior (Menu, Tabs) or only styles from tokens (Stack, Text).
- **Hook.** Behavior with no markup, exported when a recipe or a product's own markup needs it, such as `useRovingFocus` and `useCombobox`.
- **Recipe.** Copyable code in the docs that puts exports together around product data or flow, such as Combobox and File upload. It is not a package export.

Rules:

- **Anything that carries Todae tokens or styles is an exported component**, even when the browser does all the behavior. Link, Table, Separator and VisuallyHidden, for example, are `*.Root` components for this reason. Don't style bare elements in `todae.base`. *Why:* every Todae look should come from an export a company can find, wrap and restyle.
- **A component owns behavior and accessibility, and a recipe owns layout.** Keyboard handling, focus, ARIA wiring, state, positioning, measurement, and tokens go in a component or a hook. A recipe owns layout, opinionated composition, and feature bundles, built from those primitives, so a company can copy it and restyle it without breaking accessibility. If copied recipe code would still carry hard behavior, move that behavior into Todae. Layout CSS with no script, no focus movement, and no measurement may sit in a recipe, such as the avatar stack's overlap.
- **Composer is a recipe, and the mention pieces stay components.** Ben's reason: "Composer had too many features baked in for the concept of this DS." `defineMentionSource`, `useMentions`, the suggestion list, the peek on the stock Popover, `Mention.Root`, `MentionText`, and the `mention.*` tokens stay components. The frame, the toolbar, the attachments, and submit become a recipe built from `Field.Textarea`, `Button`, and the mention pieces. This reverses option 2. That option made Composer a component made of parts. The decision removes the published `Composer` export in 0.6.0. See [Composition](apps/docs/app/(en)/composition/page.mdx).
- **A container that gives context or keyboard handling to whatever children it holds is a component** (Fieldset shares `disabled` and `invalid`; Toolbar gives roving focus). **A composition that wires specific exports to each other is a recipe** (Combobox connects a Field to an OptionList).
- **Don't ship a wrapper with no behavior, styles or tokens of its own.** If the arrangement is worth showing, write a recipe.
- **Don't add a headless hook that only mirrors a component.** `useTabs` and `useMenu` were dropped because the thin native parts plus `useRovingFocus` cover custom markup. Tree's keys are likewise a `tree` mode of `useRovingFocus`, not a `useTree` hook.
- **A look that only redraws an existing component is a variant of it, not a new component.** The typing indicator is `Loader.Root variant="dots"`, not a `TypingIndicator.Root`: it is the same native `<progress>`, with the same role, name and reduced-motion rule. *Why:* Ben chose it when planning the chat components, so a chat UI adds no component that would duplicate Loader's semantics. Ben later renamed Spinner to Loader (2026-10-14), so the spinner is the default `variant="spinner"` beside `dots`, and a component's name says what it is for, not how it is drawn.
- **Body text draws at `text.font.size`, and each heading draws at `text.h1.font.size` through `text.h6.font.size`.** Body refs `font.size.3` and the sheet reads `--todae-text-font-size` on `.root`. The element from `as` selects `text.hN.font.size`. Those tokens ref `font.size.6`, `font.size.5`, `font.size.4`, `text.font.size`, `text.font.size` and `font.size.2`. h4 and h5 follow the body token and can be overridden on their own. There is no `size` prop, no scale class, and no `text.size.*` ladder. `.label` stays on `text.label.font.size` and wins on a heading. A product sets the variable on the element or an ancestor with no `[data-appearance]` or `[data-density]` element and no scoped theme root between them, or overrides the token in the theme. *Why:* a theme needs to change one heading level the way it changes `avatar.size`, without a size prop.
- **A type role is a `Text.Root` variant, not a component.** `variant="label"` is the role for eyebrows, kickers and metadata. It reads `text.label.*` for its family, size, weight, leading, letter spacing, case and color, and sets `font-family`, from `text.font.family` by default, while body text and headings leave it to the product, so a company can make labels mono without CSS. A given `tone` or `weight` wins: the default color and weight sit on `.root` and `.heading`, before the role and the tone and weight classes, and a test checks that order. *Why:* a portfolio built on Todae (2026-10-22) needed mono, capital, tracked eyebrows, which a company should get from tokens, and Text already owns type on the token scale.
- **Cut text is `Text.Root lines`, not a component.** `lines` clamps with `-webkit-line-clamp`, and a word longer than the line breaks so it ends in the ellipsis too. When the text is cut, the main entry's `Text.Root` shows the whole text in a tooltip on hover and on keyboard focus (`:focus-visible`) of the text or of the nearest tab stop or `useRovingFocus` item around it, such as a link, a row or a menu item; that element shows the tip of the first cut text it holds. An `aria-activedescendant` host, such as a listbox, shows none, since its active item moves without focus. Only a focus change or a pointer entering opens the tip. It is `aria-hidden` and adds no `aria-describedby`, since clamping changes only painting and screen readers read the whole text, but it takes the first Escape, as a visible tip must be dismissable (WCAG 1.4.13). `@tounsoo/todae/text` clamps with no tooltip. The client `Text.Root` renders the server one in the same place with or without the tooltip, so a change of `lines` never remounts the text, and a Text without `lines` runs no tooltip hooks. Focus and hover reach the tip through `useTooltipInternal`, so `useTooltip`'s API is unchanged. Middle truncation, such as of a path, is out of scope. *Why:* names and titles in tables, cards and navigation are cut everywhere, and a keyboard user must be able to see what a pointer user sees.
- **A cut label or cut text is measured when the person reaches it, not kept up to date.** Button's truncated-label tip and a clamped `Text.Root`'s tip read layout only when the pointer enters the element, or keyboard focus reaches it, or for Text the nearest holder around it, such as a link, a row or a roving item; a label or text is cut or not only to someone looking at it. A cut one turns its tip on and takes the hold that found it once the tip has mounted, and one found to fit turns it off; nothing watches the element between. So a page of Buttons and clamped Texts builds no observer and reads no layout, and neither mounts a tip until one is needed: a Button's tooltip engine lives in its tip, which mounts when a label is found cut or a named icon-only Button has been reached, and an icon-only one keeps it from then on, also one reached before it turned icon-only. A Button's tip and a clamped Text's tip repeat the element's own name, so both are `aria-hidden` and describe nothing. Every Button starts the page's watch for presses when it mounts, a Button with no tip included, so a focus a script moves after a press, as a dialog does on open, opens no tip on the first reach either. A Button's tip adds its anchor name to the button from code while it is mounted, as a Coachmark or popover anchored by ref does, and takes it off when it unmounts, so the button's own style never changes for a tip, a Button nothing has reached has no style of its own, and the names the others added stay. Focus for every clamped Text in a document is heard by one capture `focusin` listener, which measures the texts a focused holder holds in document order and shows the first cut one's tip; a click or a menu opened by one moves focus without `:focus-visible`, and the pointer has the hover tip. Browsers ring any focus on an editable element (`:read-write`), such as a `contentEditable` Text, so there a press since the last key, read as every tooltip reads it, opens no tip either; a key held with Ctrl, Meta or Alt doesn't count as that key. A tip that is on follows its text as Text renders again and goes once it fits, but a change no render made, such as a container resizing, shows at the next reach. `data-todae-cut` marks a clamped text while its tip is on. Button reads its content for icon-only detection after each commit, and only when a child is something other than a string, a number or a `Button.Icon`, or `render` draws it; a child that swaps an icon for text from its own state is read at the Button's next commit. *Why:* the 2026-11-06 performance audit found one re-render of a parent of 200 Buttons rebuilt 200 ResizeObservers and every clamped Text read layout on each render, because JSX children are a new object every render; components are used many to a page, so per-render work multiplies. The Bench record of the same day then showed 1,000 Buttons still kept 2,000 observers, one of each kind per Button, and 1,000 clamped Texts the same. Moving them onto shared observers still left about 540 bytes of bookkeeping per Button, a slower unmount and about 1.3 kB more code, for a watch that only a tip on hover or focus needs, so both now measure on reach. The audit of 2026-11-10 then found each Button still ran the whole tooltip engine with no tip to show, about 9.5 kB of heap per Button in the 0.10.1 Bench record, and that the tip read the name twice to a screen reader.
- **A part that repeats shares its page-wide watching with every other copy.** Observers and page-wide listeners go through one shared registry, never one per copy: `src/internal/sharedMutations.ts` and `src/internal/sharedObservers.ts` for mutations and sizes (a todae-named button's spoken text, a Disclosure's `open`, an OptionList's options, a scroll area's Tab stop, a chip input's rows and a highlighted textarea's size), `src/internal/rootListeners.ts` for capture listeners on a document or shadow root (every control's form `reset`, and a NumberInput's or typed input's `submit` hold, in the order they mounted, with `'stop'` for `stopImmediatePropagation`), and `src/internal/tabKey.ts` for the Tab press every Toolbar reads at the window. The label watch of `Field.NumberInput` keeps one observer per document and finds the inputs a record is about by walking up from its target. Layout a copy reads after a commit or an observer report goes through `src/internal/layoutBatch.ts`, every read before any write. *Why:* the 2026-11-10 audit and the 0.10.1 Bench record found 1,000 number inputs built 2,001 MutationObservers and added 2,000 document listeners, 1,000 toolbars added 1,000 window listeners, a label observer did 100,000 `contains` checks for 100 inputs and 1,000 unrelated appends, and 100 highlighted textareas recalculated styles 4,102 times on mount, because each copy read a computed style after each write.
- **No icon component and no icon set.** Components take icons as children or slots (`Button.Icon`, `Alert.Icon`). Todae draws the few glyphs a part needs to look whole, such as a close cross or a check, and `GlyphsProvider` swaps them for any library's icons. There is no global icon size scale; give a new icon slot its own `icon.size` token.

## Component API

- **Compound namespaces.** A component with parts is a namespace object with a `Root`: `Menu.Root`, `Menu.Item`, `Table.HeaderCell`. A component without parts is a namespace with only a `Root` (`Separator.Root`, `Stack.Root`). *Why:* one shape across the package.
- **A part lives inside its Root or arranges its Roots.** `Menu.Item` goes inside `Menu.Root`; `Button.Group` joins several `Button.Root`s. An element that stands on its own in the Root's place is not a part: another look of the same element is a variant prop, and anything else is its own component, such as `CodeBlock.Root` beside `Code.Root`. *Why:* Ben chose (2026-10-21) to make the code block its own component, since it has its own tokens, scrolling and accessibility needs, and block-only parts such as a copy button need a Root to live in; to drop `Chip.Overflow`, since a +N count is a plain `Chip.Root` with a visually hidden name beside it; and to keep `Button.Group` as a part of the Button family.
- **Don't nest namespaces** (no `Field.Button.Root`), and give each root one interactive role. Components sit side by side: a Field and a Popover are siblings, neither wraps the other. The exceptions are `Field.Picker` and ChipList's +N panel, which render their `Popover.Root` themselves, the way `Field.Select` has the browser's picker. `Field.Picker` holds any panel as its children, such as a `Calendar.Root`, an `OptionList.Root`, a `ColorPicker.Root` or one of the product's own, mounted only while it is open, and closes once a pick in a Calendar or a single-pick OptionList makes the value (`PickContext` in `components/pickerDone.ts`, which a panel calls with `complete` false for a change that goes on, such as a ColorPicker drag, so the field still hears a person's edit). `closeOnPick={false}` keeps it open for a panel that takes more than one pick, and a function child gets `close`. Any element wired with `useField`'s `getControlProps` in the same field, a Field part or a custom control, registers when it mounts and becomes the field's control, and `Field.Picker` leaves the field's id, description and focus to it, so a `Field.DateInput` and its calendar button, or a hex `Field.TextInput` and a swatch, share one field. Alone, the button is the field's control. *Why:* Ben asked (2026-11-09) for one rule a team building a design system can learn: anything you type into is a Field part, and what a popover holds is the panel's own component inside one `Field.Picker`. He also said "Stop making HOC when it can be composited", so a panel made of other parts, such as a date and time, is a recipe, not a part.
- **Dates and times are typed Field parts, with a picker composed beside them.** A date is `Field.DateInput`, a range of dates `Field.DateRangeInput`, a time `Field.TimeInput` and both `Field.DateTimeInput`, with the same props where they mean the same thing (`value`, `onValueChange`, `min`, `max`, `required`, `locale`, `placeholder`). Each is a text input the person types into freely in the locale's own formats, read on blur, Enter and a submit of its form with `parseDate`, `parseDateRange`, `parseTime` or `parseDateTime` and rewritten with the matching `format…` helper; typing alone fires nothing, and text that says no value stays, flagged once a commit tried it, and blocks a submit (`TypedInput` in `components/Field.TypedInput.tsx`). Without `onValueChange` the input is read-only, and a press on it opens a `Field.Picker` beside it. A picker beside one is `Field.Picker` around a `Calendar.Root` (with `mode="range"` for a range) or an `OptionList.Root` of `timeOptions`, whose name and glyph come from the typed input (`picks` in the field's registry); a date and time is both in one picker with `closeOnPick={false}`, a docs recipe. A new temporal part follows the same shape. *Why:* native date and time inputs look and behave differently in each browser and on phones and open the browser's own popups, which can't take Todae's tokens, so Ben dropped them on 2026-10-14. On 2026-11-09 he chose typed inputs as Field parts with composed pickers over the five `Field.*Picker` parts that held their own calendar or list ("Clearer rule wins"). The accepted cost: a bundler that doesn't tree-shake the `Field` object, such as esbuild or webpack, loads every Field part on a page with any field. A date and time is still one typed input, so one value, label and error go together.
- **Relative time is a helper that keeps no clock.** `formatRelativeTime(value, now, options)` writes text such as "3 minutes ago" with `Intl.RelativeTimeFormat` from a `now` the product passes, and keeps no timer, so the product decides when the text changes and can render the server's instant first. Under a day it counts whole seconds, minutes or hours between the two. From a day the unit is days, weeks from 7 dates apart (a count that stops at 4), months from a whole month and years from a whole year or 12 calendar months, and the count is in the calendar, in the value's time zone and the Gregorian calendar, with weeks from the locale's first day as in Calendar, so the "yesterday", "last week", "last month" and "last year" that `numeric: 'auto'` writes are the date, week, month and year before. `numeric` defaults to `'auto'`. *Why:* a ticking clock in Todae would re-render every product that shows a time and break server-rendered text, and Intl's words for -1 name the calendar unit before, which elapsed spans miscount.
- **A range of dates is one `DateRange` value, picked in `Calendar.Root mode="range"`.** `DateRange` is `{ start, end }`, both days included, and the props types follow `mode`. The first pick anchors a range and the second completes it, in either order; `onValueChange` fires only then, and Escape, or a modal's close request, drops the anchor without closing a popover around the calendar, through the Escape stack (see the Escape bullet). A new `value` equal to one of the last eight ranges picks reported and no value has answered yet is the parent's answer to that pick, however late, and moves neither the grid nor an anchor set since (it and the older reports then count as answered, so quick picks can be answered in turn); any other new `value` drops the anchor and moves the grid to its start unless the Tab stop is on one of its ends. The accepted cost: a parent that turns a pick down and later sets that same value, with no other value between, doesn't move the grid to it. A range holds only days that can be picked: after the first pick, a day past one that `min`, `max` or `isDateDisabled` rules out can't end it. Inside a `Field.Picker`, the completed range closes it, and `Field.DateRangeInput` sends a range through a value input as an ISO 8601 interval, such as `2026-10-03/2026-10-10` (see the value-input bullet). Presets such as "Last 7 days" are a recipe, not part of the calendar. *Why:* one value keeps a range's ends from being stored or validated apart, a gap in a range would hide a day that can't be booked, and presets are the product's data.
- **A number is `Field.NumberInput`, not a native number input.** `Field.TextInput` has no `type="number"` (a development warning covers JavaScript callers), so there is one way to enter a number, as there is for dates. It renders a native `<input type="text" role="spinbutton">`, so the browser keeps IME, undo and selection, and the value reaches the form through a value input of type `number` (see the value-input bullet), so the form sends `1234.5` whatever the locale. The pure `formatNumber` and `parseNumber` of `numberText.ts` write and read the locale's text beside `formatDate` and `parseDate`. The decisions:
  - **`onValueChange` fires only on a commit** (blur, Enter, a step key, a step button or a submit of the input's form), never per keystroke. A text that parses to nothing is kept, flagged and blocks its form through the value input's custom validity, and is never committed. *Why:* the callback per parsed keystroke leaks out-of-range values into product state.
  - **The grid wins over the digits the text shows.** A commit is within `min` and `max` and, with a `step`, on the grid counted from `min` (or 0); without a `step` it is rounded to the digits the text shows, by Intl, so the text, `aria-valuenow`, the value input and the callback agree. `boundsOf` is the one source of the lowest and highest number a commit can give, which `aria-valuemin` and `aria-valuemax` and the step buttons' disabled state read too. *Why:* one number everywhere, so the product is never told one the form does not send.
  - **One submit rule: a submit waits for the commit instead of forcing it.** Every commit waits for its own render, a step with no draft too. A submit of the input's form that finds a draft that reads, or a commit that waits for its render (a product's auto-submit in `onValueChange`), is held, the draft commits as blur does, and the form is submitted again once after the render that shows the commit, so the form sends what the product rendered and the product is told the number that is sent. A draft commits once, and a commit that takes the input out of the page still sends the form. One watcher holds it from the moment it is held, on the input's root node and not in the input's effects, which a Suspense boundary or an Activity turns off: it folds every later submit of the form into the held one (cancelled, the newest submitter kept), and its `MutationObserver` sends the form once, from the observer's callback after React's commit and never inside a layout effect, when the input is gone from the page or the page shows the commit (the input counts its commits in a data attribute, which render never reads). So a product's `onSubmit` sees the DOM, refs and layout effects of the whole layout commit (not passive effects, which a commit outside a discrete event runs later) and may call `flushSync`, and visible, Activity-hidden, Suspense-hidden and removed inputs all settle by that one rule. *Why:* forcing a render (`flushSync`) split the product's state from the payload when the submit started in a commit phase. Liveness is a decision: while a commit's render is pending (a Suspense boundary that has not resolved), every submit of the form waits for it, because sending the old number is worse than waiting; there is no timeout. Text that is no number never sends the old number either: the value input's custom validity lets a check that runs block it, and where none will run (a `noValidate` form that is not `Form.Root`, which registers its `<form>` in the `FORM_ROOTS` set of `Form.model.ts` in a layout effect, or a submitter with `formNoValidate`, a `Form.Root`'s too) the hook cancels the submit with `stopPropagation`, so every unreadable input of the form flags, and flags the text and moves focus to the first of them. Two limits: a native validating form checks before `submit` fires, so a programmatic submit with a stale invalid number is blocked (commit first, by blur or Enter); and the product sets its value synchronously in `onValueChange`, since the held submit goes out after the render that answers the commit, not after a transition or a store that updates later. The mechanics live in `useFormSubmitHold`'s comments.
  - **Step buttons keep focus and are not tab stops** (`Field.Increment` and `Field.Decrement` are parts, not a `stepper` prop). They reach the input through an entry it publishes to the field's registry, are disabled where a key would do nothing (`canStep`), and are named from the input's label, which one shared `MutationObserver` per document follows (`watchLabel`), reading again only when a label, or an element an `aria-labelledby` names, changes. *Why:* a press must not commit early or take the phone keyboard down, and a label can mount from any component.
  - **Typed characters are filtered only where that is safe**: an `insertText` that could not become a number is refused in `beforeinput`, while deletions, pastes and compositions land and are read or flagged on commit; Home and End are left to the caret, and there is no wheel stepping.
  - `formatOptions` leaves out `UNSUPPORTED_FORMAT_OPTIONS` (compact and scientific notation, significant-digit and rounding options), which `parseNumber` cannot read back or which round differently from a commit. Mechanics (the 15-digit guard, the step arithmetic, the token names) live in the code comments of `numberText.ts` and `Field.NumberInput.tsx`.
  *Why a text input, not a native number input:* it gives a string, no locale grouping, accepts `e`, steps on the wheel and draws a spinner that tokens can't reach.
- **A one-time code is `Field.OneTimeCode`: one native input drawn as boxes, not an input per digit.** The input has `autocomplete="one-time-code"`, is always `dir="ltr"`, and lies transparent over the boxes, which are `aria-hidden` and drawn from the value and the input's selection, never stored; `className` and `style` go on the wrapper that draws them. `onChange` gets the native event with the raw text and `onValueChange` the code. The decisions:
  - **One rule for where text lands: `editOf` in `oneTimeCode.ts`.** Todae puts every insert in itself (typing, paste, a drop), so the input has no `maxlength`: WebKit cuts typed text to it before `beforeinput`, which left a key typed at a caret inside a full code with nothing to insert, and Chromium cut a whole composition to it. Ben chose dropping it over working around WebKit. A paste and a drop are read from their own events, after the product's handler, so one the product cancels lands nothing. A cleaned text of `length` or more is a whole code and replaces the value; anything shorter replaces the selection and writes over what follows as far as it needs room, and what still doesn't fit is cut. So nothing typed is pushed off the end of the code, and with the caret after a full code nothing lands, so a product that sends at the last character never gets a second, different code from an extra key. Each edit goes in with `execCommand`, so it is a step of the input's own undo. *Why:* four review rounds found bugs while the rules were spread over `beforeinput` branches, composition handlers and a drop side channel.
  - **One `reconcile` for a change Todae didn't make**: autofill that skips `beforeinput`, an insert the browser won't let be cancelled, a composition, the browser's undo. What changed between the input's previous text and its new one is read as an insert by `editOf`, or kept as a deletion; for a composition, from the selection it started at, and for an insert the browser won't let be cancelled, from the selection its `beforeinput` saw, so a character typed next to the same one lands where it was typed (only an `insert*` `beforeinput` records that selection; any other one, or a blur, drops it). A change that leaves the code as it is reaches `onChange` but not `onValueChange`, and an undo or redo step that is no code reaches neither. *Why:* one reading of the input's text, rather than one per path, so every path keeps the rule.
  - **A composition is the browser's while it runs.** A React write would end it, so the input renders its own text and the boxes show it reconciled. A composed text that is already a code is reported as it is typed, through `onChange` and `onValueChange` alike, since a phone keyboard may compose a whole alphanumeric code as one word; a romaji or pinyin step such as `k` can so be reported and taken back, which the docs say plainly. Every path that reports a code also calls `onChange`: a composition that ends on the text the input already holds is written through the same event path. Anything else is applied when the composition ends: when the rule changes the input's text, Todae writes the code, not an `execCommand` edit, which would leave the commit on the undo stack as a step that is no code. At the end the `value` is told apart by its content, not by when it arrived: `cleanCode` lets only digits and Latin letters through, so the one lossless change a product can make to a code it was told is its case, and a `value` equal to the start code or any code reported during the composition, ignoring case, is the product's answer to it (an uppercased code, however late, even to an earlier step). A `value` that is neither the code the composition started from nor that answer is an override, and it wins (an override equal to the start code is indistinguishable from no change). Otherwise Todae reports the code the composition ends on whenever it differs from the last one reported, even when it equals the product's `value` (a fixed or case-normalizing product hears the take-back), and when nothing was reported, only when it differs from `value`. Every write Todae makes itself, rather than through `execCommand`, is one `InputEvent` of `inputType` `insertReplacementText` whose `data` is the whole new code, so `onChange` reads it like an edit. `onBeforeInput` is not accepted: typing goes through Todae's own native `beforeinput` first, so a product's would never see typed text. So undo after a composition may also take back what was typed just before it, or leave the code as it is, and never reports a code the person didn't see. Composition is verified in Chromium only, which has CDP's IME input; paste in Chromium, Firefox and WebKit. *Why:* round 5's machinery to keep that undo exact broke in more cases than it fixed, and round 7's hold of a full code until the end lost composed codes for products with `onChange` alone or that normalize.
  - **Full-width digits and Latin letters** (U+FF10–FF19, U+FF21–FF3A, U+FF41–FF5A) count as their ASCII ones in `cleanCode`; not NFKC, which would also turn `½` into `12` and `①` into `1`.
  - **A press or a drop is placed by the boxes**, not by the transparent input's own text: a press on a box selects its character, so typing replaces it, and a press or a drop on an empty box or past the last one is after the code. The wrapper fills the field's row and is left to right in any page, so the room past the last box is after the code. The press is read on `click`, not by cancelling it, so a phone focuses natively and keeps its keyboard. A drop the product cancels in its `onDrop` lands nothing.
  - **The ring goes on the active boxes, not the shell**; with the caret after a full code no box is active and the row draws it. The row (`data-todae-focus-ring`) draws a transparent ring-sized outline while the input is focus-visible, so `revealRing` has the room the moment focus lands, before the render that marks the active box.
  - **The length check is a custom validity** (`useCustomValidity`) while `0 < value.length < length`, so it reports `kind: 'customError'` with the `tooShort` string and wins over a `Field.Root` `customValidity` while the code is short. It is not `minLength`, because the browser's `tooShort` skips a value a script sets or a cleaned paste writes: an exception to "nothing in Todae computes `required` or `min`".
  - **There is no `onComplete`**: the product sends when `value.length === length`.
  *Why one input:* a row of one-character inputs breaks paste, SMS autofill, undo and screen readers, and a native input keeps them all.
- **A button in a field's line is an icon-only `Button.Root` in `Field.Root`.** In any field but a `Field.Textarea`, it takes `field.action.size` and is centered on the field's first line, so a one-line field stays one line tall and a `Field.ChipInput` whose chips wrap keeps the button the same size on its first line (the chip row, with `chipLayout="row"`), and its rule outweighs Button's own icon-only padding in any sheet order. In any field, a press on it keeps focus where it is when focus is in the field (the shell cancels the `mousedown`), so the caret stays and Safari, which doesn't focus a pressed button, doesn't blur the field; Tab still reaches it. The cost, which the step buttons share: a mouse press doesn't move focus to it, so a screen reader doesn't read it then. It stays a plain button: it is not the field's control, and `Field.Root`'s `disabled` doesn't reach it. There is no `Field.Action` part and no reveal or clear prop. *Why:* a password's show button or a clear button is a `Button.Root` the product already styles, and what it does is the product's; only its size and its press in the field are Todae's.
- **`Field.TextInput` keeps its caret when its `type` changes while it has focus**, from the selection it has when the type changes, put back in the next frame since Chromium moves the caret when it next renders such an input; checked in Chromium, Firefox and WebKit. *Why:* a show button switches a password to text, and the browser would move the caret.
- **A part that renders an element forwards native attributes and its ref.** Type its props with `ComponentPropsWithRef<'element'>`, spread the rest onto the element, and merge `className` with `cx`. *Why:* a company wrapper only has to spread props to keep everything working.
- **Don't make behavior depend on a child's component type.** Parts register through context, or a parent looks for a data attribute the child renders. A type check may only guess the first server render, as long as registration or a data-attribute read corrects it after hydration. *Why:* a company's wrapped `OptionList.Option` or `Button.Icon` must still work.
- **A part picks its element in one of two ways.** A part that must know its tag, from a short list of HTML elements, takes `as` (`Stack.Root`, and `Text.Root`, which sizes a heading by its level). A part whose single interactive element can be another element, such as a router's link, takes `render`, which gets the props the part would have put on its element and returns that element: `Link.Root`, `Nav.Link`, `Button.Root`, `Menu.Item` and `Toast.Action`. Type the props `render` gets as `<Part>RenderProps`, or reuse the type of the part it is a kind of, as `Nav.Link` takes `LinkRenderProps`; leave out the props only the default element takes (`Button.Root` drops `type`, `disabled` and the toggle), add no role, and log a development-only error when the element can't carry the part's role, as `Button.Root` does for anything but an `a` or a `button`. Parts whose element must stay a button, such as close buttons and `Menu.Trigger`, take `ButtonActionProps`, which has no `render`. Routers plug in the same way, with no router dependency. *Why:* Ben chose (2026-10-20) one mechanism over a component per role and look, such as a ButtonLink, which doesn't scale; `render` over `as` keeps the props types simple and lets the product choose which props reach a router's link.
- **Text Todae writes by itself**, such as a close button's default name, comes from `StringsProvider` (`useStrings()`), not a hard-coded English string. A server entry, which can't read context, uses `DEFAULT_STRINGS`.
- **Glyphs** are read from `GlyphsProvider`. Put glyph state (hidden, rotated, mirrored) on the `[data-todae-glyph]` wrapper span, not on the `svg`, so a swapped-in icon follows it.
- **Server entries.** A component that a Server Component should render directly gets a server-safe entry, `src/server/<slug>.ts`, imported as `@tounsoo/todae/<slug>`. Add the slug next to the existing ones in four lists: the entries in `vite.config.ts`, `exports` in `package.json`, the server-entry list in `src/entries.test.ts`, and `paths` in `apps/docs/tsconfig.json`. Where the component reads a client provider or needs hooks for part of its behavior, such as Text's tooltip, the client version is a `*.client.tsx` wrapper exported from the root entry.
- **Keep `'use client'` out of component and hook files.** It sits in `src/index.ts` and the provider files. `src/entries.test.ts` checks that a server entry's import closure has no `'use client'`, hooks, `createContext` or CSS import, so helpers a server entry needs stay hook-free in their own files (`cx.ts`, `tone.ts`).

The rules below were read from the code rather than decided in a thread. Follow them unless there is a reason not to.

- **Controlled state comes in triples:** `value`/`defaultValue`/`onValueChange`, and the same for `open`, `checked` and `pressed`, built on `useControlledState` (`hooks/useControlledState.ts`), which products get too. The callback gets the new value, not an event, and `undefined` means uncontrolled. Its setter builds on the latest write, so two writes before a render both count, and a controlled write renders the hook again so a change the owner did not pass back is dropped; a controlled value with no callback ignores writes.
- **`onOpenChange(open, reason)`** passes a typed reason, such as `'escape'`, `'backdrop'` or `'close-button'`, so a product can tell why an overlay closed.
- **Names.** Props types are `<Component><Part>Props` (`BadgeRootProps`). Union prop types are exported as `<Component><Prop>` (`AlertTone`, `ButtonVariant`). Form state is `disabled` and `invalid`, not `isDisabled` or `error`. Modal overlays take `dismissOnEscape`, `dismissOnBackdrop`, `initialFocusRef` and `restoreFocusRef`.
- **Read Fieldset state** through `useFieldsetState`: `disabled` is OR-ed with the nearest Fieldset, and a control's own `invalid` wins over the Fieldset's.
- **Run the consumer's handler first** with `composeHandlers(theirs, ours)`, which skips Todae's behavior when the consumer calls `preventDefault()`. A handler that opens or acquires, such as a trigger's click, pointer enter or focus, follows this rule. A handler that releases or keeps focus bookkeeping runs Todae's part after the consumer's handler, whatever it did. Examples are `useTooltip`'s pointer leave and blur, the focus-leave close or tab-stop return on blur in `Menu.Content`, `Tabs.List`, `ToggleGroup` and `Tree`, `useRovingFocus`'s focus tracking, and `Menu.Trigger` clearing its pending open end on blur. A prevented event then can't leave a tip or menu open, or a key's request pending.
- **Form validation is the browser's, and Todae decides when, in what words and where focus goes.** `Form.Root` is a component: a container that gives context to whatever children it holds, with focus moves and ARIA wiring a recipe may not carry. It sets `noValidate` and holds no values, schema or async logic. Nothing in Todae computes `required` or `min`; `describeValidity` reads the control's `ValidityState` and words the first failed flag from `StringsProvider`, and `validationMessage` is used only for a `customError`, whose text is the product's. `customValidity` on `Field.Root`, `Fieldset.Root`, `Checkbox.Root` and `RadioGroup.Root` goes through `setCustomValidity`, so a live rule blocks a submit like any other and needs no second engine. One control has one custom validity, so each owner registers its message for that element and the control gets the first non-empty one, innermost owner first (the control's own part, then the enclosing fieldsets outward), an empty message or none being no rule; an owner unregisters on unmount or when its target changes, so a `Fieldset.Root customValidity=""` never clears a nested `Field.Root`'s message. Todae reads the element before it writes: it writes the winning message whenever the element's current custom message differs (so a product's `setCustomValidity('')` doesn't make Todae give up its rule), and clears only when the element still holds exactly what Todae wrote (`validity.customError && validationMessage === written`), so a product's own message survives. A control barred from validation (disabled, or readOnly) reports an empty `validationMessage`, so there Todae trusts its record of what it wrote, and a product's own message set while the control is barred may be cleared. On a `Fieldset.Root` it goes to the fieldset's own first validating control, else the first at any depth (the message then shows where that control's error shows), with a development warning when there is none. *Why:* a second validity engine drifts from the browser, and the browser's own message is in the browser's language, not the page's.
- **A form of several steps is a recipe over `Form` and `Steps`.** The [Wizard](apps/docs/app/(en)/recipes/wizard/page.mdx) recipe gives each step its own `Form.Root`, all mounted and `hidden` but the one showing, and there is no `Wizard` part. `Steps.Root variant="progress"` draws where a person is in a form, with a still marker on the current step and no strike-through; the default `plan` draws work that runs. Moving focus to the shown step's heading stays in the recipe: it is one focus call on a heading the product renders, made from a microtask queued in a layout effect on the step, after `Form.Root` has rendered any reply, and skipped when focus is already in the step's form. Todae has no notion of steps to hang it on, and choosing and focusing a control for a reply stays in `Form.Root`. *Why:* the steps and where they send are the product's flow; one form across the steps would show every step's problems after the first Next, a form that remounts doesn't take a reply as one, and a spinner on a step the person is filling in reads as loading.
- **Sign-in and sign-up are a recipe.** The [Sign-in and sign-up](apps/docs/app/(en)/recipes/sign-in/page.mdx) recipe shows a password with an icon-only `Button.Root` toggle in its field that switches the input's `type`, keeps one label and is set back to hidden on submit; it puts a wrong email or password on the password through `Form.Root`'s `errors`, and asks for a code in a second `Form.Root` with its own `key`, focused with `autoFocus` and sent a short pause after it is full. There is no `SignIn` or `PasswordInput` part. *Why:* which accounts exist, how they are checked and where a code goes are the product's, and the parts already carry the focus, the validation and the autofill.
- **A validation scope is a `Field.Group` or `Fieldset.Root` inside a `Form.Root`, not a new wrapper.** Its controls are the `input`, `select` and `textarea` elements that take part in validation and whose nearest `[data-todae-validation-scope]` is it, so a nested scope answers for its own. `Field.Group` and `Fieldset.Root` carry that attribute in or out of a form, so "own" is the same structural fact everywhere and `customValidity` lands on the same control either way. An `ErrorMessage.Root` with no `id` registers with the scope, renders only while the scope shows a problem, and is the only thing that puts the error id in `aria-describedby`, so the id never dangles: on the controls for a `Field.Group`, on the `<fieldset>` alone for a `Fieldset.Root`, and never on a control with `invalid={false}`. The scope joins controls through the `FieldsetContext` merge (`invalid` added, `errorId` set), so each control's own `invalid` still wins and a `Fieldset.Root invalid` still applies; nothing is plumbed per control. Outside a `Form.Root` a scope is inert. *Why:* `Field.Group` and `Fieldset.Root` already hold a label and its messages, and Ben chose one wrapper for that.
- **What a scope shows is a pure function of the controls' validity, the server errors, their dismissals and one reveal flag.** Per form: the attempt counter, the dismissals and the summary's entries (the scopes that failed at the last attempt) live in `Form.Root`; per scope: touched and revealed. A change marks only the scope that owns its target as touched, and a change or reset from a portaled element outside the form's DOM acts on nothing. A scope is revealed after a change inside it followed by focus leaving it (`useFocusLeave`, so a window switch is not leaving), or after any submit attempt; a reset un-reveals every scope. There is one timing and no `mode` prop, as `:user-invalid` has one. *Why:* it rewards early fixes and punishes late, and it keeps the prop surface small.
- **Server errors are the product's `errors`, keyed by control `name`, and do not block a submit.** They show at once and win over a native problem in what is shown, across all the scope's named controls, disabled and read-only ones too (native problems come only from controls that validate). Todae never writes `errors`: a product clears it when it sends (in `onSubmit`) and sets it when the reply comes. An edit to a control hides its entry until the next submit, or until `errors` drops that name or changes its text (a map of name to hidden text, forgotten as soon as the entry leaves `errors`, so an availability check that clears and re-sets "Taken." shows it again, while inline `errors` rebuilt every render with the same content changes nothing); a reset hides every current entry. A reply is a change of content, not of object: after a send, a commit whose `errors` content differs from the commit before and has entries is the reply (clear-then-set counts; a rebuild of the same content does not), unless an edit, reset or failed submit came first. A reply lists and focuses only server errors, never a native problem the person hasn't reached, and the row of a disabled control (`:disabled`, so a disabled fieldset counts) in the summary is plain text. The summary stores each row's `Reading` (`name`, `id`, `label`, `disabled`, carrier) as the scope read it, compared by one `sameReading`. In development `Form.Root` warns, when a reply to a send names a control no scope shows, once per form and name; a name no control has yet is rechecked one task later, and the key is spent only when it warns. The check stays at reply detection, not at render. After a successful send the form keeps waiting, so an `errors` change the person didn't cause is taken as the reply. *Why:* the server knows what the browser can't, and a stale error that blocked a resubmit would trap the person.
- **Form's submit check runs before the product's `onSubmit`.** This is a deliberate exception to running the consumer's handler first: a submit with an invalid control is cancelled and never reaches it, unless the submitter has `formNoValidate`, which is a send to the server without the check, not an attempt: it still reaches `onSubmit`, clears the dismissals and waits for a reply (except that a `Field.NumberInput` holding text that is no number blocks even this submit: it is cancelled and focus moves to the text), but leaves the attempt count and the summary's failed list alone, so it reveals nothing new. A failed submit focuses `Form.Summary` if it renders, else the first problem in document order, with the normal scrolling `focus()`. All focus (failed submit and reply) derives from `failingEntries`: a control a scope reads takes focus only as the carrier of its scope's entry, and only when that entry is enabled, so a scope whose shown control is disabled gives no focus to its other controls; on a failed submit these merge in document order with native problems of controls no scope reads. The summary lists the scopes that were failing at the last attempt, so a field fixed and broken again, or edited into a new problem, doesn't join it until the next submit. Its entries are state computed outside render by one `refresh` action: `Form.Root` reads the DOM (with the scopes' own pure helpers) when a submit or reply happens, and again from an effect or event when a scope sets new readings, when a scope unmounts, when `errors` or the dismissals change and when a reset has applied, keeping only the entries still failing. `Form.Summary` renders the stored entries and reads nothing during render. Neither the rows nor the focus wait on the scopes' state. A row links to its control when it has an `id` and is a button when it has none. *Why:* the product's handler should run for a valid form without repeating the check, and a person who submits a form with a problem needs to be told where.
- **A `Field.Root`'s parts meet in one registry.** `Field.Root` owns a `FieldRegistry` (`components/fieldRegistry.ts`), and it is the only way the parts of a field learn about each other. Every element wired with `useField` registers once, from its ref, as `{ node, role, takesName, toggle? }`: `role` is `control`, or `picker` for `Field.Picker`'s button (`useFieldControl({ role: 'picker', toggle })` in `Field.Picker.tsx`), which leaves the field's id, description and focus to any control beside it; `takesName` is whether `getControlProps` gave it the field's name, recorded where the props are made, never read back from the DOM; `toggle` is what a press on the shell calls to open a picker. A `Field.Root` nested in another adds its registry to the outer one's (`addChild`), so a press on the outer shell can open the inner picker it lands on. A text control publishes its text for `Field.Counter` (`useTextControl`; the counter counts the text control that mounted last), a `Field.NumberInput` its stepper for the step buttons, a typed input what a `Field.Picker` beside it opens (`picks`, for the button's name and glyph) and a pick listener (`onPick`), and each value input itself. A pick in a `Field.Picker` calls `picked()`, so a typed input beside it drops what was typed, even when the pick is the value already set, and reports a person's edit under its own name; a typed input that becomes read-only or editable calls `editableChanged()`, so `Field.Root` places its `customValidity` again. Parts write from refs and layout effects, and read through `useRegistryValue`, one `useSyncExternalStore` path. The one write a render makes is `seedText`, the text before any commit, which only the counter's server snapshot reads, so server markup and hydration show the count. *Why:* a field's ownership was decided by a count store with three sub-stores, a `counted` flag, a data attribute written and read back after render, and two module-level `WeakMap`s across seven files, and its text was written to the store during render (audit of 2026-11-02, finding 3).
- **Every value a control holds reaches the form through one native, validated element.** `Field.TextInput`, `Field.Textarea`, `Field.Select`, Checkbox, Switch and RadioGroup are that element. A form reset puts that element back with no change event, so after a reset that no handler cancelled (`useFormReset` in `internal/formReset.ts`, which waits a task for those handlers), Checkbox, Switch and RadioGroup store what the reset put back and report it through their change callback, and `Field.NumberInput` drops the text being typed. Neither reads as an edit. They read the inputs' `defaultChecked`, which React sets once from the checked state an input mounts with (in a group, the last radio in tree order that has it, as the reset checks them in order), not `checked`, since a render in the reset's own task (a `Field.Group`, or a product's `onReset`) writes the old `checked` back first; then they render again, so a controlled owner that keeps its value shows it. A controlled owner that sets a new value in its own reset handler has answered the reset, so the control leaves that value alone. A RadioGroup reset to no pick reports `null`, so `onValueChange` takes `string | null`, as `value` does. A control whose value is not its text (the typed inputs `Field.DateInput`, `Field.TimeInput`, `Field.DateTimeInput` and `Field.DateRangeInput`, `Field.NumberInput`, `Field.ChipInput`, a product's `role="slider"`) renders a **value input**, with the props from `useField().getValueInputProps(options, control)`: an `<input>` of the native type that matches the value (`date`, `time`, `datetime-local`, `number`, `text`), visually hidden with `VisuallyHidden`'s class, `aria-hidden`, `tabIndex={-1}`, `autoComplete="off"`, `data-todae-value-input`. It is not `readOnly`, `inert` or `type="hidden"`, since each of those bars the element from constraint validation. Never write `type="hidden"` for a value a form should validate. It is **controlled** (`value` and a no-op `onChange`), so a value the product sets fires no event, and **a person's edit is announced explicitly**: `useField().notifyValueChange()`, which a control calls from its user path (a pick, a chip added or removed), tells `Form.Root` (`edited`: ends the wait for a reply and hides the server error under the field's name and the names the control and the value input send) and the nearest validation scope (`touch`) through context, with no DOM event. No product-driven set, form reset or mount may read as an edit. The feature lives in `components/valueInput.ts` (`useValueInput`, which `useField` joins), not in the hook. **The getter takes the control's resolved props as data, so the order of calls cannot make it stale:** `control` is what `getControlProps` returned (the text input's props, for a typed input), and the getter reads `disabled` (including an `aria-disabled` control), `form` and whether the control has a `name` from it; the type makes the argument required and brands it, so only `getControlProps` produces one. The input goes without a name when the control has one, else takes `options.name` (a typed input's own `name` prop), else the field's name unless a control already took it, which it asks the field's registry (`namedBy`); presence is read with `useSyncExternalStore` over the registry (`useRegistryValue`) returning only the boolean a decision needs, so a control re-renders only when that flips, not as another control mounts; the name its own control took is not counted, so a named control mounts in one commit. The getter's `ref` is the same function across renders while the bounds are, so React does not detach and attach it each time. Nothing overrides the decision at a call site. **Ownership is structural:** the control's ref, as it registered with the field, is what a value input speaks for, so a typed input's value input always speaks for its text input. `Field.Picker` renders no value input and sends nothing: beside a control its button drops the id and the description and never takes the field's focus target from it (the registry's `focusTarget` is the last `control` to mount, else the last picker). An input focused with no owner blurs. The ref registers the input with the field's registry and in `validity.ts` (`registerValueInput`, one private `WeakMap` of `{ owner, bound }`, which `Form.Root` reads since it finds controls in the DOM): `owner` is used by `focusTargetFor` and `reachTarget` for `Form.Root`'s first-problem focus, `Form.Summary`'s links and the row's `id`, `disabled` and label, and `bound` is `{ min, max }` already worded by the typed input in the format its text uses (`valueBounds` in `htmlValue.ts`, with `formatDate`, `formatTime` or `formatDateTime`), so `describeValidity` names it without parsing. `Field.Root`'s `customValidity` goes on the field's control when that is a carrier, except a read-only typed input, which a form leaves unchecked, else on **the first value input of the field in document order** (the registry's `firstValueInput`). A typed input's value input holds what a readable draft says before the commit, so the browser's own check of a form, which runs before its submit event, sees it. The messages for `date`, `time` and `datetime-local` read "or later" and "or earlier" (`dateRangeUnderflow`, `dateRangeOverflow`). Focus on the input moves to its owner (a native `focus` listener, since WebKit sends a date input no `focusin` once focus moves into its own fields), so the browser's own check outside `Form.Root` lands on the control too. `FOCUSABLE_FIELD_CONTROL_SELECTOR`, `tabbables.ts` and the shell's focus ring exclude `[data-todae-value-input]`, so it is no tab stop and no press on a shell focuses it. `TypedInput` takes `required` once, for `aria-required` on its text input and for the value input, which the `FieldValueInput` component renders; `valueBounds` builds the bounds options. Choices per control: `Field.DateInput`, `Field.TimeInput` and `Field.DateTimeInput` use `date`, `time` and `datetime-local` with `min`/`max` from their props and `step="any"` on the last two, since any time can be typed; a `Field.TimeInput` whose `min` is later than its `max` is an overnight range, as a native time input reads it, and `timeOptions` with the same bounds lists the same times (`timeSlots`' `allowOvernight`); a native date input holds only the years 1 to 275760, so a value or bound outside them reads as none, and `htmlDate` and `htmlDateTime` warn once in development. A typed input's text input says `aria-required` itself; a required `Field.ChipInput`'s text box, which is not what must be filled, is described by the `required` string (`aria-describedby`) instead; a custom control sets `aria-required` itself where its role allows. `Field.DateRangeInput` uses `text`, since no native type holds a range, and sends the range as an ISO 8601 interval written by `htmlDateText`, which holds any year and so does not warn; a text input takes no `min` or `max`, so a range outside them sets the value input's custom validity (`outOfBounds`), worded with the same "or later" and "or earlier" strings as a date's bounds and reported as `rangeUnderflow` or `rangeOverflow` (`markCustomKind` in `validity.ts`, which also reports a typed input's unreadable text as `badInput`); a color has no part that sends, so a `Field.TextInput` beside a `Field.Picker` with `swatch` sends the color as typed, since a `color` input lowercases the value and turns any value that is not `#rrggbb` into black; `Field.NumberInput` uses `number` with `step` from its props (`any` without one) and `min` and `max` from `boundsOf` (the grid points within the range, so an off-grid `max` gives the highest point on the grid), and `bound` in its own format; its text input is cut loose from the field's name (`getControlProps(props, { sendsName: false })`, so the control passed to the getter has none and its name marker is off), so the value input sends `1234.5` whatever the locale and a text input beside it can still take the name; `Field.ChipInput` has always sent only the text being typed, so its value input sends nothing (its text input took the name), carries `1` or nothing and is empty exactly when there are no chips, which `required` checks. A value input is a carrier like any native control: `carriersIn` finds it inside a `Field.Group`. *Why:* a value that submits is then a value the browser validates, and the browser does the math, including date ranges.
- **A part rendered outside its Root should throw.** Misuse that can still render (an icon-only button with no name, both `checked` and `defaultChecked`) logs a development-only `console.error` or `console.warn` behind `process.env.NODE_ENV !== 'production'`. The exception is a server-safe component, such as Card, Table and DataList: its parts read no context, so they render anywhere and can't throw.
- **State reaches CSS through `data-*` attributes.** Boolean state is an empty attribute, left off when false (`data-selected`, `data-disabled`); enum state is its value (`data-tone`, `data-orientation`). Name an attribute that other Todae code looks up `data-todae-*` (`data-todae-glyph`, `data-todae-roving`).
- **Disabled items.** Menu items and listbox options take `aria-disabled`; menu items also stay in the arrow-key order, so a screen reader announces them as unavailable. Items that are buttons, such as tabs and toggle-group items, take native `disabled`. Standalone native controls take `disabled`.

## Hooks

- **Prefer one options object in and one result object out,** typed `Use<Name>Options` and `Use<Name>Result`, for hooks that drive markup.
- **Prop getters** are named `get<Element>Props` (`getTriggerProps`, `getListboxProps`). A getter that takes the caller's props merges them and keeps the caller's ref.
- **A hook that creates ids** accepts an optional `id` and returns them as `ids`, so a recipe can wire labels by hand. Ids that end up in a CSS selector or ident go through `useDomId()`.
- **The package source has four layers, and imports run one way.** `src/components/` holds the parts. `src/hooks/` holds the public hooks, `src/overlay/` the overlay engines (the modal stack, `popover.ts` and `tooltip.ts` with the tooltip's intent machine, warmth counter and wire types) and `src/internal/` the helpers every layer shares (ref and handler composition, `cx`, DOM ids, IME checks, `focusWithoutScroll` and `revealRing`, the active element, `warnOnce` and the toolbar context). A public hook whose engine is an overlay, such as `usePopover`, `useTooltip` or `useModalLayer`, is a thin file in `hooks/` over `overlay/`. `hooks/`, `overlay/` and `src/mentions/` take only types from `components/` (the overlay engines do build on `hooks/useControlledState.ts`), and `internal/` imports nothing else in the package; the `todae/layer-imports` rule in `eslint/todae.mjs` holds both by resolving each import's path, so every spelling of a path, re-exports, inline `type` imports and `import()` are checked. A hook that is Field's or Form's glue, such as `useField`, lives in `components/` beside the context it reads. An overlay anchored somewhere other than its trigger gets its style from `anchoredContentStyle` in `overlay/anchorName.ts`, the twin of `anchorTriggerStyle`, and `usePopover` takes that anchor as `anchorName`. *Why:* popover, tooltip and modal behavior lived in three folders and hooks and components imported each other, so there was no one place to look and no rule to hold the direction.

## Tokens

- **Follow DTCG 2025.10.** Aliases are JSON Pointer `$ref`s (`{ "$ref": "#/color/gray/900/$value" }`); the build rejects curly-brace aliases. *Why:* companies should be able to use standard DTCG tools on Todae's tokens.
- **One Todae `$type`: `textTransform`** (`none`, `uppercase`, `lowercase` or `capitalize`), for letter case, which DTCG 2025.10 has no type for. Add no other non-standard type. *Revisit when DTCG adds a standard type for letter case:* move to it and retire `textTransform`.
- **The base theme is Graphite:** cool ink grays, a neutral ink accent, small radii and a 600 bold. Tokens that a theme may want to change but Graphite leaves flat still exist, set to a neutral value, such as `card.shadow`, the overlay shadows (`dialog.shadow`, which `sheet.shadow` and `drawer.shadow` follow, `popover.shadow`, which Menu, the field pickers and the Select list follow, `tooltip.shadow` and `toast.shadow`) and each button variant's `shadow` (`shadow.none`, a transparent layer rather than `none`, so Button can add its pressed ring to it), the `font.letter-spacing` tokens (0), the `font.text-transform` tokens (`none`), the chip dismiss button's box (`chip.dismiss.size`, `radius` and `bg`, which equal the bare icon by default), and ToggleGroup's track and the segment tokens that differ from Button (`togglegroup.*`: an empty track and joined secondary buttons, which a theme can turn into a segmented control without a variant; a vertical group does not draw the track). A container that restyles the buttons inside it, as ToggleGroup does, sets Button's `--_button-*` inputs from its own tokens, which Button reads before its variant's. *Why:* a company retheme overrides a token instead of writing CSS against a component.
- **Four layers, lowest first:** `core` (raw scales), `appearance` (light and dark semantics), `density` (spacing per density) and `contract` (what components read; button variants are a contract modifier). A token references a lower layer, a token in its own set or modifier context, or a token in an earlier set or modifier of its own layer in `resolutionOrder` (`tokens/resolver.json`); the build checks this. A token in a set before the first scoped modifier, such as core, is declared only on `:root`, so it holds a literal and references nothing.
- **Give a new component contract tokens and have its CSS read them.** Put them in a file in `tokens/components/` and add that file to the contract set's `sources` in `tokens/resolver.json`; the build ignores a file that isn't listed. Give the component's top group a `$description` saying which component reads it, and give a new semantic token its own; a test fails on an undescribed appearance, density or contract token. Point color tokens at semantic `appearance` tokens; a `ring.focus` color is the exception (see focus rings below). Every contract token is read by Todae's code, or listed in `src/styles/tokenUsage.test.ts` as one products apply themselves; a token nothing reads would only mislead a theme author. *Why:* a rebrand changes the appearance layer and every component follows.
- **Component token names** are `<component>`, then up to three parts, the property, and an optional state (`chip.bg.hover`, `separator.color`, `text.h3.font.size`, `steps.marker.progress.dot.size`). The properties that take a state are `bg`, `border`, `color`, `decoration`, `decoration-thickness`, `fg`, `leading`, `ring` and `shadow`. Every one of them takes the shared states `default`, `hover`, `active`, `pressed`, `focus` and `disabled`. Both lists are `tokens/name-schema.json`, the only place they live. A component that needs its own words after a stateful property lists them in a slot for that property in `tokens/resolver.json`, with the shared ones it uses (`"option.bg": ["default", "hover", "selected", "selected-highlighted"]`). The build holds the group to exactly that list, and the name check accepts those words there and nowhere else. A word after a stateful property names another value of that property, a state or a role (`field.fg.placeholder`, `text.leading.tight`). So the schema gives each stateful property the `$type` of its values, and the name check fails a word whose token has another type, or a word that is itself a property, even when a slot lists it. A sub-property joins its property with a hyphen instead (`focus.ring-width`, `link.decoration-offset`, `chip.ring-width`), and a bare property holds its own value (`focus.ring`, `alert.critical.border`). The build fails a token under another token, and two tokens that write one CSS variable, so a token package that still writes a renamed path such as `focus.ring.width` fails instead of building. `tokens:check` applies that schema to contract paths only, and it fails a token in any layer that no component stylesheet or source literal reads, directly or through an alias whose chain ends in a read. A core, appearance or density token is a step of a scale, such as `color.red.400`, `space.7` or `color.bg.canvas`, so it stays while another step of the same scale is read. `apps/docs` is not a reader. Names that already fail are `tokens/name-grandfather.json`. That list can only shrink. The change that fixes a name deletes its entry. `tokens:check --base <sha>` fails a new entry. A base commit with no list skips that once. `pnpm tokens:grandfather` rewrites the list from the current violations and refuses to add an entry once the file exists. *Why:* a new state word, or a token nothing reads, used to ship with nothing checking either. The state words used to live in three places that disagreed, so the build required names the name check rejected. Slots then listed sub-properties such as `focus.ring.width` and `link.decoration.thickness` as states, and the check couldn't tell the two apart.
- **Focus rings read `focus.ring`, `focus.ring-width` and `focus.ring-offset`.** A new component's `ring.focus` color token points at `focus.ring`, not at the accent; `tokenConsistency.test.ts` checks this. The `focus` set comes before `button` in `resolutionOrder` so button variants can read it. *Why:* one token recolors the focus rings (invalid rings keep their own `ring.invalid` color), and a company's own focusable UI has a ring to reach for.
- **Translucent colors take `alpha` from the `opacity` scale** with a `$ref`, not a literal. `color.bg.transparent` keeps a literal 0 on purpose. A shadow's color is literal too, since the build rejects a `$ref` inside a shadow layer.
- **Contrast is APCA (Lc), not WCAG 2 ratios.** Text pairs and their minimums live in `$extensions["dev.todae"].contrast` in `tokens/resolver.json`, and the build fails a pair that falls short. Semantic pairs sit on the appearance modifier; pairs of Field, Nav, OptionList and Tree text on their own backgrounds, and of `text.label.fg` on the four `color.bg` surfaces and `popover.bg`, sit on the contract set, so a company that restyles those is checked. The contract set also checks indicator pairs: progress and meter fills on `progress.track`, the switch thumb and check glyph on `selection.bg.checked`, the switch thumb's edge (`selection.thumb.border`) on the off track (`selection.track.bg`), and primary button text on its fill. A graphic pair needs Lc 30 and a text pair needs Lc 60. The docs playground measures those pairs for every preset in light and dark, and every preset must pass them. A pair whose background may be translucent lists the opaque surfaces it can sit on in `over`. A company pair with the same `fg` and `bg`, in any of its sets or modifiers, replaces Todae's and keeps its `over` unless it lists its own. A company's token build inherits these pairs, and its resolver may change a pair's minimum or add pairs. `ThemeProvider` overrides are measured only in development, against Todae's pairs and minimums (generated into `CONTRAST_PAIRS`), from the browser's computed colors; a `console.warn` names the pairs that fail with the provider's overrides but pass on the same element without them. The OKLCH to sRGB and APCA math has one copy, `src/color/apca.ts`, which the token build, `overrideContrast.ts` and the playground's preset check all import, so a color measures the same in each. A pair that fails names the nearest lightness of its `fg` or its `bg` that passes, on the token that holds the literal value, in steps of 0.001, leaving out a lightness that would fail a pair that passes now; a literal in Todae's own files is named as one to override in the company resolver's entry of the same name, and a failure with the same advice as the one before it says "same as above".
- **The accent is neutral ink, not a hue.** Don't introduce a blue accent; a build test lets only `color.category` read the blue scale.
- **Tones.** Status tones are `info`, `success`, `warning`, `critical`. Category tones are numbered `category-1` to `category-8`, not named after hues, so a company can re-hue without renaming. Avatar takes neutral and category tones, not status tones. `categoryTone(key)` hashes a string to a tone; keep its pinned test values, since changing the hash changes every user's color.
- **Generated files are committed.** Run `pnpm tokens` after editing token files; `pnpm tokens:check` fails on drift.
- **The public token API is `tokens/api.json`.** `pnpm tokens` writes one entry per token path and its `$type`. The same path in more than one context is one entry. `pnpm tokens:check` fails when the file drifts, and the error says to run `pnpm tokens`.
- **CI rejects a removed, renamed, or retyped public path.** The walk is the first-parent commits from the base, so merging main does not look like a removal of a path this branch added. A new path only needs the snapshot updated. A changeset does not waive a removal, a rename, or a retype, and restoring the path later does not either. `tokens/api-approved-removals.json` lists paths Ben approved. Each entry's `approved` note is `Ben, <date>, <link>`, and an empty note fails the gate. The error says to add that note or restore the path. The first pull request has no `api.json` on the base, so it passes. Fernway is left out on purpose, because it is a consumer brand and not Todae's public token API. This gate does not start or publish 1.0.0. *Why:* a deleted or retyped path breaks every theme that overrides it, and the failure should name the path.
- **CI names the components that read a changed token.** `scripts/token-consumers.ts` diffs `tokens/tokens.generated.json` and lists each component that reads a changed value, directly or through a `var()` reference or a button pack alias. The job appends that list to the step summary and does not fail the build. Preset files are out of scope. *Why:* a reviewer changing one token cannot see what it touches from the diff alone.
- **The token build lives in `scripts/tokens/`, one concern per module.** `shared.ts` holds the token types, pointer helpers and CSS block helpers; `scope.ts` the `--scope` rules; `contrast.ts` the contrast checks, on the OKLCH and APCA math it imports from `src/color/apca.ts`, a module that imports nothing; `io.ts` file reads and writes. The build runs in one direction: `serialize.ts` (CSS names, values, the catalog and override keys) imports `shared.ts`; `rules.ts` (paths, parity, slots and the resolver `rules`) imports those two; `resolver.ts` (loading and merging resolvers), `graph.ts` (reference, order and consume var checks) and `emit-css.ts` import what is below them; `build.ts` runs the build, and `cli.ts` parses `todae-tokens`. No module imports one above it. `consumers.ts` imports `consumeCssVar` and `cssVarName` from `serialize.ts` so the report uses the same pack alias the build emits. `names.ts` imports `dependents` and `readsOf` from `consumers.ts` so the name check walks that same alias graph, and it does not read files or git. `scripts/package-tokens.ts` runs that check for `pnpm tokens:check`. `scripts/build-tokens.ts` is only the `todae-tokens` bin, and `pnpm tokens` runs `scripts/build-own-tokens.ts`, which is not compiled into `dist`, so an installed package can't rewrite its own files. `scripts/tokens-builder.ts` is the published `tokens-builder` entry and exports only what companies, the docs MCP and the playground use: `buildCompanyTokens`, `cli`, `contrastResults`, `apcaContrast`, `oklchToSrgb`, `resolveEntries`, `parseScope` and the resolver types. Tests import the module they test. Imports between scripts end in `.ts`, since Node runs them with `--experimental-strip-types`; `tsconfig.scripts.json` rewrites them to `.js` for `dist/scripts`, and writes `src/color/apca.ts` to `dist/src/color`, since its root is the package folder. *Why:* the file had grown past 2,000 lines of unrelated concerns, and an entry that exported every internal made each one public API.
- **A component's token shape is resolver `slots`, not code.** Button's shape is slot groups on the `button` set and the `buttonVariant` modifier in `tokens/resolver.json`, and a company entry of the same name inherits them. A company entry may add slot groups but not change one of Todae's, and a token under a group a slot closes belongs in the entry that declares that slot. A slot group lists every child its group may have, token or subgroup, so `button.base` and each state group are closed. The build has no rule for one component. It does check every alias modifier the same way: two alias modifiers may not share a root, only a context declares `<root>.<context>.*`, a root with a `<root>.base` keeps every other token there, a name under the root (`radius`, `font`) belongs either on `<root>.base` or in the contexts, never both, a context may not be named like one of those names, and a token may not declare a consume var (`--todae-button-bg-default`) that a context or `<root>.base` feeds. A context can still add a group of its own, such as a company's `button.<variant>.lift`, when every context declares it. *Why:* a component's rules in the build script were a second place to change for a new state, and a company could not see them in its resolver.
- **Extensibility comes first.** Companies add sets, contexts, variants and densities in their own resolver and build them with `todae-tokens build`. New token features should work through that path, not by editing Todae's files. A company changes one of Todae's tokens by declaring it in a set or modifier named like the Todae entry that declares it; for a button variant, in the context named after the variant. The catalog's `entry` names that entry, with a `context` field for a button variant, and the build names it when a token is in the wrong one. A build error names the fix where it can: the token that reads a missing or out-of-order reference, the keys one context has and another lacks, the entry to list earlier. *Why:* a company author meets these rules first in an error message.
- **A scoped theme holds the whole graph.** `todae-tokens build --scope <selector>` writes Todae's tokens and the company's inside `@scope (<selector>)`, with each attribute rule also written on `:scope`, so a nested scope wins by scope proximity whatever order the files load in. A scoped element without `data-appearance` or `data-density` takes the context of the nearest element around it that has one (`@scope ([data-appearance="dark"]) to ([data-appearance])`), or the default. The scope element also sets the `--_todae-*` override inputs of the tokens it re-declares to `initial`, so an outer `ThemeProvider`'s overrides stop at it, while a provider on or inside it still applies. A sub-brand lists its main brand's token files in its own resolver; a build never layers on another company build. *Why:* a scope holding only the company's tokens would show an outer scope's value for every token it leaves alone, and Todae's tokens that read a scoped core change would not follow it, since Todae computes them only on `:root` and on elements that carry a modifier attribute.
- **`examples/fernway` is the second brand.** It themes Todae with tokens only, through the package's published entry points, and CI builds its tokens, typechecks it and bundles it. When a theming feature lands, show it there if a company would reach for it. *Why:* the token build tests run `buildCompanyTokens` on fixtures, but only a real app sees the published entry points, the generated files and the `ButtonVariants` augmentation together.
- **A nested provider keeps the enclosing one's value when it sets none.** A `ThemeProvider` with no `appearance` and a `DensityProvider` with no `density` take the enclosing provider's; only the outermost defaults, to `system` and `comfortable`. *Why:* a provider that only sets overrides shouldn't flip part of a page to the operating system's scheme or the default density.

## CSS

- **Todae's CSS sits in one cascade layer, `todae`.** `src/styles/layers.css` declares `todae.reset` (empty), `todae.base` (tokens and the modal scroll lock) and `todae.components`, and is imported first by every build entry. A company's token build adds `todae.theme` after them. *Why:* a company places Todae with one name, and its own CSS wins by layer order, not specificity.
- **Component styles are CSS Modules** in `@layer todae.components`. Components that style a single native element (Link, Table, Code and similar) use the `todae.components.native` sublayer, so container components such as Pagination beat them.
- **Take colors, spacing, radii and sizes from tokens** through their `--todae-*` custom properties rather than literals. Restyling goes through tokens first; a class works for layout.
- **Classes are camelCase**, and a part's main class is usually `.root`. Name a custom property a sheet sets for its own arithmetic `--_<name>` (`--_ring-room`), so it doesn't look like a token.
- **A component that passes a prop to its sheet through an inline custom property names it `--_<name>` too,** as `Grid.Root` sets `--_column-count` and `--_min-item-size`, and `DataList.Root` `--_min-item-size`. Only a token's custom property starts with `--todae-`.
- **Space a label or caption from its control with `Field.Group`,** a column that puts the label or caption `field.label.gap` above the control. Label carries no margin. Description and ErrorMessage keep their own top margin for use outside a group; inside one the group gives them the same distances. *Why:* Ben chose one wrapper that also covers captions, such as a `Text.Root` over a RadioGroup, which a Label margin can't reach.
- **Space layout with named gap steps, not values.** `Stack.Root` takes `gap="none" | "condensed" | "normal" | "spacious"`; each step but `none` is a contract token that reads a density token, so it follows the density. A gap that is not a step is the product's own CSS. `Grid.Root` still has one `grid.gap` and no steps. *Why:* Ben chose named steps over a free value so spacing stays on the density scale.
- **Prose type draws at `prose.font.size` and `prose.h1.font.size` through `prose.h6.font.size`.** Body refs `font.size.3`. h1 refs `font.size.6`, h2 refs `font.size.5`, h3 refs `font.size.4`, h4 refs `font.size.3`, h5 refs `font.size.3`, and h6 refs `font.size.2`. h4 and h5 are separate tokens. The sheet reads `--todae-prose-font-size` on `.root` and `--todae-prose-h1-font-size` through `--todae-prose-h6-font-size` on the heading elements, still inside the element scope. There is no class ladder. *Why:* after the type-scale strip, Prose still hardcoded `--todae-font-size-*`, so a theme could not override rendered markdown the way it overrides `text.font.size` and `avatar.size`.
- **Style markdown's bare elements through `Prose.Root`.** Its sheet reaches `h1`–`h6`, `p`, `ul`, `ol`, `li` and `blockquote` through `@scope`, with any other element as the lower bound, so a demo, card or code block inside the prose keeps its own type. It zeroes each child's end margin and the first child's start margin and spaces the rest with `:nth-child(n + 2)`, which outweighs a child component's own margins. A list with a `role`, such as the lists of Stack, Breadcrumbs and Tree, keeps its own indent and item spacing, since markdown renderers leave lists without one. The docs build compiles CSS with Lightning CSS, because Next's default CSS Modules compiler leaves the class inside `@scope` unrenamed. Inline code, code blocks, links and tables are mapped onto their components in the product's markdown renderer, a recipe on the Prose page. *Why:* one export a company can restyle sets rendered text for docs and chat alike, and Todae still styles no bare element in `todae.base`.
- **Streaming belongs to `Message.Root`, not `Prose.Root`.** `streaming` sets `aria-busy` and `data-streaming` and draws nothing; a product shows a reply still coming with Loader's `dots`. Todae does no token smoothing in JS, and a message knows nothing about any agent SDK's message shape. *Why:* Ben chose this for the chat components, so Prose stays a plain text style that docs and chat share. He dropped the caret drawn from CSS after four review rounds, because selectors can't see text nodes, so no rule placed it right in all rendered markdown.
- **Use logical properties** (`inline`, `block`) for layout, and `:dir(rtl)` for anything that must flip.
- **Some CSS rules are tested, and Stylelint checks the rest of that contract.** `src/styles/tokenConsistency.test.ts` still checks a pressed button's hover order, Prose's font-size tokens, focus rings drawn off the focused element, ring colors pointing at `focus.ring`, overlay shadow tokens, token aliases, and tones. `todae/token-root-scope` checks which token roots a sheet may read. `todae/local-custom-property` requires a custom property the sheet sets to start with `--_`. `todae/focus-ring-token` checks `outline` and `outline-offset`. `todae/disabled-state` bans opacity on a disabled state and limits its cursor to `not-allowed` or `inherit`. `todae/no-raw-literal` bans a pill radius, a numeric `line-height` other than 1, a fractional opacity, a named easing keyword, and a `1px` hairline, and it skips `@media (forced-colors: active)` the way that test used to. `todae/no-raw-value` rejects a raw color, spacing, radius, font size, or a raw color in a shadow. `src/components/noScrollbarStyling.test.ts` bans scrollbar styling, and `src/styles/no-container-transforms.test.ts` bans a `transform` on an element that may contain a tooltip trigger, except a popover's `scale` on its way in or out (see Motion).
- **Forced colors.** Where a state shows only through fill (pressed, selected, checked, current), add an `@media (forced-colors: active)` rule that maps it to system colors.
- **Use `!important` only for rules that must hold**, such as `VisuallyHidden.Root` and hidden tab panels.
- **Wrap hand-written selectors in `todae.base` in `:where()`,** so any class a company adds wins.

## Platform

- **Use the best native HTML and CSS features, with no JavaScript fallbacks and no support matrix.** The feature list is on the [Native platform](apps/docs/app/(en)/platform/page.mdx) page; add a feature there when a component starts to depend on it. The root README carries a dated table of the first browser versions that have those features, worked out from the page; recheck it when a component starts to depend on a newer feature. *Why:* Todae stays small and gets better as browsers do.
- **Overlays.** `Dialog` and `BottomSheet` render in place on a modal `<dialog>` (no portal), so they inherit the theme. `Popover`, `Menu` and `Tooltip` use `popover="manual"` with CSS anchor positioning. `Menu.Content`, `Menu.SubmenuContent` and every Popover surface (`Popover.Root`, `Coachmark.Root`, the ChipList panel and the Mention peek) mount their content on the first open and keep it after it, while the surface element itself is always there, so ids that point at it resolve: a page can hold hundreds of row menus, comboboxes and chip lists that never open, and keeping the content after the first open holds uncontrolled state and what the exit motion fades. `Tooltip.Root` renders a `<span>`, so a trigger and its tip can sit inside a paragraph, such as a citation marker in a reply; a tip holds phrasing content only, and `Tooltip.Root` logs a development error for an element that would close a paragraph, such as a `<p>` or `<div>`. *Why:* an interactive tip stays mounted while closed, so a `<div>` in a server-rendered `<p>` made the HTML parser close the paragraph. `Mention.Root`'s peek is a `<span>` popover for the same reason, and renders its content only while open, so its server HTML is an empty span. Only a pinned peek (a click, or Space on a link) moves focus and returns it to the mention; a peek that hover or focus opened leaves focus where it is, since focus moved on hover is announced and then holds the peek open. Page scroll stops through `:root:has(dialog:modal)` in CSS, not a scroll-lock hook. `Coachmark.Root` is the one overlay that dims the page yet leaves an element outside it usable, so it is not a modal `<dialog>`: `src/overlay/coachmark.ts` sets `inert` on everything but the target, what the target names in `aria-controls`, the popup, guest layers, popovers, such as the target's tooltip, and a `<dialog>` that opens while it holds, such as one the target opens, wherever it sits, through `inertOutside` in `src/overlay/inertOutside.ts`, which unmarks only what it marked and follows a target that changes, as a tour's next step does, and cycles Tab between the popup and the target itself. The dim page is a `popover="manual"` box anchored over the target whose shadow covers the screen and which presses pass through. *Why:* `showModal()` makes everything outside the dialog inert, the target included, and a coachmark exists to keep the target pressable. A dialog moves focus in as it opens, which an inert dialog refuses, and the coachmark can't know which dialog its target opens before then, so `liftDialog` lifts one out of the dim page right before it opens and dims it again once it closes: Todae's modal surfaces call it from `useModalDialog` before `showModal()`, and a dialog of the page's own is lifted on the `beforetoggle` a browser sends first. A closed dialog stays dimmed as part of the page until then, as does one already open without being modal before a coachmark held, and a page dialog lifted on `beforetoggle` stays lifted until it closes or no coachmark holds, so it stays usable through a tour's later steps, and a press in a lifted dialog isn't a press on the dim page: on 2026-11-06 a coachmark on a combobox's trigger left focus on the trigger when its dialog opened, since the target names the dialog's listbox in `aria-controls` only after that focus, and a dialog opened by a button that names nothing stayed inert.
- **Escape and close requests go to the innermost layer first, through one selection.** `useEscapeKey` holds the page's one stack of layers. A key and a modal `<dialog>`'s `cancel` (Escape, the Android back gesture, `requestClose()`) ask each layer the same question with the element that has focus, and the innermost layer that takes it acts; a layer that isn't a popup, such as a Drilldown, yields to a popup beside it. Menu, Popover, Drilldown and a range Calendar with an anchor take close requests; Tooltip and Toast take only the Escape key, so the back gesture passes a tip or a toast by. A component claims Escape by registering a layer, never by stopping the key's propagation, which can't reach the stack's document listener when React's root is the document itself (Next.js, Remix). The surface closes only when no layer takes the request, also when Chromium won't let the page cancel it. `closedby` follows the layers that take close requests registered inside the element, not whether one takes a request now, so an uncancelable request with only a hidden layer inside closes the element natively and the shell shows it again. *Why:* the back gesture reaches a modal with no key and Chromium cancels only some close requests, so the key and the gesture must answer alike, and a `closedby` read while rendering can't follow a tab switch.
- **The modal overlays share one shell, and the close parts share one button.** `components/dialogShell.tsx` holds the modal machinery (open state, presence and exit, focus, the `<dialog>` wiring, backdrop clicks, Title, Description and Close) for `Dialog`, `Drawer` and `BottomSheet`. Each passes a `DialogShell` that names what differs: its classes and exit, whether the `<dialog>` covers the screen around a `panel` or is the panel itself (which also decides what counts as a backdrop click), and whether it stays mounted while closed (`keepMounted`). `BottomSheet` adds only snap points, drag and the grabber. Every close part (the three modals' `Close`, `Toast.Close`, `Alert.Close` and `Attachment.Remove`) renders `CloseButton` from `components/closeButton.tsx`, which supplies the ghost look, the glyph, no tip and the fallback name; the caller adds its class, marker and click action. A new modal or close part builds on these. *Why:* the 2026-11-02 audit found BottomSheet had copied about 72% of the shell and the close button was copied five times, and the copies had started to drift.
- **Toast** holds text and buttons, no nested menus or dialogs. Its region follows Todae's modal stack into the front modal; a product's own modal `<dialog>` joins that stack through `useModalLayer`. Each toast, and the region itself, is a layer on the Escape stack while focus is in the region, joining when focus comes in so an overlay shown before then doesn't take its Escape: Escape in a toast dismisses it, after a layer inside it such as a button's tooltip, and Escape on the region sends focus back where it came from. `Toast.Region` composes one hook per concern: `useToastHost` and `useRaiseOnNew` in `src/overlay/useToastHost.ts` move the host with the modal stack and raise it for a new toast, and `useRegionPointer`, `useRegionFocus` and `useStackMeasure` in `src/components/` hold the hover, tap and press model, focus with its hotkey and Escape, and the stack's measured offsets. *Why:* the region was one 434-line function whose seven concerns shared refs, so changing one meant holding all of them in mind.
- **A timing only a hook reads**, such as a tooltip's show and hide delays or a step button's hold delay and repeat interval (`field.stepper.repeat-delay`, `field.stepper.repeat-interval`), is a contract token too. The hook or part reads it from the element's computed style and falls back to the token's default when it can't. The hover skip window is the exception. `useTooltip`'s `skipDelay` is 300ms when omitted, and it is not a token. Each tip reads its own `skipDelay` when the pointer enters. The open count and the time of the last hover close are what the tips share. *Why:* a theme tunes every timing in one place, CSS or not.
- **Motion** takes its durations and easings from contract tokens, respects `prefers-reduced-motion`, and only has to work in Chrome. A component that animates as it opens and closes has motion tokens of its own: `motion.duration.enter`, `motion.duration.exit`, `motion.easing.enter` and `motion.easing.exit`, plus one for any other timing or distance it animates, and one that only fades in, as Tooltip, Alert and ErrorMessage do, has only the enter pair. Its stylesheet times it from those tokens alone, never from another component's or from a shared layer, and a part that draws on another component moves with that component's tokens, as Menu and the field pickers move with Popover's, unless it has motion tokens of its own, as Coachmark's popup does. ## Accessibility

- **Follow the ARIA Authoring Practices pattern** for each interactive component, and keep that behavior in the component or a hook, not in a recipe.
- **What counts as a tab stop is answered in one place.** `src/overlay/tabbables.ts` owns it: `firstTabbable` and `getTabbables` for what Todae treats as tab stops in a subtree now (the candidates Todae recognizes, in document order, minus disabled, hidden, inert and `aria-hidden` content, and minus every radio of a named group but its one stop), `getTabOrder` for what content holds whatever styles hide now (Toolbar's arrow-key items, and a ScrollArea an ancestor hides), `getCandidates` for every kind of control content holds (Tooltip's content rule), `isReachable` for whether focus can move to an element at all (roving items carry `tabindex="-1"`), and `canFocusNow` for whether a script can focus it now, outside the tab order. Code that asks whether Tab stops on an element, or where Tab goes next, asks it; finding a component's own part by its marker, such as a chip's remove button, is a different question. Don't write a new focusable selector or visibility check; extend this module. `hidden` and `aria-hidden="true"` subtrees strictly inside the queried root count as removed content on purpose; one on the root itself does not, so a Toolbar that carries `aria-hidden` keeps its arrow keys. Content behind an open modal is not ruled out, since its inertness is a passing page state and `focus()` on it is a no-op. Two kinds of check stay apart because they answer other questions: Field's `FOCUSABLE_FIELD_CONTROL_SELECTOR` (which control a press on the field's shell focuses; like `tabbables.ts`, it leaves out `[data-todae-value-input]`), and the `checkVisibility` calls in OptionList, useModalDialog and Drilldown (whether the container is rendered at all). *Why:* three hand-written selectors had drifted, so a control one counted another skipped.
- **A named radio group is one tab stop, chosen as Chromium's forward Tab chooses it.** `tabbables.ts` lists only the group's checked radio, or with none checked, the root's first that can take focus. Whether a radio claims its group follows the browser: a negative tabindex, `disabled`, `hidden`, inert or a hidden style rule it out, and `aria-hidden` does not. So a checked radio of the group outside the root takes the group out of the root, unless the root is in an open modal dialog that radio is not in, and a radio under `aria-hidden` in the root that claims its group takes the group with it, since the root lists no `aria-hidden` content. Shift+Tab into a group with none checked lands on its last radio instead, which the list does not show. Firefox and WebKit decide the claim differently (WebKit lets any checked radio claim its group, Firefox lets a disabled one go), so the browser tests compare the list with native Tab there only where no radio has to claim; the list itself is checked in all three. *Why:* default initial focus must land where Tab would, and a radio group is one stop.
- **Scroll containers that hold controls keep focus rings whole.** `ScrollArea`, `BottomSheet.Body`, `Drawer.Body`, `Popover`, `Splitter.Panel` and the `Dialog` and `Drawer` panel run `revealRing` from `src/internal/revealRing.ts` when focus lands (Dialog and Drawer from the `<dialog>`'s composed `onFocus`, with the panel as the area), and set `scroll-padding` to a ring's width plus offset. A new part that scrolls controls with outset rings does the same. A part that draws a control's ring on a child or sibling of the focused element, such as a Checkbox indicator, the ColorPicker thumb or a Tree row, marks that element `data-todae-focus-ring=""` (a transparent outline that only gives the room counts, as on Field.OneTimeCode's row of boxes); `tokenConsistency.test.ts` lists those rules. Code that moves focus where it must not scroll calls `focusWithoutScroll(el)`, not `el.focus({ preventScroll: true })`, so `revealRing` leaves it alone too. *Why:* the browser scrolls a focused control into view by its own box, so a ring drawn on another element, such as a Field shell, can stay cut at the edge.
- **Arrows at a scroller's cut-off edges are one internal part, `ScrollEdges`.** It renders as the scroller's first child: a sticky box of no size at the content box's start corner holds absolutely placed bands, sized from the scrollport and padding that a ResizeObserver measures (its fractional content box, since a band past the scrollport by clientHeight's rounding makes overflow of its own in Firefox), so the arrows stay on the edges in block and flex layouts without a wrapper around the content, and a negative margin takes back a flex gap so the items keep their place. A grid scroller shows none, since the rail would take a grid cell. WebKit does not hold a sticky box along the inline axis of a right-to-left scroller, so the rail checks its place after each scroll and moves itself back by the difference, which is nothing where sticky holds. An arrow shows while there is room to scroll toward its edge; a mouse or pen that moves onto it (not one an arrow appears under, told apart by movementX and movementY, or by where the pointer was before the move where a browser reports no movement) scrolls each frame, carrying the part of a pixel each frame leaves over, faster the longer it rests (one even speed under reduced motion), and stops at the end. They are `aria-hidden`, never focusable, ignore touch, and cancel `pointerdown` and `mousedown` so a press neither focuses the scroller nor closes its popup. While one shows, the scroller's `scroll-padding` on that edge grows by `scroll.arrow.size`, so focus moving through the list brings a row clear of the band. The band paints `--_scroll-surface` when a Popover, Dialog, Drawer, BottomSheet or Card sets it to its own fill, else `scroll.arrow.bg`. A scroller that draws a rule along its block end sets `--_scroll-rule` on the rail to the rule's thickness, and the side bands stop above it. `ScrollArea` shows them with `arrows`; Popover (`arrows`, default on), Menu and its submenus and a horizontal `Tabs.List` (`arrows`, default on) show them by default. One page shares their watching and measuring: every scroller's arrows, every horizontal `Tabs.List` and every `useRovingFocus` group observe sizes through one shared `ResizeObserver`, and the arrows and tab lists follow children coming and going through one shared `MutationObserver` (`src/internal/sharedObservers.ts`), each target observed once however many parts watch it. That `MutationObserver` is the page's only one for `useRovingFocus` and `useHighlight` too (`src/internal/sharedMutations.ts`): a target is observed with the widest options its listeners ask for, and each listener hears only the records its own options would have given an observer of its own, those about a subtree removed from its target in the same batch included, a microtask after they happen, or at once when it takes them in a layout effect. *Why:* the 2026-11-06 Bench record showed every roving group and highlight still built a `MutationObserver` of its own, so 1,000 tab lists or toolbars carried 1,000. What they measure, in a commit or an observer callback, runs in one microtask before paint (`src/internal/layoutBatch.ts`): every rail's reads, then its writes, then which arrows show, then each tab list's scroll to its selected tab, and a measure that finds nothing new writes nothing. So a layout effect of the page's own, which runs in the same commit, sees a tab list before it scrolls to a newly selected tab; the browser paints it scrolled. *Why:* the first Bench record (2026-11-06) showed 1,000 Tabs took 2.8 s to mount, built six observers each, and laid the page out twice per Tabs, because each rail wrote its sizes and read the next list's in turn. In an overlay they run only while it is open: Popover (so Coachmark and Mention's peek too), Menu and its submenus pass their open state as `active`, so a closed one keeps no observer and reads no layout, and one that has never opened renders no rail; the rail mounts on the first open, measures as the overlay shows, stops as it closes and keeps its arrows as they were through the exit fade. A popover likewise reads its anchor's box to aim its growth only as it opens or closes. *Why:* the 2026-11-06 performance audit found every closed Menu, Popover and Coachmark ran the arrows' observers and layout reads from mount, so a table of 200 row menus did that work 200 times while showing none. A horizontal tab list scrolls sideways in one row rather than spill past its root, and its stylesheet gives the rail its negative inline margin from the first layout, so the indicator never slides in from a gap, which gives up its content-based minimum width so a flex or grid layout can narrow it. It draws the line under its tabs as a background at the foot of its padding box, since a scroller clips at its padding box and would cut the indicator that lies on a border (in forced colors, which drop that background, the line is a border just below the indicator), and it scrolls a selected tab past its edge into view on the first render, on each change of selection, once a list that was hidden shows, and when tabs arrive late or push it past the edge while the list sits where it left it (once the user scrolls, it stays put), measuring by layout offsets so an ancestor's transform changes nothing, and moving the list alone, never the page. Chromium places an anchor-positioned box in a right-to-left scroller that overflows off by the whole scroll range, so such a list sets `data-flat-indicator` and draws each tab's own indicator, which sits right but doesn't slide. Another control in the list, such as an add button, draws its focus ring inside itself, as the tabs do, since the list clips at its edges. *Why:* Ben asked (2026-11-05) for arrows that say a list goes on and scroll on hover, built once; a list cut off between rows can look finished where scrollbars hide until used, and the band size matches a menu row, as in his reference recording. The same day he asked for Tabs to scroll with them on by default, while Toolbar and ToggleGroup keep wrapping.

The focus ring goes around the track, inset (`outline-offset` of minus the ring width), so no clip or scrolling panel around a nested root can cut it. A panel scrolls its own overflow and keeps its focus rings whole like any scroll container, so one that can overflow and holds nothing focusable needs a ScrollArea for keyboard access. Saving sizes is the product's `onValueChange`. `show="start"` or `"end"` shows one panel across the root (one track, `data-show`; the default `"both"` shows the two) and takes the other panel and the handle out with `display: none`, both panels still mounted and no side marked empty; focus inside what it hides is the product's to move, and so is a way to reach the hidden panel (a Drawer, a back button), which is what keeps one panel on a narrow screen within WCAG 1.4.10 Reflow. *Why:* a sidebar, a file tree and a chat side panel keep their width when the window resizes while the other pane flexes, and a pixel size lays out on the server with no measurement; two panels per root keep the keyboard and ARIA model to the one the pattern defines, and nesting covers the rest without a pane list to register and reorder. `show` exists so a layout that runs out of room, such as the App shell's sidebar moving into a Drawer, keeps the other panel mounted: swapping the splitter for another element there would remount it, and zooming to 200% crosses such a breakpoint. Proportional splits and double-click reset are out of scope.
- **An app shell is a recipe.** The [App shell](apps/docs/app/(en)/recipes/app-shell/page.mdx) recipe puts a header, with a skip link at its start, and a `Splitter.Root` with the `Nav.Root` sidebar and `main` in one grid, and below a `matchMedia` breakpoint sets `show="end"` and moves the nav into a start `Drawer.Root`; there is no `AppShell` part. The header's one button toggles the sidebar while wide and opens the drawer while narrow, so it keeps focus across the switch; the nav renders in one place at a time and hands focus to that button through `useFocusHandoff` when it unmounts holding it, and a layout effect moves focus off the handle, which `show` hides but keeps mounted; the drawer closes whenever the page changes, in the render that shows the new page, and `restoreFocusRef` points at the new page's heading only when the page changed while the drawer was open. An overlay's focus restore records the opener once, when it opens, so a `restoreFocusRef` that changes while it is open still wins over the opener. The server sends the narrow layout. *Why:* the layout must switch without remounting the page, and the nav must never be in the page twice.
- **A filter bar is a recipe.** The [Filter bar](apps/docs/app/(en)/recipes/filter-bar/page.mdx) recipe puts one `Menu.Root` of `Menu.CheckboxItem`s per field in a `Toolbar.Root`, lists the chosen values in a removable `ChipList.Root` beside a "Clear all" button, and hands focus to the first filter button through `useFocusHandoff` when that row goes away holding focus. It announces the number of matches half a second after the last change, and not while a filter menu is open, so the count doesn't talk over each value's checked state. Todae has no `FilterBar` part or filter state, since the fields, their values and how they match are the product's, and the parts already carry the menu keyboard, checked state, chip focus and the focus hand-off. *Why:* each product filters different data, and the hard focus and keyboard behavior is already in parts and hooks.
- **A context menu is `Menu.ContextTrigger`, a region inside `Menu.Root`, not a menu of its own.** It listens for the browser's `contextmenu` event and for Shift+F10 and the ContextMenu key, which it handles itself so they work where the browser fires no event (macOS); handling the key stops Chromium's own event. A key opens the menu below the element it came from (its nearest ancestor with a box), and so does a `contextmenu` with Chromium's keyboard `button` of -1, an empty `pointerType`, or no point and no `pointerType`. Any other request, a Mac Ctrl+click and a long press included, opens at its point. Either way the menu anchors to a box in viewport coordinates on a `popover="manual"` span that `Menu.Content` shows just before itself, so the box sits in the top layer, where an ancestor's transform can't move it, and comes before the menu there, as an anchor must. The menu stays where it opened when the page scrolls or the element goes away, as a pointer's menu does; anchoring to the element itself followed scrolling but lost transforms and dropped the menu to the corner when a live update removed the element. A request lasts one open: it is dropped when the menu closes, and one the owner hasn't applied is dropped by the next press or key (not a held key's repeat or a lone modifier) or by an open asked for another way, such as a `Menu.Trigger`'s, so an owner may open the menu late, in a transition, while a request it turned down isn't reused. A request that comes while the menu is open shows its box after the menu, so `Menu.Content` shows the menu again in front of it, and the popovers held open inside it in front of the menu, keeping focus; a screen reader's request from another region while the menu has focus keeps the first opener. Escape, Tab and a press outside give focus back to what had it when the request came, while it is in the page and can take focus, else to the `Menu.Trigger`. A text field in the region keeps the browser's menu, an inner region takes a request before an outer one, and an open menu cancels `contextmenu` inside it. There is no long-press timer: iOS Safari fires no `contextmenu` on a long press, so the docs ask for a visible `Menu.Trigger` beside every context region. *Why:* the native-only rule rules out a JavaScript gesture, and a context menu is hidden, so its commands need a visible way in on every platform.
- **A submenu is `Menu.Submenu`, with `Menu.SubmenuTrigger` and `Menu.SubmenuContent`, parts of the Menu family rather than a nested `Menu.Root`.** The trigger is a `menuitem` with `aria-haspopup="menu"`, and the content is a `role="menu"` popover rendered beside it inside the menu it opens from, so the outer menu's focus-leave and outside-press checks, and the Escape layer stack, see the submenu as inside it. Each list has its own `useRovingFocus`, so keys and typeahead stay in the list that has focus. The arrow toward the line's end, Enter or Space opens it on its first item, and the arrow toward the start or Escape closes only that submenu; choosing an item or Tab closes the whole menu. The pointer resting on the trigger for `menu.submenu.delay.show` opens it without moving focus, and focus moving to another item of the outer list closes it. A pointer leaving the trigger sets a safe triangle, from where it left to the submenu's near edge, for `menu.submenu.delay.hide`: items it crosses inside the triangle don't take focus, so the submenu stays open on the way. *Why:* Ben chose the three parts on 2026-11-04 over a nested `Menu.Root`, whose `Menu.Trigger` would change element and props type by where it sits, asked for the safe triangle, and approved the two delay tokens.
- **Toolbar keeps its no-tabindex design:** Tab is steered to the edge of a run instead of managed `tabindex`. This was chosen knowing its limits (an ancestor that cancels Tab after the hop, an item that stops Tab propagating, Safari skipping buttons by default); don't switch back.
- **axe runs over the docs demos in a real browser**, with color contrast off, since contrast is APCA in the token build. `site.browser.test.tsx` runs it over the English site chrome, and `apps/docs/axe` over the built Korean pages in light and dark at desktop and phone width.

## Docs

Each component, hook and recipe gets a page in `apps/docs/app/(en)` and a Korean twin in `apps/docs/app/ko`, changed in the same pull request (see [`.agents/playbooks/docs-translation.md`](.agents/playbooks/docs-translation.md) and [`apps/docs/TRANSLATING.md`](apps/docs/TRANSLATING.md)).

- **Draw Todae's mark from `apps/docs/lib/brand.tsx`.** The header, the favicons (`/brand/mark.svg`, `/brand/mark-32.png`, and `/favicon.ico`, which wraps the 32px PNG), the touch icon (`/brand/mark-180.png`) and the link-preview card all render its shapes; don't copy the mark into CSS or another file. *Why:* each copy drifts when the mark changes.
- **A page's description fits a search result.** `remarkPageMetadata` takes the page's `export const description`, else the opening whole sentences of its intro paragraph that fit 160 wide, a Hangul or CJK character counting as two (`lib/pageSummary.mjs`); a description below 50 wide or cut mid-sentence fails the build, which names the page. Write `export const description` under the imports, in both languages, when the intro's opening sentences don't summarize the page, such as a recipe's "A recipe, not a package namespace." *Why:* search results cut a snippet near 160 Latin letters, so descriptions of up to 200 lost their ends there, and a cut mid-sentence ended in an ellipsis.
- **`/robots.txt` and `/sitemap.xml` come from `app/robots.ts` and `app/sitemap.ts`.** The sitemap lists every page once per language that has it, with its languages as alternates, as the hreflang links do, and leaves out a Korean URL that only shows the English page, which canonicalizes to English. Robots keeps crawlers off `/api/`, the MCP endpoint.
- **Page shape for a component or hook:** a short intro with a live `<Example>` and code, any topic sections, then `## Accessible composition` (**Todae handles:** / **You supply:** / **Watch for:**), `## When to use` (**When:** / **When not:**), and `## Props`. The docs MCP server reads "When to use".
- **The Todae MCP is the docs site's server** at `/api/mcp` (`apps/docs/app/api/[transport]`), not a package of its own, so it works in any client with no install. Its tools look things up, build and draft; they return files for the client's agent to save and keep nothing. A tool that builds a caller's tokens runs the built `todae-tokens` CLI in a child process with a time and memory limit, so it runs the same checks as `todae-tokens build` and a slow build can be stopped; a server instance runs at most two such builds at once and refuses more rather than queuing them. *Why:* the builder is written for trusted files and some of its checks grow faster than linearly with the input, so capping input sizes did not bound a call's cost. The [MCP server](apps/docs/app/(en)/mcp/page.mdx) page lists every tool; update it when a tool changes.
- **The MCP endpoint bounds what a request can cost before a tool runs** (`apps/docs/lib/docs-mcp/limits.ts`). It reads at most 2 MB of a body, room for 512 KB of files escaped as `\uXXXX`, and refuses the rest unread. It answers a body that isn't JSON, or that nests more than 256 levels, itself, since mcp-handler never answers either. A request makes at most 4 tool calls. The SDK walks every element of a message before any tool's limit runs, so one walk that stops at the first limit measures the body first: outside `build_tokens` files, at most 2,048 array items and object members and no key over 128 characters; inside them, the build cap and 512 KB, shared by the request's build calls. `build_tokens` keeps an element cap that its files can fill, and refuses more than 64 files before zod checks each name; every other tool gets 1,024 array items and object members, enough for `scaffold_design_system` to replace every appearance color in light and dark. The calls of a batch share one cap, the small one unless every call is `build_tokens`. Its answers are `Cache-Control: no-store, no-transform`. *Why:* zod 3 checks every element of an array after its `.max()` fails, so one cap sized for files let a 1 MB call to a small tool spend half a second and return an 8 MB error, a batch multiplied any per-call cap by its length, a 2 MB body of keys cost the SDK's own checks over half a second wherever they sat, and zod repeats a key in every issue under it, so long keys made an error four times the call.
- **Every page and endpoint response but a redirect sends `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` and `Content-Security-Policy: frame-ancestors 'none'; base-uri 'self'; object-src 'none'`,** from `headers()` in `apps/docs/next.config.mjs`. The policy sets no `script-src`, which would need hashes for the two inline appearance scripts in `SiteShell.tsx`. *Why:* the site sent no security headers, so another site could frame its pages.
- **`get_changes` on the MCP reads the package's `CHANGELOG.md`,** which the release workflow writes, and counts a change as breaking when it is under "Major Changes", or under "Minor Changes" before 1.0. It refuses a changelog line it can't place instead of dropping it, and a prerelease version, since Todae has no prerelease mode; a test fails while `.changeset/pre.json` exists. CI's test of the real changelog catches a changelog it refuses; on the live site, such a changelog fails `get_changes` alone. *Why:* an agent upgrading a project needs the changes after the version it has, which the installed package can't hold and the npm tarball doesn't ship.
- **A part with enough to say gets its own page** under its component, such as `/field/select`. List it as a child of the component's link in `siteGroups.ts`; the sidebar, built from `Nav`, shows children in a `Nav.Branch` after the component's link, not in a `role="tree"`. *Why:* Ben chose collapsible links, so every entry stays a link.
- **Every function and namespace part the main entry exports has a `*.meta.ts`**, including helpers such as `formatDate` and provider hooks such as `useStrings`; `src/metaCoverage.test.ts` fails without one. Give it a docs page: a props table on its own page or on one that already explains it, or a `PART_PAGE` entry in `apps/docs/lib/docs-mcp/mdx.ts` naming the page that explains it. It also needs When copy there. *Why:* the docs MCP lists only what has a meta, so an export without one is invisible to agents.
- **Prop descriptions** live in each part's `*.meta.ts` and reach the props table through `pnpm schema`. When one changes, update its Korean entry in `apps/docs/lib/i18n/props/ko.json`.
- **[Get started](apps/docs/app/(en)/guides/get-started/page.mdx) is the install page,** and the READMEs' install and quick start say the same in short: TypeScript 6 for the types (pinned to `~6.0` in the install command, since typescript-eslint, which Next.js's ESLint config uses, accepts TypeScript below 6.1), the stylesheet in the `todae` layer, and parts in client components on Next.js. Change them together, and check a change in a new Next.js and Vite app. *Why:* a fresh-install check on 2026-10-21 found npm refusing the install next to TypeScript 5, the quick start failing in a Server Component, and the reset in a Next.js app made without Tailwind CSS stripping Todae's styles, none of which the docs said.
- **Every MDX page lists its sections.** `lib/remarkPageContents.mjs` gives each top-level `##` and `###` heading a GitHub-style id and wraps the page in `DocsPage`, which shows `Contents` beside it on wide screens and folded under the lede on narrow ones. A heading that ends in `{/*#id*/}` uses that id instead, the same in every language, because a translation keeps the English link target while its own words would slug differently. A page with fewer than two sections gets no list. Headings scroll clear of the top bar with their own `scroll-margin-block-start`, which `Contents` reads.
- **Tables are JSX** with `Table` parts. The docs MDX has no GFM, so pipe tables render as plain text.
- **Write narrow claims.** Absolute words such as "only", "never" and "always" are the claims reviews most often find wrong. State what the code does and stop. A meta's description copies the source's JSDoc in whole sentences; without JSDoc, it says what the function returns for a valid input, with an example. It does not describe wrong-typed input, round trips ("X reads it back"), "does what Y does" or a parser's grammar; the docs page carries those details.

### Code blocks and live examples

Code on a docs page is copied into products, so write it in the package's own style and wiring. `apps/docs/lib/codeBlocks.test.ts` checks three of these rules mechanically: that each fence names one of the languages below, that no line starts with a tab, and that `...` is not used as a placeholder. It skips the pages in its `PENDING` set, which don't follow this section yet.

- **A live example is one file, shown as its own code.** Each example under `apps/docs/examples/<slug>/` is a module whose default export is the demo. A page imports it and writes `<Example of={Name} />` on a line of its own at the top level; `lib/remarkExamples.mjs` shows the whole file above the demo, without its `'use client'` line, and renders `<Name locale="…" />` with the page's language. English and Korean pages import the same file, so the code shown is the code that runs and a translation changes only prose. An example that needs the language takes the `locale` prop, never a docs hook. It imports only from the package, React and icon libraries, and uses no class from the docs stylesheet, so the code shown is all it needs. An example whose CSS is part of what a product copies, such as Avatar group's stack or Avatar's size classes, imports a stylesheet from its own folder (`import styles from './Name.module.css';`, the only CSS import the build takes), and the page shows that file after the code of the first example that imports it. `lib/exampleDependencyLoader.mjs` makes a page rebuild when an example it shows changes, and the docs MCP inlines the same code with `withExampleCode`. A fence on the page stays for code that has no demo. The build refuses an `<Example>` without `of`, since its demo would show with no code on the page or through the MCP. *Why:* Ben chose one file per example (2026-11-03, [0009](docs/decisions/0009-docs-example-files.md)) after the copies on each page drifted from the demos.

- **Every fence names its language:** `tsx` for code with JSX or a hook call, `ts` for other TypeScript, `css`, `json` or `sh`.
- **Indent with two spaces**, not tabs. In TypeScript, use single quotes for strings, double quotes for JSX attributes, semicolons, and trailing commas in lists that span lines, as `packages/design-system` does.
- **Mark left-out content with `…`**, such as `<Dialog.Body>…</Dialog.Body>`. Don't use `...`, which reads as a spread.
- **Declare each id that a snippet names in `htmlFor` or an `aria-*` attribute,** such as `const id = useId();` or `const cb = useCombobox({ … });`, above the JSX. App state such as `value` and `setValue` can be assumed.
- **Show real wiring.** A `Label.Root` sits with its control in a `Field.Group` and points at it with an id from `useId()` or a hook's `ids`, not a literal. Every control has an accessible name. Links are `Link.Root`, and a router's link goes in through its `render` prop.
- **Icons are real icons with their import,** from `lucide-react`, not placeholder names such as `YourIcon`. Inside a slot such as `Button.Icon`, put the icon element on its own line.
- **Imports.** A block with an `export function` imports everything it uses: Todae from `'@tounsoo/todae'`, or from a server entry such as `'@tounsoo/todae/code'` when a Server Component should render it.
- **The site renders code with Todae's own parts.** MDX maps fenced blocks to `CodeBlock.Root` (inside a `ScrollArea.Root`, through `DocsPre`) and inline code to `Code.Root`. The site doesn't override the code block's tokens, padding, type or colors.
- **A long code block shows a peek.** `DocsPre` shows a block of more than 40 lines as its first 20, fading out, with a Show all code button under it that sets `aria-expanded` and opens the rest. Open, the button stays at the bottom of the screen while the block runs on and folds it again, keeping its place in the viewport. The rest stays in the page, hidden with `hidden="until-found"` where the browser supports it, so find in page reaches it and opens the block. Print, and a page whose scripts don't run, show it whole. The docs MCP reads the page's MDX and the example files, so it gets every line. *Why:* Ben chose (2026-11-13) a peek for every long block over collapsing blocks fully, since the code is the point of a recipe, or splitting recipes into file tabs.
- **The site shows Todae as it ships.** `apps/docs` sets no Todae token in the site's own chrome, and its pages load no font of their own (the link-preview images draw with their own fonts); the site's own chrome reads Todae's tokens as they are. A demo, including the home showcase, may set `--todae-avatar-size` on the element it sizes. An element with `data-appearance` or `data-density`, or a scoped theme root, between that element and the avatar resets the size. Themes appear only inside the Playground, through `ThemeProvider` overrides. *Why:* people judge Todae's base theme by the site itself.

## Releases

- **CI rejects scratch paths.** An added or edited path under `.audit/`, a file named `*-body.md`, or any PNG fails the Forbidden paths job, except inside the pinned pstack copy in `.agents/pstack/plugin`, where the same job runs `.agents/pstack/check.sh` and `.github/scripts/pstack-upstream.sh` and fails on anything but upstream's files. A new file under `.claude/` fails unless the name ends in `.md`, `.json`, or `.mjs`. An edit to a file that is already under `.claude/` passes that rule, and a deletion passes. The job runs on draft pull requests. The error is one line that names the path. *Why:* local notes, screenshots, and logs are not part of the product, and the failure should say which file to drop.
- **A new docs page, section or check comes with agent docs.** A pull request that adds a docs page under `apps/docs/app/(en)/`, a group to `SITE_GROUPS`, or a job or command step to a workflow that pull requests start or a command to `pnpm check`, also changes `CLAUDE.md` and the verify skill's `SKILL.md` or `verify.mjs`. Where one or both need no change, its body says why on a line `Agent docs unchanged: <reason>`, outside any HTML comment so that it shows. The Agent docs job fails otherwise, through `.github/scripts/agent-docs.mjs`, and runs on drafts. [0016](docs/decisions/0016-agent-docs-check.md) says what it counts and misses. *Why:* agents learn the repository from those two files, and the written rule alone was missed.
- **Every remote action is pinned to a commit.** A `uses:` in `.github/workflows` or `.github/actions` names a full 40-character commit SHA, with its version in a comment, such as `actions/checkout@<sha> # v4.4.0`. A local `./` action is exempt, and a `docker://` image needs a `sha256` digest. The Static job fails on anything else, through `.github/scripts/pinned-actions.mjs`, which reads the YAML rather than matching lines, and names each file and line. Dependabot (`.github/dependabot.yml`) moves the pins and their comments in grouped monthly pull requests, at most one for the workflows and one for the setup action. *Why:* a tag can be moved to other code after review, and the release jobs hold a GitHub App token and npm's trusted-publishing token, so they must run exactly the code that was reviewed. Without updates, pinned actions would stay on old versions.
- **Checks covers every blocking job, and publishing waits for it.** The `Checks` job in `ci.yml` needs every job that can block a merge and fails unless each one passed, or was skipped on purpose: Token API and Agent docs on a push, and everything but Changes and Forbidden paths on a change that is only Markdown no tool reads or the pinned pstack copy. CI runs on every push and pull request, so `Checks` always reports, and it fails on a draft rather than reporting skipped. `release.yml` publishes only after `Checks` passed on the commit it releases. *Why:* branch protection can then require one name, a skipped required check counts as passing, and a Version Packages pull request merged on a stale base must not publish code that main's CI failed.
- **npm dependencies update in grouped monthly pull requests.** Dependabot (`.github/dependabot.yml`) proposes npm version updates from the workspace lockfile once a month, in at most two pull requests: minor and patch updates together, and major updates together. A release must be a week old before a version update proposes it. Security fixes, when the repository turns on Dependabot security updates, come as soon as an advisory is published, together in one pull request. It raises ranges in `package.json` (`versioning-strategy: increase`) rather than widening them. Playwright is left out and bumped by hand, because its version must match the digest-pinned Docker image in `ci.yml`. *Why:* every pull request runs CI, and the published package has no runtime `dependencies`, so its development tools are what these updates move; grouping keeps the count low, and the week gives a compromised or broken release time to be pulled.
- **Changesets versions and publishes `@tounsoo/todae`.** A pull request that changes what the package ships (its code, types, CSS, tokens, schema or CLI) adds a changeset with `pnpm changeset`. CI fails a pull request that changes the package without adding a changeset; tests, fixtures, snapshots, `CHANGELOG.md` (which the package doesn't ship) and dotfiles don't count, a pull request whose only counted change is to `devDependencies` that the tests use and that can't change the built output, such as Vitest or Testing Library, passes without one (`.github/scripts/changeset-exempt.mjs` lists them; Vite, TypeScript and the `@types` packages build what ships, so they aren't on it), unless it also touches `.changeset/` other than its README, whose changesets and config `changeset status` checks, and any other change that ships nothing gets `pnpm changeset --empty`. *Why:* the changelog is built from these files, so a change without one is missing from the release notes.
- **A changeset is short.** Its first line says what changed for people who use Todae, in one sentence that names the component, hook or token. It leaves out why, how and edge cases, which belong in the pull request and the docs. A breaking change adds one bullet per break, each saying what to change in your code, such as "`getTriggerProps().ref` is a callback ref; read `cb.triggerRef` for the element." `.changeset/config.json` prints each entry as that line and a link to its pull request, or to its commit when there is none, with no author or thanks. *Why:* people read the changelog to find what to change when they upgrade, and `get_changes` on the MCP hands the same text to their agent.
- **Relative imports in shipped `src` files name the emitted file,** such as `./cx.js` for `cx.ts`. `tsconfig.build.json`, which covers the files that ship (not tests or `*.meta.ts`), resolves modules as `nodenext`, so `pnpm typecheck` fails on a missing extension there. *Why:* the published `.d.ts` files keep the source's import paths, and TypeScript projects that resolve modules as `node16` or `nodenext` can't follow a path without an extension.
- **Every entry in `exports` lists `types`, then `default`, never `import`.** The package stays ES modules only, and `./package.json` is exported too. `engines.node` is `^20.19.0 || >=22.12.0`, the versions whose `require()` loads an ES module without a flag, which the `todae-tokens` CLI's `import.meta.dirname` also needs. `files` leaves out the repo-only token files (`tokens/api-approved-removals.json`, `tokens/name-grandfather.json`, `tokens/name-schema.json`), and `tsconfig.scripts.json` compiles only the bin and `tokens-builder`, so the CI-only scripts don't ship; `.changeset/config.json` doesn't count those files as shipping, and `scripts/package-files.test.ts` holds the two lists together. `pnpm ssr:smoke` installs the packed tarball into `examples/ssr-smoke`, resolves every export and loads each module entry with `import()` and `require()`, and renders server entries from a Server Component, with no `transpilePackages`. *Why:* Node's `require()` of an ES module matches `require` or `default` and never `import`, so Jest in CommonJS mode and `require.resolve` tooling failed on every entry, and a smoke run against the workspace with `transpilePackages` bypassed `exports` and never saw that.
- **Top-level code in shipped `src` files has no side effects.** A top-level value built by a call or `new` is marked `/* @__PURE__ */`, and one that reads a property, such as `styles.panel`, or spreads is built inside a function called that way. `package.json` marks only CSS files as having side effects, and `src/entries.test.ts` fails when bundling the main entry with nothing imported leaves any code. *Why:* bundlers drop an unused component only when nothing at its top level could have a side effect, and esbuild treats calls, property reads and spreads as possible ones.
- **Bumps before 1.0:** a breaking change is `minor` and everything else is `patch`. *Why:* in semver, a `0.x` minor is the breaking release, and a `major` would publish 1.0.
- **Merging to `main` doesn't publish.** `.github/workflows/release.yml` turns changesets on `main` into a "Version Packages" pull request with the next version and changelog. Merging that pull request publishes to npm through trusted publishing, so the workflow holds no npm token. npm only takes a trusted publisher for a package that exists, so the first version is published by hand. `apps/docs` is private and never published or versioned.
- **The docs deploy from `docs-stable`, not `main`.** Vercel's production branch is `docs-stable`, and only `release.yml` moves it, forward only: to the tip of `main` when its package version is on npm, no changeset that releases something is waiting, and the package source is the same as at that version's tag. When only the source differs it goes to that tag, and otherwise to the commit tagged with the latest version on npm. With no such tag it leaves `docs-stable` alone and warns. It decides from npm and the changesets, not from whether this run published, so a failed publish leaves the docs on the last release and a re-run catches up. A docs-only change goes live at once when no such changeset is waiting, and with the next release when one is. GitHub Actions builds every deployment and Vercel only hosts it ([0012](docs/decisions/0012-docs-build-in-github.md)): `docs-deploy.yml` deploys `docs-stable` to production and gives pull requests and `main` preview deployments. *Why:* the docs and their MCP server describe the package people install, so a page, prop or token on them has to be in the version on npm, and a failed publish must not move them ahead of it.
