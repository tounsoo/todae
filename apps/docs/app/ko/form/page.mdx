# Form

제출하기 전에 안의 컨트롤을 검사하고, 각 문제를 페이지의 언어로 보여 주는 네이티브 `<form>`입니다. 컨트롤에는 네이티브 규칙(`required`, `type="email"`, `minLength`, `min`, `pattern`)을 두세요. 브라우저가 내린 판정은 Todae가 읽고, 나머지를 맡습니다. 언제 보여 줄지, 문구, `aria-invalid`, `aria-describedby`, 포커스가 갈 곳입니다.

`Form.Root` 안의 각 [`Field.Group`](/field)이나 [`Fieldset.Root`](/fieldset)는 검증 범위(validation scope)입니다. 그 안에서 `id` 없이 쓴 `ErrorMessage.Root`가 범위의 첫 문제를 보여 주고 컨트롤을 거기에 연결합니다.

```tsx
const nameId = useId();
const emailId = useId();

<Form.Root errors={errors} onSubmit={onSubmit}>
  <Form.Summary />
  <Field.Group>
    <Label.Root htmlFor={nameId}>Name</Label.Root>
    <Field.Root id={nameId} name="name">
      <Field.TextInput required minLength={2} value={name} onValueChange={setName} />
    </Field.Root>
    <ErrorMessage.Root />
  </Field.Group>
  <Field.Group>
    <Label.Root htmlFor={emailId}>Work email</Label.Root>
    <Field.Root id={emailId} name="email">
      <Field.TextInput type="email" required value={email} onValueChange={setEmail} />
    </Field.Root>
    <ErrorMessage.Root />
  </Field.Group>
  <Button.Root type="submit">Create account</Button.Root>
</Form.Root>
```

아래 빈 폼을 제출해 보거나, 가짜 서버가 이미 아는 주소인 `ben@example.com`을 입력해 보세요.

## 문제가 표시되는 때

범위는 안에서 값이 바뀐 뒤 포커스가 범위를 벗어나거나, 제출을 시도하면(유효하든 아니든) 문제를 보여 줍니다. 사용자가 필드를 만지기 전에는 아무것도 보이지 않습니다. 한 번 표시되면 문제는 양방향으로 실시간입니다. 값이 유효해지면 사라지고, 다시 유효하지 않으면 돌아옵니다. 리셋하면 모든 범위가 다시 숨겨집니다. `:user-invalid`와 같은 타이밍입니다.

타이밍은 하나뿐이고 `mode` prop은 없습니다. 폼 안의 일반 `<input>`처럼 범위 밖에 있는 컨트롤도 제출을 막고 포커스를 받지만, 메시지는 보여 주지 않습니다.

## 문제의 문구

문구는 [StringsProvider](/utilities/strings-provider)에서 오며, 컨트롤의 `ValidityState`에서 처음 실패한 플래그로 고릅니다. `valueMissing`, `typeMismatch`, `badInput`, `patternMismatch`, `tooShort`, `tooLong`, `rangeUnderflow`, `rangeOverflow`, `stepMismatch`, `customError`입니다. 범위 값은 컨트롤 자신의 속성에서 읽으므로 `minLength={2}`는 "Use at least 2 characters"라고 말합니다. 브라우저 자체의 `validationMessage`는 브라우저의 언어로 나오므로, Todae는 `customError`에만 그것을 씁니다. 이는 직접 쓴 텍스트이고 번역되지 않습니다.

한 필드의 문구만 다르게 하려면 `ErrorMessage.Root`에 함수를 주세요. 함수는 오류의 `kind`와 `message`를 받습니다.

```tsx
<ErrorMessage.Root>
  {(error) => (error.kind === 'valueMissing' ? 'Add at least one tag.' : error.message)}
</ErrorMessage.Root>
```

## 제출

`Form.Root`는 `noValidate`를 설정하므로 브라우저는 말풍선을 그리지 않고, `onSubmit`보다 먼저 자체 검사를 합니다. 유효하지 않은 컨트롤이 있는 제출은 `preventDefault()`를 호출하고, `onSubmit`을 건너뛰며, 포커스를 옮깁니다. `onSubmit`은 모든 컨트롤이 유효할 때 실행됩니다. "임시 저장"처럼 `formNoValidate`가 있는 버튼의 제출은 네이티브처럼 검사를 건너뜁니다. 이는 시도가 아니라 서버로 보내는 일입니다. 사용자가 아직 닿지 않은 것은 드러내지 않고 요약의 목록도 그대로 두지만, 숨겨진 서버 오류를 다시 표시하고 유효한 제출처럼 응답을 기다립니다. `requestSubmit()`도 같은 검사를 거칩니다.

포커스는 `Form.Summary`가 보이면 그곳으로, 아니면 페이지에서 처음 유효하지 않은 컨트롤로 가며 화면 안으로 스크롤됩니다.

## 요약

`Form.Summary`는 마지막 제출에서 실패한 것을 범위마다 링크 하나로, 레이블과 메시지와 함께, `id`가 없는 컨트롤은 링크 대신 버튼으로 나열합니다. 제출이 실패하면 포커스를 받으므로 스크린 리더가 개수와 목록을 읽고, 링크는 해당 컨트롤로 포커스를 옮깁니다. 고친 컨트롤은 목록에서 빠지며, 제출이 실패하기 전이나 남은 문제가 없을 때는 아무것도 렌더링하지 않습니다. 함수 자식은 목록을 대신합니다.

```tsx
<Form.Summary title="Check these fields">
  {(fields) => (
    <ul>
      {fields.map((field) => (
        <li key={field.label}>
          <Button.Root variant="ghost" onClick={field.focus}>
            {field.label}
          </Button.Root>
          {field.error.message}
        </li>
      ))}
    </ul>
  )}
</Form.Summary>
```

## 서버 오류

서버 응답처럼 직접 찾은 오류는 컨트롤의 `name`을 키로 `errors`에 넣으세요. Todae는 여기에 쓰지 않습니다.

```tsx
const [errors, setErrors] = useState<FormErrors>({});

<Form.Root
  errors={errors}
  onSubmit={async (event) => {
    event.preventDefault();
    setErrors(await createAccount(new FormData(event.currentTarget)));
  }}
>
  …
</Form.Root>
```

서버 오류는 즉시 표시되고, 브라우저는 모르는 것을 서버는 알기에 표시되는 내용에서 네이티브 문제보다 우선합니다. 제출을 막지는 않습니다. 컨트롤을 편집하면 다음 제출까지, 또는 그 `name`의 텍스트가 바뀔 때까지 그 항목이 숨겨지므로, 다시 실패한 제출 뒤에는 같은 텍스트도 다시 표시됩니다. 리셋하면 현재 항목이 모두 숨겨집니다. 서버 오류는 비활성화되었거나 읽기 전용인 컨트롤에도 표시됩니다. 유효한 제출 뒤 편집 전에 내용이 다른 `errors`가 도착하면 포커스는 요약이나 서버 오류가 있는 첫 컨트롤로 갑니다. 같은 내용의 `errors`가 새 객체로 다시 전달되거나 빈 `errors`가 오는 것은 응답이 아닙니다.

## 브라우저가 검사할 수 없는 규칙

`Field.Root`, `Fieldset.Root`, `Checkbox.Root`, `RadioGroup.Root`의 `customValidity`는 브라우저의 `setCustomValidity`로 메시지를 설정하므로 제출을 막고 위의 타이밍을 따릅니다. 빈 문자열은 규칙이 지켜졌다는 뜻입니다. `Field.Root`에서는 필드의 컨트롤에, `Fieldset.Root`에서는 자기 컨트롤 중 검증에 참여하는 첫 컨트롤에, 컨트롤이 모두 중첩된 그룹 안에 있으면 어느 깊이든 첫 컨트롤에(메시지는 그 컨트롤의 오류가 보이는 곳에 나타납니다), `RadioGroup.Root`에서는 검증에 참여하는 첫 라디오에 적용됩니다. `Form.Root` 없이도 네이티브 API로 동작합니다.

## 범위

범위는 자기 컨트롤만 책임집니다. 안에 있는 `input`, `select`, `textarea` 중 검증에 참여하는 것이며, 안에 중첩된 범위의 컨트롤은 제외됩니다. 범위의 문제는 이름이 있는 컨트롤(비활성화되었거나 읽기 전용인 것 포함)의 첫 서버 오류, 없으면 첫 네이티브 문제이며, 각각 페이지 순서를 따릅니다. 범위가 문제를 보여 주면 안의 모든 Todae 컨트롤이 invalid로 표시되고, 컨트롤 자신의 `invalid`가 여전히 우선합니다. `invalid={false}`로 컨트롤을 뺄 수 있습니다. `invalid`가 있는 `Fieldset.Root`는 범위가 무엇을 보여 주든 invalid로 남습니다.

범위는 `ErrorMessage.Root`가 렌더링되는 동안 그 id를 컨트롤의 `aria-describedby`에 더합니다. `RadioGroup.Root`는 각 라디오가 아니라 그룹에, `Fieldset.Root` 범위는 `<fieldset>`에 더하며, 그 안의 컨트롤은 invalid로 표시되지만 같은 설명이 한 번 더 붙지는 않습니다. `ErrorMessage.Root`가 없는 범위도 컨트롤을 invalid로 표시하지만 id는 더하지 않으므로, 없는 요소를 가리키는 설명이 생기지 않습니다. 범위마다 `ErrorMessage.Root`는 하나만 쓰세요.

`Form.Root` 밖에서는 `Field.Group`과 `Fieldset.Root`가 이전과 같고, `id` 없는 `ErrorMessage.Root`는 개발 중에 오류를 기록합니다. `id`가 있는 `ErrorMessage.Root`는 이전처럼 어디서나 동작하며 연결은 직접 합니다.

`Field.TextInput`, `Field.Textarea`, `Field.Select`, `Checkbox.Root`, `Switch.Root`, `RadioGroup.Root`는 네이티브 컨트롤이므로 참여합니다. 피커와 `Field.ColorPicker`, `Field.ChipInput`은 값을 hidden input에 두는데 브라우저가 이를 검증에서 제외하므로, 이들의 `required`는 후속 작업에서 지원합니다.

## 접근성을 지키는 조합

**Todae가 맡는 것:** `noValidate`와 제출 검사. 실패한 폼은 `onSubmit`에 닿지 않습니다. 브라우저의 `ValidityState`에서 온, 페이지 언어의 문구. 문제를 보여 주는 범위의 컨트롤에 `aria-invalid`를, 그리고 `ErrorMessage.Root`가 렌더링되는 동안 그 id를 `aria-describedby`에 설정합니다. 제출이 실패하면 `Form.Summary`나 처음 유효하지 않은 컨트롤로, 요약 링크에서는 해당 컨트롤로 포커스를 옮깁니다.

**직접 제공할 것:** 컨트롤의 네이티브 규칙, 메시지를 보여 줄 각 `Field.Group`이나 `Fieldset.Root` 안의 `id` 없는 `ErrorMessage.Root`, 요약이 읽는 모든 컨트롤의 레이블. 서버 오류를 받을 컨트롤마다 `name`. StringsProvider로 번역한 문자열. `customValidity`에 쓸 직접 쓴 텍스트.

**주의할 점:** 레이블이 없는 컨트롤은 요약에서 `name`으로 읽힙니다. 모든 범위 밖의 컨트롤은 제출을 막지만 아무것도 보여 주지 않습니다. `readOnly`와 `disabled` 컨트롤은 검증되지 않지만 서버 오류는 표시되며, `Field.TextInput`은 `onChange`나 `onValueChange`가 없으면 읽기 전용입니다. 범위 안의 어떤 컨트롤도 갖고 있지 않은 `name`의 서버 오류는 어디에도 표시되지 않으며, `Form.Root`가 개발 중에 경고합니다. 메시지는 나타날 때 낭독되지 않습니다. 포커스를 옮기고 말하는 것은 요약입니다.

## 언제 쓰나요

### Form.Root

**언제:** 네이티브 규칙이 있는 폼에서 각 필드가 페이지의 언어로 문제를 보여 주고, 포커스와 ARIA가 연결되길 원할 때. 값은 갖지 않고 컨트롤에 남습니다.

**쓰지 않을 때:** 검사할 규칙이 없는 폼 → 일반 `<form>`. Enter로 보내는 컴포저 → 자체가 폼인 [Composer](/composer). 스키마나 서버가 정하는 규칙 → `onSubmit`에서 실행하고 결과를 `errors`로 넘기세요.

### Form.Summary

**언제:** 긴 폼, 또는 사용자가 고칠 것을 한 곳에서 보아야 하는 폼. 스크린 리더가 가장 먼저 읽습니다.

**쓰지 않을 때:** 처음 유효하지 않은 컨트롤로 가는 포커스로 충분한 짧은 폼은 빼세요. 포커스가 그곳으로 갑니다.
