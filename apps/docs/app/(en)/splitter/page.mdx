# Splitter

Two panels you can resize, such as a sidebar and the page beside it. `Splitter.Root` holds a `Splitter.Panel`, a `Splitter.Handle` and a second `Splitter.Panel`, in that order. `value` is the size of the first panel in CSS pixels, and the second panel takes the rest. The handle is a `separator` with one Tab stop: drag it, or focus it and press the arrow keys.

```tsx
import { useId, useState } from 'react';
import { Splitter, Text } from '@tounsoo/todae';

export function AppLayout() {
  const navId = useId();
  const [width, setWidth] = useState(240);

  return (
    <Splitter.Root
      value={width}
      onValueChange={setWidth}
      min={180}
      max={480}
      collapsible
      style={{ blockSize: '100%' }}
    >
      <Splitter.Panel>
        <Text.Root as="h2" id={navId}>
          Projects
        </Text.Root>
        …
      </Splitter.Panel>
      <Splitter.Handle aria-labelledby={navId} />
      <Splitter.Panel>…</Splitter.Panel>
    </Splitter.Root>
  );
}
```

`Splitter.Root` is a grid, and the size reaches the sheet as a custom property, so a server renders the layout with no measurement. It never overflows its container: if the container is narrower than the size, the first panel shrinks to fit and the size you hold stays as it is, so it shows again when there is room. A vertical splitter, and any splitter that should fill its parent, needs a definite size from you along its height, as the examples do with `blockSize`.

## Pixel sizes

Sizes are CSS pixels, not percentages. A sidebar keeps its width when the window resizes and the other panel flexes, which is what a sidebar, a file tree or a chat side panel needs. `min` and `max` are pixels too, and the container limits `max` as well. With no `value` or `defaultValue` the first panel starts at 240px, kept within `min` and `max`. Proportional splits, such as two equal editors, are not covered.

Saving a size is yours. `onValueChange` fires on every change, from a drag or a key, with the new size in pixels. Todae stores nothing, so keep the size where your product keeps preferences and pass it back as `defaultValue` or `value`.

```tsx
<Splitter.Root defaultValue={savedWidth} onValueChange={saveWidth} min={180} max={480}>
  …
</Splitter.Root>
```

`primary="end"` sizes the second panel instead and lets the first take the rest, for a side panel on the far edge.

## Collapse

With `collapsible`, the first panel can go to 0. Enter on the handle collapses it, and Enter again restores the size it had. A drag that goes below half of `min` snaps to 0, and a drag between that and `min` stops at `min`, so the panel is either closed or at least `min` wide. The handle's `aria-valuemin` is 0 while a panel is collapsible. A collapsed panel is hidden, so its links and buttons leave the tab order and the accessibility tree, and the handle stays as the way back. A button of your own can reopen it too: it sets the size you hold, and `aria-expanded` and `aria-controls` point at the panel, whose `id` you can set on `Splitter.Panel`.

## Keys and pointer

The arrow keys move the handle the way they point, by `step` pixels (16 by default). Moving it toward the panel being sized shrinks that panel, so which arrow grows it depends on where the panel is. In right-to-left text the first panel is on the right, so Left grows it. Todae reads the direction from the element.

A press with the primary pointer button on the handle focuses it and captures the pointer, and the size follows the pointer from there. The handle does not jump to the pointer: it keeps the distance from where it was pressed. The thin line has a hit area of at least 24 pixels centered on it, and `touch-action: none` lets a touch drag it. `data-dragging` is on the root while the pointer is down.

## Vertical split

`orientation="vertical"` stacks the panels, and the handle becomes a horizontal separator that Up and Down move. The root needs a block size, since the panels share it.

```tsx
import { useId } from 'react';
import { Splitter, Text } from '@tounsoo/todae';

export function EditorWithOutput() {
  const editorId = useId();

  return (
    <Splitter.Root orientation="vertical" defaultValue={96} min={64} style={{ blockSize: '18rem' }}>
      <Splitter.Panel>
        <Text.Root as="h2" id={editorId}>
          Query
        </Text.Root>
        …
      </Splitter.Panel>
      <Splitter.Handle aria-labelledby={editorId} />
      <Splitter.Panel>…</Splitter.Panel>
    </Splitter.Root>
  );
}
```

## Nested panes

A root holds exactly two panels. For more panes, put a `Splitter.Root` inside a panel, which is how a mail layout of mailboxes, a message list and a reading pane is built: the mailboxes split from the rest, and the list splits from the message. Each root has its own size, bounds and handle, and the inner root fills its panel.

```tsx
<Splitter.Root defaultValue={160} min={120} collapsible style={{ blockSize: '18rem' }}>
  <Splitter.Panel>…mailboxes…</Splitter.Panel>
  <Splitter.Handle aria-labelledby={mailboxesId} />
  <Splitter.Panel>
    <Splitter.Root defaultValue={200} min={160} style={{ blockSize: '100%' }}>
      <Splitter.Panel>…message list…</Splitter.Panel>
      <Splitter.Handle aria-labelledby={inboxId} />
      <Splitter.Panel>…reading pane…</Splitter.Panel>
    </Splitter.Root>
  </Splitter.Panel>
</Splitter.Root>
```

</Example>

Panels scroll their own overflow (`overflow: auto`), so content stays in its pane. A [ScrollArea](/scroll-area) with `block-size: 100%` in a panel fills it and scrolls there, with the panel itself not scrolling.

## Accessible composition

**Todae handles:** The window splitter pattern. `Splitter.Handle` is a focusable `role="separator"` with `aria-orientation` across the layout, `aria-valuenow`, `aria-valuemin` and `aria-valuemax` in pixels, and `aria-controls` pointing at the panel it sizes. It moves with the keys above, by physical direction and with the text direction, and by pointer. A handle with no name of its own is named "Resize" from the `resizePanel` string of [StringsProvider](/utilities/strings-provider). A collapsed panel is hidden with `visibility`, so it leaves the tab order and the accessibility tree.

**You supply:** A name that says what the handle resizes. `aria-labelledby` pointing at the heading of the panel it sizes, as the examples do, or `aria-label`. A definite size for the root along the axis where the panels stack, and a heading or label inside each panel. The saved size, when it should outlive the page, and a way to restore a collapsed panel for people who do not find the handle, such as a button wired as in Collapse.

**Watch for:** A handle with no name beyond "Resize", when two splitters share a page: name each one. A panel's own `aria-label` on its plain `div`, which assistive technology ignores; put the label on a landmark inside, such as a `nav`. A panel that can overflow but holds nothing focusable, such as plain text in a narrow pane: a keyboard cannot scroll it, so wrap the content in a [ScrollArea](/scroll-area), which takes a Tab stop while it overflows. A vertical root with no block size, which collapses to its content. A panel wrapped in another component: the root finds its panels and handle as direct children by the `data-todae-splitter-panel` attribute and the separator role, so the wrapper must render them as direct children and pass props through. More than two panels in one root, which the root warns about in development.

## When to use

**When:** Two areas the person should size, which keep their size while the window changes: a sidebar and main content, an editor and its output, a list and a reading pane.

**When not:** A panel that only opens and closes → Drawer or Disclosure. A sidebar that becomes a drawer on a phone → Drawer. Equal or proportional columns → Grid. A control that sets a number → Slider.
